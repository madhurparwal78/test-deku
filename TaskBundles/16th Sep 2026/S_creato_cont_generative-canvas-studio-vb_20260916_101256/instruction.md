# Quarro

Build and deploy a working web application from this brief. There is no starting codebase. When you are done, a stranger must be able to open the app in a browser, play the brief replay canvas on the home page, sign up, open the canvas they were playing with in their own studio, generate a first asset on it, and subscribe to a plan, without hitting an error page. A creator from a different studio, and anybody with no account, must NOT be able to read that generated asset by any means, and a client may read it only after it has been delivered to them and only until the delivery is revoked. The generated bytes must live in the object store at their scheme's key; a copy on the app's own disk does not count, a database column holding the bytes does not count, and neither does a row that merely says a generation happened. Credits must be exact: a retried run charges once, a failed run charges nothing, and two runs racing for the last credits cannot both be paid for.

## Overview

Quarro is an infinite-canvas creative workspace for independent designers, video editors and small studios who deliver work to clients. One subscription reaches every image, video, audio and language model the product carries. Work is built as a graph on a canvas: each node is one generation with its own prompt, model and quality tier, and wires carry one node's output into the next. The in-product assistant is called Ivo, and it can route a node to the right model when the creator does not choose one.

This build is two things on one origin. The first is the public surface that explains, prices and demonstrates the product: a home route with a real-time three-dimensional layer, a playable node graph and a corridor of finished work, the model roster and one page per model, pricing with a credit forecaster, a model comparison bench, an enterprise route, a desktop-app route, a manifesto, a blog, an about route and the legal pages. The second is the signed-in workspace behind it: studios, canvases, generation runs, a credit ledger, plans and credit packs, teammates, and deliveries to clients.

The buyer is an independent creative or a small studio principal who bills clients, and the home route addresses five audiences by name: agencies, creative directors and filmmakers, marketers, e-commerce teams, and go-to-market teams. That buyer arrives asking one question: can this replace the four subscriptions and three hand-offs my work needs today? The public surface answers by letting that visitor play a real graph from brief to finished output before they have an account, then carries the graph they were playing with into their first canvas. That playable graph is the distinctive central interaction of the product, and it is the one to get right first.

It deliberately is not: a real model provider (every output is generated inside this app, deterministically, from the prompt and the model), a payment processor (no card is collected anywhere), a mail sender, a documentation site, a live co-presence tool, or a native application (the desktop route describes one).

The genuinely hard part is that an output is private in several places at once. A generated asset belongs to the studio that made it; its bytes are in the object store; a client may read exactly the assets delivered to them and nothing else; and every read, whatever route it comes through, is decided by the application on each request. Around that boundary sits a credit ledger that must stay exact under retries, failures and concurrent runs.

## User roles

| Role | Can do | Cannot do |
|---|---|---|
| `creator` | Sign up without an invitation. Belong to exactly one studio, as its owner or as a member. Create and open canvases in that studio; add, edit and wire nodes; run nodes and rerun stale nodes, spending the studio's credits; read every output the studio generated; run the model comparison bench; deliver an output to a client by email and revoke that delivery. A studio **owner** additionally chooses the studio's plan, buys credit packs and invites teammates. | **Cannot read, edit or run anything in another studio, including an output the other studio generated or delivered.** **A member cannot change the plan, buy credit packs or invite teammates.** **Cannot read a delivery addressed to a client unless their own studio sent it.** |
| `client` | Sign up without an invitation. Read every delivery addressed to their own email address and stream each delivered output while its delivery stands. Use every public route, the replay canvas and the credit forecaster. | **Cannot read any output that was not delivered to them, or one whose delivery was revoked.** **Cannot create a canvas, run a node, run the bench, subscribe, buy credits or join a studio.** **Cannot read another client's deliveries.** **Cannot join a studio.** |

Authorization is enforced **server-side on every mutating endpoint**. Hiding a button in the UI is not authorization: a direct API call from a `client` session to any `creator`-only endpoint must be rejected by the server (an unauthorized request is denied, not served), leaving the protected state unchanged.

The same holds inside the `creator` role: a member's direct call to an owner-only endpoint is denied and changes nothing, and a creator's direct call naming another studio's canvas, node, output or delivery is denied and discloses nothing about it. Membership is read from the server's own records on every request; a role, a studio or a membership supplied in a request body is never trusted.

Signup is open. `POST /api/auth/sign-up` takes an `account_type` of `creator` or `client` and defaults to `creator`; any other value is refused as invalid and creates nothing. Both account types are self-service and neither grants anything the other lacks in a way that could be abused, because every grant is scoped to records the account owns or receives.

## Core features

### Auth

Email and password, implemented in this application, with bearer tokens. Passwords are hashed, never stored in the clear, and the exact literal `deku-demo-pw-2026` must work at login for every seeded account.

1. `POST /api/auth/login` takes `email` and `password` and returns `access_token` and `user` (with `id`, `email`, `role`, `display_name`). A wrong password or an unknown address is refused with the same outcome for both, with the error code `unauthenticated`, so the refusal does not reveal which addresses exist. A token lasts twelve hours. The client sends it as a bearer token on every request except login, sign-up, the health route and the public read endpoints.
2. `POST /api/auth/sign-up` takes `email`, `password`, `display_name` and optionally `account_type`. The password must be at least ten characters; the email must be a well-formed address; the display name must be one to sixty characters. Any failure is refused as invalid, names the offending field in the error, and creates nothing. A second sign-up with an address already in use is refused as a conflict and creates nothing.
3. A `creator` sign-up opens a new studio named after the display name, as in `Mina Park's studio`, on the `free` plan with `billing_period` `monthly` and no `credit_option`, and grants that studio `500` trial credits once. If the address has a pending invitation from a studio, the sign-up joins that studio as a member instead: no new studio is opened and no trial credits are granted.
4. `GET /api/auth/me` returns the signed-in user with their `role`, and for a creator their studio's `id`, `name` and their `membership`.
5. `/sign-in` is a form with the labelled fields `Email` and `Password` and the action `Sign in`; `/sign-up` adds `Display name` and a choice between `I make work` (a creator) and `I receive work` (a client), with the action `Create account`. A refused sign-in or sign-up shows its reason inline.
6. A token that expires mid-action leaves the page in place, shows an inline notice saying the session ended, and offers to sign in again without discarding what was being typed. There is no password reset flow and no email is sent anywhere by this product.

### Studios, plans and teammates

7. `GET /api/v1/workspace` returns the caller's studio: `id`, `name`, `plan_code`, `billing_period`, `credit_option`, `credit_balance`, `seat_limit`, `members` (each with `email`, `display_name`, `membership`) and `pending_invitations` (a list of email addresses). A client calling it is denied.
8. Five plans exist, in this order, with these codes: `free`, `creator`, `growth`, `professional`, `enterprise`. Their prices, allowances and seat limits are the table in `### Pricing, yields and the credit forecaster`. `enterprise` is not self-serve: it is reached only by booking a call.
9. `POST /api/v1/workspace/invitations` takes `email`. Only the owner may call it. It succeeds only when the studio's plan has an open seat: `free`, `creator` and `growth` allow one seat in total and so can never invite, which is refused with the error code `limit_reached`; `professional` and `enterprise` have unlimited seats. Inviting an address that already belongs to an account is refused as a conflict. Inviting an address twice is refused as a conflict. A successful invitation is listed under `pending_invitations` until that address signs up, at which point it becomes a member and the invitation is marked accepted.

### Credits and billing

10. Every studio has a credit ledger. `GET /api/v1/credits` returns `balance` and `entries`, newest first, each entry carrying `id`, `kind`, `amount`, `reference` and `created_at`. Entry kinds are `trial`, `plan_grant`, `pack`, `run` and `bench`. Spending is a negative `amount`. The balance is the sum of the entries, computed on read, and it is never negative.
11. `POST /api/v1/subscription` takes `plan_code`, `billing_period` (`monthly` or `annual`) and, for `professional` only, `credit_option` (`110k` or `300k`). It requires an `Idempotency-Key` request header. Only the owner may call it. It sets the studio's plan, records one billing event whose `amount_minor` is the monthly price for `monthly` or twelve times the per-month annual price for `annual`, in `usd`, and adds one `plan_grant` entry equal to the plan's monthly allowance. Choosing a plan grants one month's allowance; renewal is outside this build. Choosing `enterprise` or `free` through this endpoint is refused as invalid, and so is `professional` with no `credit_option`. Choosing a plan whose seat limit is below the studio's current member count is refused with `limit_reached`. Repeating the same request with the same `Idempotency-Key` returns the first result and writes no second billing event and no second grant. Worked examples: `creator` monthly records `2000`; `creator` annual records `20400`; `professional` `110k` annual records `111600`; `professional` `300k` monthly records `30000` and grants `300,000` credits.
12. `POST /api/v1/credit-packs` takes `packs`, a whole number from one to twenty, and requires an `Idempotency-Key` header. Only the owner may call it, and only on a paid plan; a studio on `free` is refused with the error code `plan_required`. Each pack adds `1,000` credits as one `pack` entry and costs `1000` in minor units, recorded as one billing event. A replayed key writes nothing new.
13. `GET /api/v1/billing-events` returns the studio's billing events, newest first, each with `kind` (`subscription` or `credit_pack`), `plan_code`, `billing_period`, `credit_option`, `packs`, `amount_minor`, `currency` and `created_at`. Only the owner may read it; a member reading it is denied. No card is collected: the billing ledger is the record of what the studio chose and what it cost.
14. Subscribing ends on a dedicated full-page confirmation at `/account/billing/confirmed`, which states the plan in the form `You are on Growth.`, the credits added in the form `50,000 credits were added to Northlight Studio.`, and the amount recorded. Buying packs ends on the same confirmation route reading, for example, `3 credit packs added for $30.`

### The canvas workspace

15. `GET /api/v1/canvases` returns the caller's studio canvases, newest first, each with `id`, `name`, `node_count`, `credits_spent`, `last_run_at` (null until a node has run) and `updated_at`. `POST /api/v1/canvases` takes `name`, one to eighty characters, unique within the studio; a duplicate is refused as a conflict and an empty or overlong name is refused as invalid.
16. `GET /api/v1/canvases/{id}` returns `id`, `name`, `nodes` and `edges`. Each node carries `id`, `node_key`, `title`, `prompt`, `model_slug`, `tier` (`standard` or `high`), `aspect_ratio`, `pos_x`, `pos_y`, `revision`, `is_stale`, `rank` and `latest_output` (null, or the output's `asset_id`, `object_key`, `content_type`, `byte_size` and `sha256`). Each edge carries `id`, `from_node_id` and `to_node_id`. `rank` is derived on read: a node with nothing wired into it has rank one, and every other node is one more than the highest rank wired into it.
17. `POST /api/v1/canvases/{id}/nodes` takes `title`, `prompt`, `model_slug`, `tier`, `aspect_ratio`, `pos_x` and `pos_y` and creates a node at `revision` one, not stale, with a `node_key` made from its title in lowercase words joined by hyphens, unique within the canvas by a numeric suffix. `model_slug` must be a manifest slug, or `auto` together with an `output_kind`; `auto` resolves at creation to the fastest available model of that output kind, ties broken by manifest order, and the node stores the resolved slug: `auto` for `image` resolves to `grain-4-turbo`, for `video` to `drift-1-6`, for `audio` to `score-lite`, and for `text` to `quill-3-mini`. An `aspect_ratio` the model does not list is refused as invalid; audio and text nodes carry no aspect ratio.
18. `PATCH /api/v1/canvases/{id}/nodes/{node_id}` takes any of `title`, `prompt`, `model_slug`, `tier`, `aspect_ratio`, `pos_x`, `pos_y`, plus the `revision` the editor last saw. A write carrying the current revision is accepted and raises the revision by one. A write carrying an older revision is refused as a conflict and changes nothing. **Two members editing one node from the same revision: exactly one edit is accepted, and the other is refused as a conflict.** Changing `prompt`, `model_slug`, `tier` or `aspect_ratio` marks that node and every node downstream of it stale; marking a node stale never changes its revision; changing only the title or the position marks nothing stale.
19. `POST /api/v1/canvases/{id}/edges` takes `from_node_id` and `to_node_id`. A wire from a node to itself, a wire that would close a loop, a wire between two canvases and a duplicate wire are all refused as invalid, and nothing is written. Adding a wire marks the receiving node and everything downstream of it stale. `DELETE /api/v1/canvases/{id}/edges/{edge_id}` removes a wire and marks the receiving node and everything downstream stale.
20. `POST /api/v1/canvases/{id}/nodes/{node_id}/runs` requires an `Idempotency-Key` header and generates that node's output. A node may run only when every node wired into it has a current output that is not stale; otherwise the run is refused as a conflict naming the upstream node, and nothing is charged. A successful run returns `id`, `status` of `succeeded`, `credits_charged` and `output` (with `asset_id`, `object_key`, `content_type`, `byte_size`, `sha256`), charges the studio the current rate for the node's output kind and tier as one `run` entry, and clears the node's stale mark. Repeating the call with the same `Idempotency-Key` returns the first run, charges nothing more, and writes no second run. Running a node that is already current generates again and charges again; its bytes are unchanged, so its output is reused.
21. A run the balance cannot cover is refused with the error code `insufficient_credits`; nothing is charged, no run is written and no object is stored. **Two runs started at the same moment when the balance covers only one: exactly one succeeds, the other is refused with `insufficient_credits`, and the balance never goes below zero.**
22. A run on a model whose manifest `availability` is `degraded` finishes at once with `status` `failed`, `credits_charged` of `0` and no output. A failed run never charges anything. The call itself succeeds and returns the failed run; a failed run is not a refusal.
23. `POST /api/v1/canvases/{id}/rerun` requires an `Idempotency-Key` header and regenerates every stale node, in rank order, returning `order` (the node ids in the order they ran), `runs` and `credits_charged`. Nodes that are not stale are not run again and are not charged. A new node that has never run is not stale and waits for its own run; any node marked stale is regenerated by a rerun whether or not it has run before. If the balance cannot cover every stale node in the batch, the whole rerun is refused with `insufficient_credits` before any node runs. Worked example: on a five-rank chain, editing the rank-two node's prompt marks ranks two to five stale and leaves rank one alone; the rerun runs ranks two, three, four and five in that order and charges four runs.
24. A node's output is a deterministic function of its prompt, its model, its tier, its aspect ratio and the digests of the outputs wired into it: the same inputs always produce byte-identical output, and changing any of them produces different bytes. Images are PNG files, stored with the content type `image/png`, whose width-to-height ratio matches the node's aspect ratio, drawn as a seeded field in the model's own gradient colours. Video outputs are animated SVG documents, content type `image/svg+xml`, whose loop runs four seconds. Audio outputs are WAV files, content type `audio/wav`, about two seconds long, synthesised from the prompt. Text outputs are plain text, content type `text/plain; charset=utf-8`, that quotes the prompt it answers. Nothing calls an outside service to generate anything.
25. A new canvas is created from an inline row at the top of the canvases table: type a name, press Enter or the create action, and the row becomes a canvas. A new node is added from the canvas toolbar and placed where the creator clicks. There is no rename: a canvas keeps the name it was created with.

### Outputs live in the object store

26. Every output is stored in the MinIO bucket named by `STORAGE_BUCKET`, reached at `STORAGE_ENDPOINT` with `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY`, and nowhere else. The object key is `outputs/{workspace_id}/{node_id}/{sha256_of_bytes}.{ext}`, where `ext` is `png`, `svg`, `wav` or `txt`: for example `outputs/7/42/3b1f0c9a8e7d6c5b4a39281706f5e4d3c2b1a09f8e7d6c5b4a3928170f6e5d4c.png`. Bytes on the app container's filesystem, bytes in a database column, and a row pointing at an object that does not exist are all contract violations, however right the page looks.
27. An output row is unique by object key: a run that produces bytes already stored reuses that output rather than writing a second row or a second object.
28. Bytes are served only through `GET /api/v1/assets/{asset_id}/content`, which streams them from the bucket with the stored content type after checking who is asking, on every request. The bucket is never made publicly readable and no time-limited link to an object is ever issued to anybody.
29. **Who may read an output.** A creator who belongs to the studio that generated it may read it. A client may read it only while a delivery of that output to their own email address stands. Everybody else is refused: a creator from another studio, a client it was never delivered to, a client whose delivery was revoked, and a caller with no token. A refusal discloses nothing about the output, and the stored object is unchanged by it.

### Deliveries

30. `POST /api/v1/deliveries` takes `asset_id`, `client_email` and an optional `note` of up to two hundred characters. Any creator in the studio that generated the output may deliver it, and the client address need not belong to an account yet; an output from another studio is refused as not found. `client_email` must be a well-formed address; it need not belong to an account yet, and a client who later signs up with that address sees the delivery. The delivery is created in state `delivered`, and the flow ends on a dedicated full-page confirmation at `/deliveries/{id}/confirmed` reading `Delivered to client@example.com.` with the address that was used.
31. `GET /api/v1/deliveries` returns, for a creator, every delivery their studio sent, with `id`, `asset_id`, `client_email`, `note`, `state` and `created_at`; and for a client, only the deliveries addressed to their own email that are in state `delivered`, each with the same fields plus the sending studio's `studio_name`. A client never sees a delivery addressed to anybody else.
32. `POST /api/v1/deliveries/{id}/revoke` moves a delivery to `revoked`. Any creator in the sending studio may revoke it; anybody else is denied. From that moment the client can no longer stream the output or see the delivery. Revoking twice leaves it revoked and writes nothing new.

### Pricing, yields and the credit forecaster

37. The pricing route renders five plan cards in plan order from `GET /api/v1/plans`, which returns each plan's `code`, `display_name`, `descriptor`, `monthly_price_minor`, `annual_price_minor`, `credits`, `seat_limit`, `yield_images`, `yield_videos` and, for `professional`, `credit_options` (each with `option`, `credits`, `monthly_price_minor`, `annual_price_minor`, `yield_images`, `yield_videos`). The `professional` top-level fields carry the `110k` option's values. For `enterprise`, `monthly_price_minor`, `annual_price_minor`, `credits`, `yield_images` and `yield_videos` are null. For `free`, `yield_images` and `yield_videos` are null.

42. The credit forecaster sits on the pricing route beneath the plan cards. A visitor builds up to six rows, each an output kind, a monthly quantity and a quality tier. Quantity runs from `10` to `5000` on a logarithmic slider and can be typed; every quantity is rounded to two significant figures, half up, so `437` becomes `440`, `1234` becomes `1200` and `1250` becomes `1300`. The total is the sum of each row's quantity times its rate.
43. `POST /api/v1/forecasts` takes `visitor_id`, `rate_version` and `rows` (each with `output_kind`, `monthly_quantity`, `tier`) and returns `id`, `rate_version`, the rounded `rows`, `total_credits`, `recommended_plan` (with `code` and, for `professional`, `credit_option`), `plan_below` (the same shape as `recommended_plan`, or null) and `overflow_cost_minor`, plus `stale`. More than six rows, a quantity outside ten to five thousand, or an unknown kind, tier or version is refused as invalid. The forecast is kept per visitor, and `GET /api/v1/forecasts/{id}` returns it.
44. The recommendation is the cheapest plan whose allowance covers the total, climbing `free` (`500`), `creator` (`20,000`), `growth` (`50,000`), `professional` at `110K`, `professional` at `300K`, then `enterprise` above that. `plan_below` is the step immediately under the recommendation, and `overflow_cost_minor` is what that lower step would pay in whole credit packs to cover the difference: the shortfall divided by `1,000`, rounded up, times `1000`. A `free` recommendation has no `plan_below` and an overflow of `0`. Worked examples under `2026-09`: `400` standard images and `30` standard videos total `58,800`, recommend `professional` at `110k`, name `growth` below, and overflow `9000`; `100` standard images total `7,200`, recommend `creator`, name `free` below, and overflow `7000`; `3000` high images total `432,000`, recommend `enterprise`, name `professional` at `300k` below, and overflow `132000`.
45. A forecast computed under a version that is no longer current is **stale**: it keeps the figure it was computed with, reports `stale` as true, and is never silently recomputed. `POST /api/v1/forecasts/{id}/recompute` recomputes it under the current version and clears `stale`. Worked example: the same `400` images and `30` videos under `2026-06` total `65,000`, recommend `professional` at `110k`, overflow `15000` over `growth`, and report `stale`; after recompute they read `58,800`, `9000` and not stale. While a forecast is stale its recommended card does not change on the page; the page says rates changed since the forecast and offers `Recompute`. The address `/pricing?forecast={id}` opens that saved forecast in the forecaster. When the pricing page loads a forecast that has been stale for more than a day, the page recomputes it and says `Rates changed, so this forecast was recomputed.`

51. Applying an edited prompt marks that node and every node downstream of it stale at once, before any rerun starts, and `Rerun graph` regenerates the stale nodes in rank order. Nodes that are not downstream of the edit are never rerun.
52. `POST /api/v1/replay/regenerate` takes `session_id`, `graph_key`, `node_key`, `prompt`, `model_slug` and `generation_token`, and never calls a live engine. When the prompt is that node's `default_prompt` and the model is its default, the result comes from the cache and the response says `source` `cache` with `nearby` false. Any other prompt or model falls back to a curated variant chosen deterministically from the prompt, and the response says `source` `curated` with `nearby` true; the node then shows the line `Showing a nearby result`. Every response carries `node_key`, `generation_token`, `source`, `nearby`, `rate_limited` and `preview_url`, an address on this origin that answers with the preview without a token, and a model of a different output kind from the node is refused as invalid.
53. Generation tokens only move forward. For each session and node the server remembers the highest token it has accepted; a request carrying a lower token is refused with the error code `stale_generation` and returns no result, and a request repeating the accepted token returns the same result again. In the page, a result that arrives carrying a token older than the node's current token is discarded, so an older prompt can never overwrite a newer one. **Worked case:** a visitor edits rank two of a five-rank graph, starts a rerun, then edits rank four while ranks three and four are still regenerating; the in-flight rank-four result is discarded, rank five stays stale until both edits settle, and ranks already regenerated that are not downstream of the second edit do not run again.
54. Public reruns are limited to `30` per session per hour and `300` per address per hour. Past either limit the request still succeeds but degrades: the response carries `source` `curated` and `rate_limited` true, and the page says so in the node. A rate limit never produces an error.
55. Each claimed node takes the graph node's key as `node_key`, its title, model and aspect ratio, the default prompt unless overridden, tier `standard`, revision one, and a position laid out by rank; the wiring is copied, and each stale key is marked stale. Claiming the same session again returns the same canvas and creates nothing new; claiming a different session when `My first canvas` already exists names the new canvas `My first canvas 2`, then `My first canvas 3`. The sign-up flow calls it straight after the account is created, so the visitor's first canvas is the graph they were playing with.
56. The hero's prompt capsule starts the replay: submitting it scrolls to the graph and shows the typed text as the graph's brief in the visitor's session.

### The model comparison bench

57. `/bench` runs one written brief against two to four models at once. It requires a signed-in creator, because every frame spends the studio's credits. The brief is one to four hundred characters. Models are chosen from a chip row drawn from the manifest; selecting a fifth is rejected, and the earliest selected chip flashes its border in the accent for a moment instead of being silently dropped.
58. `POST /api/v1/bench/runs` takes `brief`, `model_slugs` (two to four distinct manifest slugs) and an `Idempotency-Key` header, and returns the run at once with `id`, `status` of `running` and one frame per model in selection order, each frame with `model_slug`, `state`, `latency_ms`, `credits_charged` and `failure_reason`. Fewer than two or more than four slugs, a duplicate slug, an unknown slug, or an empty or overlong brief is refused as invalid. A replayed key returns the same run and starts nothing new. A bench run whose models' standard costs together exceed the studio's balance is refused with `insufficient_credits` and starts nothing.
59. `GET /api/v1/bench/runs/{id}` returns each frame's state independently, so each result can be shown the moment it lands. Frame states are `running`, `succeeded`, `failed` and `timed_out`. A model answers after a simulated delay set by its latency band: a `fast` model within about half a second, a `standard` one within about one and a half seconds, a `slow` one within about three seconds. `lumen-preview` always fails at once with the reason `Engine unavailable`. `driftwood-beta` never answers and its frame becomes `timed_out` once the thirty-second deadline passes. A succeeded frame carries a `preview_url` and costs the model's standard image, video, audio or text rate; a failed or timed-out frame costs nothing.
60. A run belongs to the studio of the creator who started it: only a creator of that studio may read its charges, retry a frame or pick, and idempotency keys are scoped to that studio. Once every frame has finished, a run with two or more failed or timed-out frames is `voided` and any other run is `completed`. Charges are written only when the run finishes: a `completed` run writes one `bench` entry per succeeded frame, and a `voided` run writes none, so no frame on it is charged, including frames that succeeded, and the page says `Two models failed, so this comparison was cancelled and nothing was charged.` A failed frame holds its place in the row, states which model failed and why in one line, and offers `Retry this model`.
61. `POST /api/v1/bench/runs/{id}/frames/{model_slug}/retry` retries one failed or timed-out frame of a completed run as a fresh attempt, charged only if it succeeds. Retrying a succeeded frame, or a frame on a voided run, is refused as a conflict.
62. `POST /api/v1/bench/runs/{id}/pick` takes `model_slug` and records the visitor's pick once per run; a second pick on the same run is refused as a conflict. A pick on a run with fewer than two succeeded frames is refused as a conflict and nothing is recorded; picking a model that did not succeed on that run is refused as invalid.
63. Bench outputs are not kept: a frame's preview exists for the session only, and nothing from a bench run is written to the object store. The run record keeps the brief, the models, per-frame latency and charge, the pick and a coarse region, for ninety days, and it does not name the person who ran it. `GET /api/v1/bench/win-rates` returns pick-based win rates over a rolling thirty days, listing only model pairs with at least `200` runs between them, so a fresh environment returns an empty list.

## UI/UX notes

Somebody arriving should understand within one screen that this is a single canvas reaching every generation engine, and should feel the work shown is considered and made with care rather than generated in bulk. The register is split and the split is deliberate: the public routes are creative-professional marketing, where atmosphere is allowed and finished work is the first thing seen; the signed-in routes are a working tool, quiet, dense and predictable, with no editorial composition and no ornament competing with the canvas. The public surface is unusually rich for a marketing site, carrying a real-time three-dimensional layer, a physics simulation and generated sound, and a build that treats it as an ordinary marketing site will look nothing like it.

It has to convey value, so the public routes give finished work room and let one thing dominate each view. It has to guide, so every public page leads with one primary action and everything else is visibly quieter. It has to reassure a creator who is paying, so nothing moves on the billing route while a price is being read and the confirmation is still and plainly worded. Things arrive rather than perform: **restraint over spectacle** in how things move, even though the surface is expensive to draw.

**Accessibility floors.** WCAG 2.2 AA holds with every effect running. Body text against its ground meets a contrast of at least 4.5 to 1 on both grounds, and large text and meaningful glyphs at least 3 to 1. Touch targets are at least 44 by 44 CSS pixels, including the forecaster slider handle on a narrow screen. Full keyboard navigation reaches everything, with a focus ring always visible: the ring is drawn in the accent with a gap in the opposing ground so it survives on both grounds and over live three-dimensional content. Icon-only controls carry labels. The three-dimensional layer is decorative and hidden from assistive technology; the node graph and the replay are not: they expose an ordered list of ranks, each a list of nodes, each node naming its title, its model and its output kind. Every gesture has a keyboard equivalent: arrow keys move the scrub by one rank, Enter expands a node, and the transport comes before the graph in tab order. The pointer spotlight never hides content that is not otherwise visible. Elements waiting to be revealed are hidden from assistive technology until they arrive. Every content image carries alternative text, and decorative images declare themselves decorative.

**Mode.** There is one designed appearance. Grounds are fixed per section, there is no light or dark toggle, and the product does not follow the visitor's system theme.

**Grounds.** Two grounds, switched per section rather than per page. The dominant ground is a near-black neutral with near-white type; the alternate ground is a near-white neutral with near-black type. Dark dominates by a wide margin: most sections sit on the dark ground and the light ground is used for the hero, the manifesto and a few interludes. A third near-black, a shade lighter than the ground, appears only inside the edge fades.

**Palette by role.** Card faces floating on the dark ground are the brightest near-white neutral, and an alternate card face is a near-white with a faint warm cast. Card type and the sticky column rule of the comparison table use a near-black with a faint warm cast rather than the ground's neutral black. Secondary type on dark is a light neutral, tertiary type and control arrows a mid neutral, and muted metadata a light neutral with a warm cast. Hairlines on dark are a deep neutral and hairlines on light a dimmer near-white neutral; a filled control on light sits on a near-white neutral. Four deep neutral steps carry the dark surfaces: a raised panel, a recessed panel, a panel border, and a hover ground, each visibly separate from the next without a shadow. Opacity variants of any of these are only ever the same colour at lower strength; no new tint is ever introduced.

**The accent, rationed.** One accent: a mid, vivid red leaning toward orange, a vermilion. It fills the header's `Start creating` action, becomes the ground of every other primary action when pointed at, and marks the active switcher tab, the node output-kind badge, the wire, the plan glow and the focus ring, and it never covers a large area: its total painted share of any screen stays under eight percent of the frame, and it never becomes a section ground. It never carries paragraph text on the dark ground; where it colours a short label on dark, such as the announcement action, that label still meets 4.5 to 1, and longer accent type sits at headline size or on the light ground. A secondary accent, a light, vivid blue, marks links and informational states. One gradient exists and is used on exactly one action: it runs from a light, soft indigo (a violet) at its near end to a mid, vivid blue at its far end. A light, soft amber, a pale yellow, belongs to exactly two things: the sign-in control and one enterprise chip. **Exclusivity over variety**: a colour that means something appears nowhere else.

**Meaning colours.** In the signed-in tool, three meanings get one colour each and appear nowhere else there: failure (a failed run, a refused action, a failed bench frame), success (a completed run, a delivered output) and in progress (a running frame, a regenerating node). A stale node is shown by desaturation, never by borrowing one of those three. There is no separate warning state: the warning triangle only ever marks a failure and takes the failure colour. Meaning is never carried by colour alone: every state also carries a word or a mark. The exact shades are yours, so long as those roles and those exclusivity rules hold.

**Type.** Four roles, and the personality lives in the contrast between them. A display serif with real character and a true italic sets every headline, reading like a magazine rather than software. A text sans at a regular and a bold weight carries body, controls and navigation. A geometric sans carries section tags and small-caps labels. A variable-weight monospace carries metadata, model names, vendor names and every credit figure, which is what makes the pricing read as measured rather than marketed; figures in it line up in a column wherever amounts stack. The display headline is roughly three and a half times the body size. It is set two ways that are not interchangeable: a running headline with generous leading, and a stacked headline whose leading is locked to the type size so deliberate line breaks sit tight. Below the display size there are a secondary and a tertiary headline, a card headline, a subheading, two lead-paragraph treatments, a relaxed body, the body itself, a small body for card metadata, a tag size for chips, a legal size, and two very small label sizes used only on the canvas for node titles and port labels. The exact families and sizes are yours, so long as those roles, that ratio and that ladder hold, and every family loads so text is readable before the face arrives and nothing shifts when it does.

**Shape.** Corners are calculated rather than fixed. Most controls and tabs are barely softened, and that is the default. Cards and large actions are noticeably rounder; chips and the smallest tags are nearly square; article and audience cards sit between; the modal is the roundest thing in the product. Pills and circular controls are fully round, expressed so that a non-square element still reads as a pill and never as an ellipse. Nested corners are concentric: an inner corner's roundness is the outer corner's minus the padding between them, so the shapes stay concentric when either changes. The pricing card's side carries a concave notch cut out of the card, which no corner rounding could express.

**Density and spacing.** Spacious on the public routes, where the gap between sections is several times the gap under a heading, shrinks by about a third at the laptop tier and to about a quarter of its widest value on a phone. Card interiors are generous on a wide screen and a little tighter on a phone. Compact in the signed-in tables, where rows sit tight so a studio's whole canvas list fits one screen. Every gap is a multiple of one base unit with a half step; the base unit is yours.

**Components behave, not just appear.** Every action has resting, pointed-at, pressed, focused, unavailable and pending states, and unavailable is never signalled by colour alone. Every panel that covers the page closes on Escape and on a click outside it. Every destructive action, revoking a delivery or deleting a wire, asks once and names what will be removed. Every input has a visible label above it and its error directly beneath it.

**Motion is eased, and it has one signature.** Things arrive rather than perform. The signature movement is a hard decelerate: a block covers most of its distance in the first third of its time and then eases to a stop over about half a second, so it feels caught rather than played, and it is never shortened to the point of snapping. Everything that fades or sharpens into place uses that one movement. A symmetric ease belongs to deliberate state changes, a long decelerate to large travel, and a gentle symmetric ease to buttons; colour-only changes on small utility controls are the quickest thing in the product. Exactly one movement overshoots its target and settles back, and it belongs only to node cards entering on the canvas; putting it on the buttons would make the surface bounce. Two things never stop moving: a film grain drifting over the dark grounds, run as two layers at different speeds, one twice the other, at a constant rate so it never pulses or visibly repeats; and a pulse travelling along each accent wire, crossing in the first half of its cycle and resting for the second, so a canvas of many wires reads as occasional signal rather than noise. Interruption is designed too: every reveal can be interrupted and settles from wherever it is, never snapping to either end. The forward arrow in an action never slides: it shrinks away in place and redraws in place, and an interrupted erase always finishes before the redraw starts.

**Reduced motion is a designed track, not a switch.** When a visitor has asked for less motion, the smoothed scroll becomes native scroll; headings arrive all at once by fading; images fade in without the focus-and-colour development; reveals fade without moving; the static drawing tier applies, so the three-dimensional scene is replaced by the flat drawn medallion and the physics coins are drawn at rest where they would have landed; the sound-reactive visual holds a still waveform; the grain is rendered once and holds; wires show at full stroke with no pulse; the plan glow holds still at the middle of its breath; the pointer spotlight rests at the section centre; the border sweep holds still halfway; the card corridor holds its middle arrangement; node cards appear by fading without overshoot; and the replay scrub moves in whole ranks with a readout. Nothing a visitor can do differs between the two tracks: every node is reachable, every prompt editable and every comparison runnable.

**Responsive.** Two real turning points, roughly a tablet width and a small laptop width, plus a few one-off adjustments for very wide screens that belong to individual components and are never promoted to system-wide breakpoints. Layout holds at every width between them. Anything that responds to a pointer hovering is switched off where no hover exists, so a tap never leaves a control stuck in its pointed-at state; the pointer spotlight exists only for a fine pointer; the smoothed scroll is off for a coarse pointer. At a narrow viewport nothing overflows sideways and every navigation target stays reachable. The comparison table becomes a sideways-scrolling region with its first column pinned and never collapses into stacked cards; the replay graph becomes a vertical list, one rank per screen, with short connectors between ranks, and loses no capability; the bench becomes a sideways strip of frames with the brief pinned above.


**What it must not look like.** No page dominated by a single hue family with no second signal; the accent is a spark on a neutral field, never a flood. No flat imitation that drops the three-dimensional glass, the physics or the sound because they are expensive. No decoration standing in for work: the corridor, the node showcase and the model galleries show outputs, not abstract shapes. No marketing composition inside the signed-in tool. No shiny opaque plastic where glass is asked for. The word `seamless` appears nowhere in the product's copy, and every quality claim resolves to a number or a named capability.

## Technical requirements

The rendering model is a client-rendered single-page application talking to a JSON API on the same origin. The language is TypeScript on Node 20, for both halves. The frontend is SolidJS, built with Vite and served as a production build. The backend is Express on Node 20, which serves the built application, the JSON API under the `/api` prefix, and the generated preview images and favicon. The datastore is PostgreSQL, reached through `DATABASE_URL`. The object store is MinIO, reached through `STORAGE_ENDPOINT` with `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY`. Authentication is email and password implemented in this application, with bearer tokens. `GET /api/health` returns `200` once the app is ready. Requests are logged as one structured record each on standard output, carrying the correlation identifier.

Use only the libraries named here plus their direct dependencies. Do not introduce a second database, cache, queue, object store, identity provider or mail vendor - the only backing services available in this environment are PostgreSQL and MinIO, and reaching for anything else is a contract violation. Both are already running and reachable at the variables above; do not download, install, compile or start a copy of either. Libraries for drawing, three-dimensional rendering, physics and sound are yours to choose, so long as they install from the public package registry at build time.

**What the browser receives.** Because the body renders in the browser, the HTML the server returns for every public route must already carry that route's own title, meta description, `og:title` and `og:image` meta properties, and the favicon declaration, so a link preview and a search result describe the right page without running any script. The server knows the route table, including every model slug from the manifest, and answers an address that matches nothing with a not-found status and the not-found page. Route changes inside the application do not repaint the header or the footer.

**API conventions.** Product endpoints carry their version in the path under `/api/v1/`; the auth routes and the health route are unversioned. A field is added without a version change and is never removed or repurposed without one. Every error uses one envelope: `{"error": {"code": ..., "message": ..., "correlation_id": ...}}`, where `code` is a stable machine code, `message` is one human sentence, and the same `correlation_id` is returned in the `X-Correlation-Id` response header. The codes are `invalid_request`, `unauthenticated`, `forbidden`, `not_found`, `conflict`, `insufficient_credits`, `limit_reached`, `plan_required` and `stale_generation`. Every refusal is a client error; nothing a caller sends produces a server error or a silent success. Where a list paginates it does so with an opaque cursor.

**Retries and races.** A client that retries a request must never be charged or credited twice. Node runs, reruns, bench runs, subscriptions and credit packs carry an `Idempotency-Key` request header, and repeating a key returns the first outcome without writing again: no second charge, no second billing event, no second grant. A request to one of those endpoints without the header is refused as invalid, and reusing a key with a different body is refused as a conflict and writes nothing. Under simultaneous requests, exactly one of two runs racing for the last credits succeeds and the other is refused with `insufficient_credits`; exactly one of two edits to a node from the same revision is accepted and the loser receives a conflict response; and the balance never goes negative. These outcomes must hold for requests that genuinely arrive at the same moment, not only for requests that arrive one after another.

**Generation.** Outputs are generated inside the app, procedurally, with no call to any outside service and no stored sample files: a seeded gradient field in the model's gradient colours for stills, the same field slowly shifting hue for timed output, a synthesised tone for audio, and a short paragraph for text. Replay curated variants and model-page samples are produced the same way. Output generation happens server-side so the bytes that reach the object store are the bytes a later read streams back.

**The three render systems.** The public surface composites three independent systems and keeps them separate: one persistent three-dimensional canvas, the node graph drawn as ordinary page elements and vector wires above it, and the page's own effect layer across both. Every scroll-linked effect and the three-dimensional scene move in step with one another and with the smoothed scroll, so nothing lags or leads the page.

**Performance budgets.** Per public route: largest contentful paint within 2.5 seconds on a connection slowed to a quarter of normal speed, interaction to next paint within 200 ms, cumulative layout shift at most 0.1, and time to first byte within 600 ms. All three render systems together hold 60 frames per second on mid-tier hardware. The three-dimensional layer never renders at more than twice the layout pixel density and stops drawing when it is off screen or the tab is hidden. The model roster renders all of its entries without skipping any, keeps its script payload under 90 KB compressed, and responds to a group change within 100 ms. The blog responds to a filter change within 200 ms with a hundred posts. A node graph stays smooth with twelve nodes and eleven wires. The app stays responsive with a hundred models in the manifest, a hundred blog posts, sixty nodes on one canvas, and ten thousand entries in one studio's credit ledger. Model-page samples and corridor stills are served in a modern compressed image format with a size for each width; canvas outputs stay PNG. Every still declares its intrinsic dimensions and a width-appropriate source so settling never shifts layout.

**The degradation ladder.** Three drawing tiers, and they differ only in how things are drawn, never in what the visitor can do. Full: a device with at least 4 GB of memory, WebGL2, a fine pointer and no reduced-motion preference gets everything. Reduced: less memory, a data-saving preference, or frames sustained above 20 ms over sixty frames drops the pixel density to one, replaces the post-processing chain with a direct render, halves the corridor, renders the grain once, shares one pulse across wires, loads outputs at half resolution, and replaces every backdrop blur with an opaque ground. Static: no WebGL2 support, or a reduced-motion preference, replaces the three-dimensional canvas with the flat drawn medallion, does not mount the physics, turns every scroll-driven effect into a one-time reveal, and stops the pulses. The document element carries `data-gl-tier` set to `full`, `reduced` or `static`, and `data-motion` set to `full` or `reduced`.

**Sound.** Nothing makes a sound until the visitor deliberately turns sound on, no audio context resumes on load, and the choice is kept for that visitor. The document element carries `data-sound` set to `on` or `off`, and it reads `off` on a first visit.

## Front-end specification

This section carries the visual detail every route needs. Nothing here restates a rule from `## Core features`, and every value is described as a relationship, a character or a behaviour; the exact values are yours.

### The design values and how components use them

Every component reads its colours, corners and insets from named design values declared once for the whole product, and a hover changes a component's named values rather than swapping it for a different look, so a control and everything drawn around it always change together. A small set of named values is load-bearing: the arrow colour, ground, hover ground and hairline of the disclosure rows; the size of the stepped pixel corner; the width of the travelling border sweep; the outer corner and inner inset of blog and audience cards; the outer corner, inset and derived inner corner of open-role cards; the start and end directions of the edge fades; and the drift distance of the hero gradient.

### Iconography

Thirty-nine marks, every one drawn inline from vector geometry, none a font glyph and none a picture file, every one taking its colour from the text around it so a hover recolours it. The wordmark is a single filled, horizontally symmetric ribbon: two vertical edges pulled toward the centre by shallow arcs that meet at a waist, like a bow tie with curved sides; it is short in the header. The menu control is three horizontal strokes and is the only stroked mark in the set. The credit medallion is a coin carrying the ribbon inset, used beside every credit figure: a middle size in the pricing credit rows and a larger size in the comparison table, and a small inline version beside the smallest credit figures. A wide lockup of the same ribbon, in the deep neutral, serves as a full-width section rule. An organic lobed blob is a section ground on narrow screens only and is hidden from the tablet width up. A signature scrawl, one continuous line of many curves, closes the manifesto: upright and scaled to its container on a narrow screen, lying flat on wider ones, and larger again from the laptop width. A rule mark of two filled bars serves as a minus and as a list bullet. The remaining thirty-one are a check, a chevron in four rotations, a close cross, a plus, an outward link arrow, a play triangle, a pause pair, a search lens, a filter stack, a sort pair, a copy mark, a download arrow, one platform mark for each of three operating systems, seven social marks, a disclosure caret, a spinner arc, an information circle, a warning triangle, and four output-kind badges for image, video, audio and text. ### The chrome

A full-width announcement bar sits above the header on the dark ground, short, carrying one sentence and one action whose text is in the accent; it scrolls away with the page and has a dismiss control. The header is not a full-width bar: it is a floating capsule on the dark ground, inset from the top-left, holding the wordmark and the menu control, above everything else on the page. Two controls float at the top-right inset: a filled pale-yellow `Sign in` leading to `/sign-in` and a filled accent `Start creating` leading to `/sign-up`; once signed in they are replaced by the studio name and a `Sign out` action. On a narrow screen `Sign in` drops away and `Start creating` stays. A sound toggle with a small waveform sits beside the menu control.

Every control has a stepped pixel corner rather than a radius: each corner is a tiny square notch, like something drawn on a low-resolution screen, drawn by two extra layers that recolour in lockstep with the control. The primary action's pointed-at state changes seven things together: its ground moves from the light ground to the accent, its text and border move from warm near-black to near-white, and both corner layers follow the text and border. A pointed-at state that misses the corner layers leaves the corners in the resting colour and the control visibly comes apart. Forward arrows inside actions erase and redraw in place.

### Motion, in detail

Six movement characters carry every transition and reveal, and each transition or reveal uses one of them: the signature hard decelerate for every fade and focus reveal; a symmetric ease for deliberate state; the single overshoot, scoped to node cards entering; a long decelerate for large travel; the gentle symmetric button ease; and a quick colour-only ease for utility controls. The continuous loops (the grain drift, the wire pulse, the plan glow's breath and the caret blink) run at a steady, unchanging rate instead; the hero glow breathes on a slow symmetric ease. Durations climb in a fixed ladder: utility colour changes are the quickest; the button's pointed-at change is a touch longer; disclosure and the three-dimensional canvas fade-in take about a third of a second; roster icon changes a little longer; the roster's tab underline a little longer again; fades and focus reveals about half a second; a long crossfade longer still; and an image's final opacity settle about a second, twice the length of its focus change. No transition or reveal uses a speed outside this ladder to feel special; the continuous loops keep their own, much slower cycles.

Seven named moments exist and each must be recognisable: the **grain drift**, two noise layers walking slowly across the dark grounds at different speeds, blended so dark areas darken and light areas lighten, inside an isolated layer so the dark sections do not lift; the **wire travel**, a pulse crossing each wire and then resting; the **plan glow**, a ring breathing slowly around one plan card between a tighter, fainter state and a wider, stronger one, blended in a perceptual colour space so it never dims as it passes the middle of its breath; the **arrow erase** and **arrow draw**, the forward arrow shrinking out and growing back in place; the **hero drift**, the hero's warm gradient drifting gently up and down; and the **hero fade**, the hero arriving once on load by fading in while settling from very slightly larger.

### The reveal and scroll system

The page scrolls on a smoothed position: native scrolling is intercepted and the page is moved under a position that eases toward where the visitor scrolled, which gives long sections their weight. The root marks the smoothed scroll as active on every public route. It is off under reduced motion and for coarse pointers.

Two kinds of scroll behaviour, and they are never confused. Continuously scrubbed properties follow scroll position exactly and reverse when scrolling reverses: the accent glow behind the hero (its position and strength), the card corridor, the model still grid (its strength), the plan card's shadow, the audience panels, and the focus of the canvas surface. Threshold reveals fire once when about a fifth of the element is visible, then let go: section headings and the roster's tab underline. Implementing a scrubbed property as a one-time reveal produces a visible step.

Five entry poses, each belonging to one kind of element, and using one pose for everything is the commonest way this system is got wrong: a card arrives slightly smaller and from a little below; an overlay panel arrives even less reduced from a shorter distance; a whole three-column grid grows slightly with no travel at all; a split headline word rises a short distance at full size and is never scaled, because scaling type mid-reveal makes the letters shimmer; and a list item or paragraph rises the same distance as a card with no scaling. The larger the element, the smaller its scale change and the shorter its travel.

Headings split into words that rise from a clipped baseline one after another, each a fixed short step behind the last, and the whole stagger is capped so a long heading never takes longer than a short pause to finish.

Images develop rather than fade. A settling image starts out of focus and in black and white; focus and colour then resolve on separate schedules, so for a moment the still is sharp but grey and for another it is coloured but soft, and the opacity finishes last on a schedule about twice as long as the focus change, so a still reads as a photograph developing. The settling element carries its own reduced-motion override so the reduced track inherits it.

### The three-dimensional layer

One persistent canvas, pinned to the top of the viewport behind every public route, transparent to the pointer and isolated so the page's blend effects composite against it rather than through it. It is mounted once and driven from the smoothed scroll position, never one canvas per section. It starts invisible and fades in only after its first frame has genuinely rendered and its shaders have compiled, so a visitor never sees an empty rectangle.

The object in it is the credit medallion as a real piece of glass. Its material is physically-based, described by real properties such as roughness, metalness and transmission rather than a hand-tuned appearance, and the material is transmissive with refraction and an environment map: light passes through it, bends by its refraction as it enters, dims and tints with the thickness it travels, and picks up a reflection of its surroundings from an environment map (both a flat panorama and a cube of six faces) of a bright sky half, a dark ground half, a soft horizon and one small hot highlight. That environment map is what makes the glass read as glass, so it deserves the most care of any drawn substitute. It is lit by three kinds of light at once, a distant directional light, a spot light and a point light, so it catches highlights inside its body. A shiny opaque surface with a reflection painted on is the usual shortcut, reads as plastic, and is not acceptable. The medallion rotates in the home hero and sits beside every credit figure on the pricing route. It is composed from simple forms, a turned rim, an extruded ribbon and a soft bevel, keeping its part names, with its scroll-driven motion described as keyframes at the scroll stops. The medallion's mesh is composed in code and compressed at build time rather than committed as a file; mesh compression applies on the wire, and a compressed-model loader decodes it off the main thread. A perspective camera views the scene. A full-viewport program receives the viewport size whenever it changes without being rebuilt, and a depth pass feeds a short post-processing chain of at least two passes into off-screen render targets before the frame reaches the screen. Repeated objects are drawn together as instanced meshes, one draw call per set.

### The physics layer

A real rigid-body simulation, not a scripted animation. On the pricing route, beneath the plan cards, a handful of credit medallions fall, strike one another and settle into a heap when the section arrives, and moving the `Professional` stepper to `300K` drops more of them onto the heap. The simulation steps at a fixed rate from the one render loop with drawing interpolated between steps, so the coins come to rest in the same place on a fast machine and a slow one; bodies at rest stop being calculated; stepping stops when the section leaves the viewport. Under reduced motion the coins start where they would have landed and hold. At the static tier the layer is not mounted.

### The sound layer

Sound is synthesised, never played from a file: a quiet ambient bed made of slightly detuned oscillators through a slowly moving filter, and short interface cues, each a brief enveloped tone with its own waveform and pitch sweep, for stepping the replay, a node landing, and a bench frame landing. The site also listens to what it plays: an analyser drives the waveform in the sound toggle and the live waveform on the `Jingle` node, read inside the one render loop. At the reduced tier and under reduced motion that waveform holds a still shape rather than disappearing.

### The effects catalogue

**Shadow.** Cards carry a lift made of two shadows at rest: an ordinary soft dark one, and an accent-coloured one turned fully transparent, so pointing at the card raises only the accent shadow's strength and tints the lift without anything moving. Chips and small panels carry a faint utility shadow. The comparison table's sticky first column is held by a solid shade offset to its left in the warm near-black, not by a border, at a different offset for each of three widths, so the rule never leaves a gap while the table scrolls. The modal carries the deepest shadow in the product, and a raised card on the dark ground carries a wide, soft one.

**Filter.** Besides the three settle stages, a still can be knocked out to a near-white plate with a faint warm cast by the browser itself, so the same still can appear in colour in one place and as a pale plate in another without a second file. The hero's accent glow is heavily blurred and the large ambient blooms on the dark ground are blurred further still. Where a shadow must follow a clipped, non-rectangular silhouette, two stacked drop shadows are used, a tight one for contact and a wide one for elevation, and they are never flattened into one.

**Blend.** One blend mode is used in the whole product, the one that darkens dark areas and lightens light ones, and only on the grain layers, always inside an isolated layer, including over the three-dimensional canvas.

**Backdrop blur.** Floating panels and cards over the canvas blur what passes behind them, and the modal blurs more strongly. Both are used only where the browser supports it, and at the reduced tier both become an opaque ground, never transparency.

**Backgrounds.** The dot grid exists twice and both are kept: on the light ground as a small repeating tile carrying a rounded dot, and on the dark ground as a faint round dot at very low strength, because the tile carries a rounded dot the other cannot and the other carries a transparency the tile does not. Edge fades run on all four sides: the top and bottom fades run from the lighter near-black to nothing in the ordinary colour space, and the left and right fades run at half strength in a perceptual colour space because they sit over moving content and must not band. A travelling border sweep, a narrow band of accent passing diagonally along an element's thin frame, is the only animated border in the product.

**Masks and compositing.** Masking and compositing shape several surfaces. A soft pointer-following spotlight with a four-stop falloff follows a fine pointer across some sections: its radius grows from nothing when the pointer enters and its edge falls away through four stages, fully visible at the centre, then about two thirds, then about a fifth, then gone; with fewer stages it becomes an obvious hard circle. Where there is no fine pointer it rests at the section centre. The wordmark serves as a mask that reveals type and media through the ribbon. A scrolling list fades out at its top and bottom tenth; an overflowing row fades at its left and right edges; a still fades out at its foot. The border sweep is masked to a thin frame. The pricing card's concave notch is a mask cut into the card. Sections meet along curved dividers, with one curve shape for narrow screens and another for wide ones.

**Clips.** Visually hidden form inputs use the accessible-hidden pattern. The segmented controls (the billing toggle and the allowance stepper) slide their accent fill by moving a clipped window that keeps the control's corner as it moves, never by sliding a filled block. Each blog card's media carries its own silhouette, so no two cards in the grid share a shape. The enterprise section ground and the about route's banded ground are each cut to their own curved shape.

**Transforms.** Only containers that genuinely move continuously are promoted to their own layer; a promoted layer that never moves wastes memory. The card corridor declares one shared perspective on its container, so every card shares one vanishing point. Grouped vector content waiting to be revealed sits collapsed to nothing and is hidden from assistive technology until it arrives.

### Zero-asset construction

The zero-asset construction rule applies to every surface: nothing is loaded from a picture, video, sound, font or model file committed with the source. Each asset class has a drawn or generated substitution. The film grain is browser-generated noise with its colour removed, composited as described above. The medallion model is composed from simple forms when needed, as described above. The environment map is generated from gradients. The flat medallion used beside credit figures is drawn from the coin geometry with a diagonal gradient from the warm near-white to the warm light grey, one small highlight and a faint inner shadow. The logo mask is the ribbon drawn inline. Every curved clip shape is drawn inline relative to the element it cuts. Sound is synthesised. Stills are seeded gradient fields keyed by the item they belong to, in the product palette or the model's gradient, at the declared aspect, so the same item always gets the same picture; timed output is the same field animating with a slow hue rotation, held to its loop. Typefaces are open-licensed families installed from the public package registry at build time and served by the app, each with a metric-matched fallback; no font file is committed. Skeletons in the bench and generation placeholders use the grain inside a thin hairline, with no spinner file and no placeholder picture.

### Glossary

Terms used in this brief, each in one sentence. **Rank**: a node's depth in its graph, where everything on one rank can be produced together because nothing on that rank depends on anything else on it. **Stale**: marked as no longer valid because something it depends on changed, and waiting to be regenerated. **Generation token**: a number raised on every new request for a node's output, so a late result from an older request can be recognised and discarded. **Idempotent**: safe to repeat, because a repeated request carrying the same key has the same single effect. **Opaque cursor**: a page marker whose contents the client does not interpret. **Rate table**: the single versioned source of what each generation costs in credits. **Correlation identifier**: a value returned with every error that lets a support conversation find the exact request. **Smoothed scroll**: scrolling in which the page is moved under a position that eases toward where the visitor scrolled. **Scroll-linked**: following scroll position continuously and reversing when scrolling reverses. **Threshold reveal**: fired once when an element becomes visible enough, then let go. **Reveal pose**: how much smaller and how far below its resting place an element waits before it arrives. **Degradation tier**: a named drawing mode for weaker devices in which what the product does never changes, only how it is drawn. **Perceptual colour space**: a colour space in which equal numeric steps look like equal steps, which keeps a slow fade even.

## Constraints

Single product, one origin. Studios are the only tenancy boundary, and every read of a studio's rows is scoped to the caller's own studio.

Every vendor, model, person, investor and studio named here is invented; no real company, product or person is named anywhere in the build, and third-party marks are drawn as abstract placeholder forms.

Not built:

- real generation engines (every output is generated inside the app);
- card collection or any payment processor;
- plan renewal, proration, refunds or dunning;
- email sending of any kind (leads are stored);
- the documentation site and the agent connector (external links only);
- the desktop installers;
- live co-presence or live cursors on a canvas (another member's change appears on the next load);
- chat-tool creation, brand kits and custom agent skills (described on the enterprise and pricing routes only);
- an administrative interface for plans, rates or the manifest.

No outbound network call at run time. No payments, email, cache, queue, search or realtime service is available; the only backing services are PostgreSQL and MinIO. No binary asset is committed with the source: no photograph, rendering, texture, video, audio clip, three-dimensional model or icon file. Every still, clip, sound, preview image and mark is generated or drawn by the app.

## Deployment contract

- The app must be reachable at `APP_PUBLIC_URL`. The port mapping is `${APP_PUBLIC_PORT}:4173` - `4173` is the container-internal port and `APP_PUBLIC_PORT` is what the outside world uses. Read both from the environment; never hardcode either.
- The HTTP API is served on that same origin under the `/api` prefix.
- `GET /api/health` returns `200` once the app is ready.
- The app starts from the environment image with no manual steps.
- Login credentials - or an explicit statement that there are none - are written to `/app/USER_README.md`.
- Reserved `.browser_screenshots/` and `.downloads/` directories exist at the app root, empty.
- Serve a production build behind a static or preview server - never a dev server.
- The server must keep running after this session ends and must not be a child of the shell. An ordinary background job dies with its shell, and the app will not be running when it is next opened.
- Bind `0.0.0.0`, never `127.0.0.1` or `localhost`. A loopback-only listener is unreachable from outside the container.
- The backing services named in this brief are already running and reachable at their environment variables. Do not download, install, compile or start a copy of any of them.
- Use only the providers named in this brief. No edge functions.
- No persistent volumes, no fixed container names, no custom networks.

Field names are exact. A list endpoint returns a top-level JSON array. A successful call returns the named resource or shape; an invalid or unauthorized call is rejected as a client error, never as a server error and never as a silent success. Bearer auth is required on everything except login, sign-up, health, the public reads (`GET` on `plans`, `rates`, `models`, `replay/graphs`, `forecasts/{id}`, `posts`, `posts/{slug}`, `desktop/releases` and `bench/win-rates`) and the anonymous writes `replay/regenerate`, `forecasts`, `forecasts/{id}/recompute` and `leads`. `replay/sessions/claim` needs a creator, and reading a bench run needs a creator of the studio that started it.

### No mocks

The named provider is the fact. Any of the following is a contract violation: an in-memory array standing in for the canvases or the credit ledger; generated bytes written to the app container's filesystem; a database column holding an output instead of an object key; an output route that answers without checking the caller against the studio and the deliveries on that request; a public or time-limited link to an object in the bucket; a balance kept in a column and adjusted in place rather than derived from the ledger; a plan list or a rate table written into the page instead of read from the store; a bench that reveals all frames together after the slowest finishes; or a run endpoint that reports success without an object existing in the bucket. The app's UI and its own tables can only reflect what lives in the provider, never substitute for it.

## Definition of done

A visitor can play a graph on the home page, sign up, open that graph as their first canvas, generate an output that lands in the object store, and subscribe to a plan. A generated output is readable by its own studio and by a client only while it is delivered to them, and by nobody else.
