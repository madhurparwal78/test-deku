# Sendline

Build and deploy a working web application from this brief. There is no starting codebase. When
you are done, a stranger must be able to open the app in a browser, sign up, add a sending
domain, mint a credential, hand a message to the sending interface with that credential, and
watch that message appear in the delivery log and settle into `delivered`, without hitting an
error page. The delivered message must exist as a real row in `messages` with a real row in
`message_events` for each state it passed through, and a message addressed to an ordinary
recipient must arrive as real mail in the `mailpit` inbox over SMTP: a state word the app draws
for itself is not a delivery.

## Overview

Sendline is an email sending platform for developers and the small teams around them. A team
points a domain at the platform, proves it controls that domain, mints a scoped credential, and
then hands the platform messages to deliver. The platform delivers them, records what happened
to each one, and tells the team's own server about it as it happens.

Two products sit on one delivery engine. Transactional sending is one message to one person,
generated by an event in the customer's own application and handed over through the sending
interface. Marketing sending is one broadcast to a stored audience, composed by a person in the
console. Everything else exists to serve those two verbs: domains and their authentication
records make delivery possible, credentials make it authorised, the log and its charts make it
observable, event notifications make it programmable, contacts and audiences make the marketing
side addressable, and metering makes it billable.

The people who use it are a workspace: an owner who can spend money, an admin who can do
everything operational, and a member who can write and prepare things but cannot change the
plumbing that makes sending work. Machine clients hold a credential and can send; a credential
can never mint another credential.

It is deliberately **not** a mailbox you read, not a customer relationship manager, not a
landing page builder, and not a workflow engine. There is no visual broadcast editor, no
template library, no automation builder, no inbound routing, no dedicated sending address, no
open tracking and no click tracking.

The genuinely hard part is that the overview's four counters and its delivery chart must
reconcile exactly with the message rows underneath them for the same window, while messages keep
arriving and their events keep landing out of order.

## User roles

Three roles, flat, assigned per workspace membership. There is no role hierarchy, no custom role
builder and no per-resource grant. The matrix below is the whole permission model: rows are what
a person can do, columns are the three roles, and anything not granted is refused by the server.

| Role | Can do | Cannot do |
|---|---|---|
| `owner` | everything an admin can, plus change the plan, remove a member, and read the usage detail and the invoice history | **nothing is withheld from the owner** |
| `admin` | read everything in the workspace; add, verify and delete a sending domain; mint and revoke a credential; create and delete a notification endpoint and replay a delivery; create an audience, import contacts and export contacts; compose a broadcast and send it to a live audience; invite a member and change a member's role | **change the plan, remove a member, read the invoice history** |
| `member` | read the message log, open a message and its rendered body, send a test message from the console, view credential metadata and its scope and its last used time, create an audience and import contacts, compose a broadcast and request that it be sent | **add or delete a domain, mint or revoke a credential, create a notification endpoint, export contacts, send a broadcast to a live audience, invite a member, change a member's role, read billing detail, read the stored text of any credential** |

A credential secret is never revealed after creation, to anybody, including the owner. The
secret is shown exactly once, in the response to the call that creates it, and what is kept is a
one-way transformation of it plus a short non-secret prefix for display. A control anywhere in
the console that shows a stored secret again is a defect.

A member may compose a broadcast but may not send it to a live audience. Composition is
reversible; sending is an irreversible mail-out to real people that spends paid allowance. The
console offers a member a request-send action which moves the broadcast to `requested` and
leaves the send itself to an owner or an admin.

Authorization is enforced **server-side on every mutating endpoint**. Hiding a button in the UI
is not authorization: a direct API call from a `member` session to any `admin`-only endpoint
must be rejected by the server (an unauthorized request is denied, not served), leaving the
protected state unchanged.

Signup is open: anyone may create an account at `/signup`, and a new account lands in a new
workspace of its own as that workspace's `owner`. The following accounts are seeded for the
`Northwind Relay` workspace, all with the password `deku-demo-pw-2026`:

| Email | Role |
|---|---|
| `owner@example.com` | `owner` |
| `admin@example.com` | `admin` |
| `member@example.com` | `member` |

One further account, `owner2@example.com`, is seeded as the `owner` of a second workspace named
`Acme Relay`. It exists so that the workspace boundary has two real sides.

## Core features

### Auth

Accounts are email and password, implemented by the app. `POST /api/auth/signup` takes an
email, a password and a display name. `POST /api/auth/login` takes `{"email", "password"}` and
returns `{"access_token": "..."}`. Every console route carries that token as a bearer token.
Passwords are stored hashed, never in readable form. `GET /api/auth/me` returns the signed-in
person, their active workspace and their role in it.

1. A signup with an address already registered is rejected as invalid and no second `users` row
   is written.
2. A login with a wrong password is denied, and the response body carries no hint about which
   half of the pair was wrong.
3. A console request carrying no bearer token is denied.

### Sending domains

`/console/domains` lists one row per domain: the name, a state chip, the last check time, and a
count of messages sent from it. Domains not in `verified` sort first. `/console/domains/new`
takes a single name field and explains what happens next before the person commits.

On submit the app generates the record set the customer must publish in their own name service
configuration, and lands them on `/console/domains/<id>`. The record table is the most important
table in the console. Each row carries the record type, the exact host name to create with a
copy control, the exact value with a copy control and never visually truncated without a way to
see all of it, and **a status for that record alone**: `pending`, `correct`, `mismatch` or
`missing`. Where a record is found but wrong, the observed value is shown beside the expected
one. A single aggregate "not verified" is the difference between a customer fixing a typo in two
minutes and opening a support conversation.

Three accommodations sit beside the table, each removing a category of support load: a copy
control that copies the host in both the bare and the fully qualified form, because providers
disagree about which they accept and pasting the wrong one is the most common failure; a note
that some providers append the domain automatically, which turns the fully qualified form into a
doubled name; and a control that copies the whole record set at once for customers whose
configuration lives in version control rather than in a web form.

4. `POST /api/domains` with a name creates the domain in `pending` and returns its generated
   record set, one `TXT` record for the sending signature under the selector `sendline`, one
   `MX` record for the return path, and one `CNAME` record for the tracking host.
5. `POST /api/domains/<id>/verify` runs a verification pass, updates every `domain_records` row
   to its own status, and moves the domain to `verified` only when every record reads `correct`.
   A domain with one record `missing` stays `pending` and names the failing record.
6. Where the records are correct but not yet visible from every resolver, the panel says the
   domain is still propagating rather than saying it failed.
7. Deleting a domain requires typing its name, states before the confirmation that sending from
   it stops at once and that messages already accepted still go out, and leaves the sending
   history in place.
8. A domain that belongs to another workspace is not found, never forbidden. Telling the two
   apart would confirm the resource is real.

The `Northwind Relay` workspace is seeded with `mail.northwind.example.com` in `verified`, and with
`docs.northwind.example.com` in `pending` carrying one record at `correct` and one at `missing`.

### API credentials

`/console/credentials` is small, and it is the place where a mistake is most expensive. Each row
carries the customer's own label, the stored prefix, the scope, the domain pin where one is set,
who created it and when, the last used time with `never` as an explicit value, and a revoke
control. The prefix column exists for exactly one reason: it is how a customer matches a secret
found in a configuration file to a row on this screen. Without it, revoking the right credential
is guesswork and somebody eventually revokes a production one.

9. `POST /api/credentials` takes a name, a scope of either `sending` or `full`, and an optional
   domain pin. It returns the full secret **once**, in that response and nowhere else, alongside
   the stored prefix. The secret begins `skey_` and the stored prefix is its first twelve
   characters.
10. `GET /api/credentials` returns credential metadata and never a secret or a hash of one.
11. `DELETE /api/credentials/<id>` revokes the credential at once. A revoked credential
    presented to the sending interface is denied.
12. A `member` calling `POST /api/credentials` is denied and no `credentials` row is written.
13. A credential presented to `POST /api/credentials` is denied whatever its scope: a machine
    client can never mint another machine client.

### The sending interface

This is the product. The console is a client of it. It is served on the same origin under
`/api/v1`, it authenticates with a credential presented as `Authorization: Bearer <secret>`, and
its request and response field names are lower snake case throughout.

`POST /api/v1/emails` takes a body of this shape:

```
{
  "from": "Support <support@mail.northwind.example.com>",
  "to": ["one@example.com"],
  "reply_to": ["help@mail.northwind.example.com"],
  "subject": "Your receipt",
  "html": "<p>Thanks.</p>",
  "text": "Thanks.",
  "tags": [{"name": "category", "value": "receipt"}]
}
```

14. `from` is required and its address part must belong to a domain in `verified` state in the
    calling workspace. A send from an unverified domain is refused and no `messages` row is
    written.
15. `to` is required and carries between one and fifty addresses. `subject` is required.
    At least one of `html` and `text` is required.
16. An `Idempotency-Key` header is **required** on `POST /api/v1/emails`. A request without one
    is refused as invalid and nothing is queued. A network timeout on a send is
    indistinguishable from a success, and a client that retries without a key sends a customer's
    password reset twice.
17. A replay of the same `Idempotency-Key` with the same body returns the stored response
    without queueing a second message, and the workspace ends with exactly one `messages` row
    for that key. Two simultaneous requests carrying one key and one body admit exactly one
    message; the second receives the stored response and creates no second row.
18. A replay of the same `Idempotency-Key` with a different body is refused as a conflict,
    because one key naming two different messages is a client fault that has to be loud.
19. The successful response is an acceptance, not a delivery. It carries the created identifier
    and the instant it was created, and it means the platform has taken durable responsibility
    for the message. Everything after that is reported in the log and through the event
    notifications.
20. `GET /api/v1/emails/<id>` returns one message and its current state. `POST
    /api/v1/emails/<id>/cancel` withdraws a message that has not yet left and moves it to
    `canceled`; a message already in `delivered` cannot be canceled and the call is refused.
21. A credential pinned to a domain that attempts to send from any other domain is refused, and
    the refusal reads exactly as the refusal an unauthorised sender receives, so the pin cannot
    be used to enumerate which domains a workspace owns.
22. A `sending` credential may call the message operations only. A `sending` credential calling
    `GET /api/v1/domains` is denied.

Three reserved recipient addresses force a delivery outcome without real mail leaving the
building. `delivered@relay.example.com` is accepted and then produces a `delivered` event.
`bounced@relay.example.com` produces a hard bounce carrying a diagnostic. `complained@relay.example.com` is
delivered and then produces a complaint event. They are excluded from metering and they produce
real event notifications, so a developer can exercise their own handler end to end.

A message addressed to any other recipient is handed to the real mail server at `SMTP_HOST` and
`SMTP_PORT`, addressed to the recipients in `to` and to nobody else, with the subject exactly as
the request supplied it and a body carrying the supplied text. A message refused before queueing
sends no mail at all.

23. A hard bounce writes a `suppressions` row for that address, and a later send to a suppressed
    address is refused before queueing with a reason naming the suppression.

### The emails log

`/console/emails` is the screen customers spend the most time in. Columns: the state glyph and
the state word, the first recipient, the subject truncated with the full value available, the
sending address with its domain emphasised, and the time, relative under a day and absolute
beyond. The whole row is one link rather than a nest of separate links.

24. Filtering is server-side and every filter lives in the query string, so a filtered view is a
    link a colleague can open. `GET /api/emails` accepts `state`, `domain_id`, `to` and
    `credential_id`, combining them with AND across types. Filtering only the rows already
    loaded in the browser produces a log that lies as soon as there is more than one page.
25. The list never claims a total count. Where a count is genuinely needed it comes from the
    overview counters, labelled with the window they cover.
26. `/console/emails/<id>` shows the subject, the state chip, the identifier with a copy
    control, the envelope, the ordered timeline and the rendered body. `GET /api/emails/<id>`
    returns the message with its `events` in occurrence order.
27. The timeline orders events by the instant they occurred rather than the instant they were
    recorded, shows both, and marks any event that arrived late. An event whose rank sits below
    the message's current state is recorded without moving the state backwards: a message that
    travels backwards from `delivered` to `sending` makes the whole screen untrustworthy.
28. A bounce row shows the receiving server's exact diagnostic text and a plain-language reading
    of it beneath. Receiving servers answer with terse codes that mean something specific and
    non-obvious, and a customer shown only the raw string guesses wrong.
29. The rendered body is shown inside a sandboxed frame with scripts, forms, popups and
    same-origin access all denied, and remote content is blocked until the reader asks for it. A
    message body is markup written by a third party and is treated as hostile.
30. A message identifier belonging to another workspace renders as not found.

### The overview

`/console/overview` is the first screen after signing in and its whole job is to answer "is my
mail working" in about two seconds. It carries four counters, then a stacked delivery chart,
then two panels side by side for recent activity and domain health.

31. `GET /api/overview` accepts a `window` of `24h` or `7d`, defaulting to `24h`, and returns
    `sent`, `delivered`, `bounced` and `complained` for that window plus one `buckets` entry
    per bucket, hourly for `24h` and daily for `7d`. **Every figure it returns equals the count
    of `messages` rows in that window and that state, and the bucket counts sum to the counters
    exactly.** An aggregate that disagrees with the rows beneath it is the defect this screen
    exists to avoid.
32. Each counter is a link into the log pre-filtered to that state and that window. A number on
    a dashboard that cannot be opened into its constituent rows is a number nobody can act on.
33. A rate is shown as a rate **and** as its two components. `0.4%` alone is meaningless when
    the denominator is seven messages, so the card reads `2 of 500`.
34. The bucket covering the current hour is drawn differently and labelled partial. Without
    that, every customer reads their most recent hour as a collapse in volume.
35. The chart states the instant it was computed, and an empty window draws a flat baseline with
    a one-line explanation rather than a blank frame.
36. Pointing at a column shows exact counts per state, and the same column is reachable by
    keyboard. A data table carrying the same figures sits beneath the chart, hidden until it is
    expanded.
37. The domain health panel carries one row per sending domain with its name, its verification
    state and its last check time, and a domain in `failed` or `pending` sorts to the top
    whatever the alphabet says.

### Audiences, contacts and broadcasts

38. `POST /api/audiences` creates an audience. `POST /api/audiences/<id>/contacts` creates or
    updates a contact by address. One address appears at most once in one audience, and a second
    create for the same address updates the existing contact rather than adding a row. The full
    contact list is browsable, searchable by address and exportable by an owner or an admin, and
    an import that loses its connection part way resumes from the last row it committed rather
    than starting again or duplicating what it already wrote.
39. `POST /api/broadcasts` creates a broadcast in `draft` against an audience, with a subject
    and a body. `POST /api/broadcasts/<id>/send` sends it to every subscribed contact, writes
    one `messages` row per recipient, and moves the broadcast to `sent`.
40. A `member` calling `POST /api/broadcasts/<id>/send` is denied, the broadcast stays out of
    `sent`, and no `messages` row is written for it. The console offers that member a
    request-send control which moves the broadcast to `requested` instead.
41. Deleting an audience while a broadcast still references it is refused, and the refusal names
    the broadcasts that must be deleted or reassigned first.

The `Northwind Relay` workspace is seeded with an audience named `Launch List` carrying three
subscribed contacts.

### Event notifications

42. `POST /api/notifications` creates an endpoint with a URL and a list of subscribed event
    types, and returns its signing secret **once**, under the same rule that governs a
    credential secret.
43. When a message reaches a subscribed state the app posts the event to every active endpoint
    subscribed to it and writes one `notification_deliveries` row per attempt, carrying the
    attempt number, the status code and the outcome. One row per attempt, not one per event.
44. `POST /api/notifications/<id>/test` sends a synthetic event of a chosen type, marked as a
    test in its payload, and returns the status code, the duration and the response body up to
    a bounded length, so the customer can see what their own server said back.
45. `POST /api/notifications/<id>/deliveries/<delivery_id>/replay` re-posts the same event with
    a new delivery identifier and the same event identifier, so a correctly written receiver
    deduplicates it. Replay is what makes a customer's outage survivable: without it, a receiver
    that was down for an hour has permanently lost that hour.
46. An endpoint whose deliveries keep failing moves to `disabled`, and the endpoint detail names
    the reason, the consecutive failure count and the last successful delivery.

### Usage

47. `GET /api/usage` returns the current period, the count of metered messages in it and the
    workspace allowance. The `starter` plan carries a monthly allowance of `500` messages.
48. A send that would take the workspace past its allowance is refused before queueing, with a
    reason naming the allowance, and no `messages` row is written. Messages to the three
    reserved test addresses are never metered.
49. A workspace at or above nine tenths of its allowance carries a banner on every console route
    naming how much is left.

### The console shell

Everything that surrounds every signed-in route. A left rail carries the workspace switcher,
then the destinations, then the settings entry at its foot; it is collapsible to an icon strip
and that collapsed choice is remembered for that person. A short sticky top bar carries the
breadcrumb, an environment marker where one applies, a search control, the notification bell and
the account menu. The main region scrolls independently of the rail, and transient confirmations
appear at the bottom right.

50. The workspace switcher lists every workspace the signed-in person belongs to with their role
    in each. Switching writes the active workspace into the session and lands on the overview
    rather than on the equivalent route, because the equivalent resource does not exist in the
    new workspace. A switch made in one tab is noticed by the others, which prompt rather than
    silently redrawing underneath somebody.
51. The search control finds messages by recipient, subject or identifier, then domains, then
    audiences, then contacts by address, then broadcasts, then console destinations, grouped by
    type with the type named, and every result is scoped to the active workspace. Pasting a
    whole message identifier is an exact lookup that jumps straight to that message.
52. At most one banner shows at a time, the most serious one, in this order: the workspace is
    suspended, the sending domain is failing, a notification endpoint is disabled, a departed
    member's credentials are unreviewed, the allowance is nearly spent, and the onboarding
    checklist. Showing four at once teaches people to dismiss all four without reading, which is
    how the serious one gets missed.
53. A new workspace carries an onboarding checklist naming the steps that have not happened yet:
    add a domain, verify it, mint a credential, send a first message. Each item links to the
    route that completes it, each ticks itself off when the underlying fact becomes true, and
    the whole checklist disappears once it is complete.
54. The account menu carries the person's name and address, a link to their profile, the theme
    control and a sign-out control. Signing out ends the session on the server, not only in the
    browser, and a token belonging to an ended session is denied.
55. `/console/profile` lets a person change their own display name and their own password, and
    `/console/security` lists their active sessions with the last-seen time of each and lets any
    one of them be ended. Changing a password ends every other session for that person.
56. Removing a member ends that person's sessions for the workspace at once and their next
    request is denied, while everything they created stays with the workspace. Their credentials
    are **not** revoked automatically, because revoking them would stop a customer's production
    sending at the exact moment somebody is walking out of the door. Instead the workspace
    carries a security checklist listing every credential that person created, each with a
    revoke control beside it, and a banner until the list is cleared.

### Credential rotation and endpoint recovery

57. The console offers a rotation flow that needs no downtime: mint the replacement, deploy it,
    watch the old credential's last-used time stop advancing, then revoke the old one. The flow
    refuses to complete its final step while the old credential is still being used, and shows
    when it was last seen instead. Rotation without that check is why people never rotate.
58. An endpoint moved to `degraded` or `disabled` shows the reason, the consecutive failure
    count and the last successful delivery, and its re-enable control sends a test first and
    refuses to re-enable when that test fails.
59. An endpoint's signing secret rotates by adding a second active secret. Both are sent for an
    overlap window that the customer ends explicitly, and the panel states that both are being
    sent and that the receiver should accept either, which is what makes rotation possible
    without a coordinated deploy.

### Consent and unsubscribes

60. Every broadcast carries a one-click unsubscribe control and an unsubscribe header, and the
    address that uses it is marked unsubscribed in that audience within seconds and receives no
    further broadcast. An unsubscribe is never silently ignored and is never made conditional on
    signing in.
61. Creating an audience records a declaration of where its addresses came from, and a contact
    import that does not carry one is refused. Marketing mail sent to addresses nobody agreed to
    is what destroys a sending reputation, and the declaration is the moment the customer takes
    that responsibility.
62. A transactional message is never suppressed by an unsubscribe: unsubscribing from a
    broadcast list has no effect on a password reset, and the two suppression reasons are
    recorded separately.

### The public surface

63. `/terms` is a public route carrying the terms of use. It is linked from the footer of every
    page and from the signup form, and a visitor who has never signed in can read it.
64. Every form refuses invalid input inline, names the field that is wrong, keeps the rest of
    what was typed, and writes nothing. Submitting the signup form with an address that is not
    an address leaves no `users` row behind.
65. An unknown address renders the product's own not-found page, which carries the product name,
    a way back to the console and a way back to the sign-in route, and answers as not found
    rather than as success.
66. Every internal link on every reachable route resolves. A link in the rail, the footer or a
    table row that leads nowhere is a defect.

**Entry and redirects.** `/` sends a signed-in person to `/console/overview` and everybody else
to `/login`. An unauthenticated request to any console path returns to `/login` carrying the
path that was asked for, and lands on it once the person signs in. A signed-in person who opens
`/login` is sent to `/console/overview`; a sign-in form is never shown to somebody already
signed in. Signing out returns to `/login`. A token that expires mid-action surfaces a sign-in
prompt in place, keeping what was typed. A person whose role does not stretch to a route sees
the route's read-only content with its write controls disabled and a line naming the reason.
A console route naming a resource the active workspace does not own renders as not found.

**Journeys.**

1. Open `/signup`, enter an address, a password and a display name, and land on
   `/console/overview` in a new workspace with every counter at zero and the domain empty state
   in front of you.
2. Sign in as `admin@example.com`, open `/console/domains/new`, enter `docs.northwind.example.com`,
   and land on the domain detail route reading a record table with one row per record and a
   status on each row.
3. On that route press the verification control and watch the record that was `missing` change
   its own status while the other stays `correct`, with the domain still reading `pending`.
4. Open `/console/credentials`, mint a credential named `Production sender` with the `sending`
   scope, copy the secret from the one panel that shows it, dismiss that panel, and see the new
   row carrying its prefix and `never` as its last used time.
5. Hand a message to `POST /api/v1/emails` with that credential, from `support@mail.northwind.example.com`
   to `delivered@relay.example.com`, with an `Idempotency-Key` header, and watch it appear at the top of
   `/console/emails` and settle into `delivered`.
6. Open `/console/emails`, filter to `bounced`, open the seeded bounced message, and read the
   timeline with its diagnostic and the plain-language reading beneath it.
7. Sign in as `member@example.com`, open `/console/broadcasts/new`, compose a broadcast against
   `Launch List`, and find a request-send control in place of a send control.
8. Sign in as `owner@example.com`, open `/console/usage`, and read the metered count for the
   current period against the allowance of `500`.

**States.** Every list has an empty state naming what is missing and offering the action that
fixes it: no domains, no credentials, no messages, no audiences, no endpoints. Every route shows
a skeleton while its data is in flight, and never an indefinite spinner. A refused request
renders its reason in place and leaves the rest of the screen usable. A filter that matches
nothing states the filter, offers to clear it and keeps it in place. Nothing in the app renders
an error page in place of a screen.

## UI/UX notes

The north star is comprehension: somebody opening this should understand within a moment whether
their mail is working. The register is operational, so the interface reads quiet and dense but
organised, built for scanning and for repeated action, with no oversized hero and no editorial
composition. The character is taken from the product this brief describes, and every sentence
below is a requirement rather than a preference.

**Ground and surfaces.** The product commits to dark and designs it fully. The page ground is a
true near-black neutral, edge to edge, so that panels merge into the edge of the display rather
than sitting on a lighter card. Surfaces that rise off the ground are a cool neutral at low
opacity laid over the ground rather than a flat mid neutral, which is what makes a panel read as
lit instead of painted. Substituting a plain grey at the same strength makes the whole page go
dull, and that is the failure to design against. Primary text is a near-white neutral at the top
of the ramp and is never pure white; pure white is reserved for the primary action fill and for
the one display heading. Secondary text is a light neutral that still clears the contrast bar.
Borders are a deep neutral, present only where a boundary carries meaning: this product prefers
space over dividers.

**Meaning by colour, and never by colour alone.** A vivid green means delivered and operational.
A soft red means bounced and failed, and it appears nowhere that is not a failure. A soft orange
means complained and warning, and its text tone is an amber. A deep neutral means queued and
canceled. A vivid teal is the live signal and is worn only by the indicator that says the
platform is running and by the pulse on a message still in flight. A soft cyan carries
informational links inside prose and nothing else. An indigo carries the compose surface accent.
Every state chip carries its word as well as its colour, and the log carries a leading glyph per
state, because roughly one reader in twelve cannot separate the green from the red and none of
them should have to guess.

**Type.** Body and interface text is `Inter`. Identifiers, record values, host names and code
samples are set in a monospace face with tabular figures, and every column of counts aligns on
its figures. One display face carries the single largest heading on a route. The scale is
deliberately short: almost the whole interface sits at `16px` and `14px` at a regular weight,
with `12px` for the smallest labels, and then the one display heading jumps straight to the top
of the scale with nothing carrying real volume in between. Filling in a conventional heading
ramp between those two ends produces a busier product that is measurably not this one.

**Shape and density.** Comfortable overall, and tighter in the log: rows sit close enough that a
full screen of messages can be read without scrolling, while a domain record table breathes
because every value in it is going to be copied by hand. Corners soften in one direction only,
from the small chips through the cards to the large panels; the exact softness is yours so long
as that order holds.

**Components and their states.** Every control has a resting, pointed-at, pressed, focused and
unavailable state, and an unavailable control is never signalled by colour alone. The primary
action on a page is visually distinct from every secondary one, and each page leads with one.
Pointing at the primary action makes it appear to emit light rather than to cast a shadow, which
on a black ground is what separates this product from a page with a conventional drop shadow.
Escape closes the topmost layer only. A destructive action confirms first, and the confirmation
repeats the fact that matters: revoking a credential repeats when it was last used, so somebody
about to revoke a credential that was working four seconds ago finds out before rather than
after. The panel that shows a new secret cannot be dismissed by clicking outside it, which is
the one place in the product where that is correct, and its dismiss control is labelled with the
consequence rather than with the word close.

**Motion.** The character is eased and very quiet, and it is uniform: a transition is a
considered entrance and exit rather than a bounce, and nothing overshoots. The default response
to a pointer is a colour change rather than a movement. Entrances travel a few pixels and scale
by a couple of per cent, so things arrive rather than fly in; anything that travels further or
scales more will look wrong beside the rest. Three page-level entrances run once on load and
then everything settles and stays still. Loops are slow enough to be watched without being
noticed, and the only one that carries meaning is the busy indicator. Nothing in this product is
driven by scroll position: the feeling of care comes from restraint rather than from
choreography, and adding a scroll-driven reveal would be a departure. Under a reduced-motion
preference the entrances and the loops stop and the colour transitions stay, because a colour
fading is not movement and removing it leaves an interface that snaps and feels broken.

**Accessibility.** Contrast meets WCAG AA for body text against its ground in every state, touch
targets are comfortably sized, keyboard navigation reaches every control in visual order with a
visible focus ring, icon-only controls carry labels, and the delivery chart is reachable and
readable by keyboard with its figures available as text.

**Responsive.** The layout holds at every width between the named tiers. At a narrow viewport
the left rail collapses to icons, the log sheds its sending-address column first and its tag
column second, nothing overflows sideways, and every navigation target stays reachable. Every
content image carries alternative text, and an image that is there for decoration declares
itself decorative.

**Layout.** A persistent left rail carries the destinations, grouped into a sending half and a
marketing half with a hairline between them, because the two halves of this product usually have
two different readers inside one customer. A top bar carries the breadcrumb, the search control
and the account menu. The overview is a grid of charts and counters; the log is a table; a
domain, an endpoint and a broadcast each open into a detail route of their own rather than into
a dialog. Creating a domain, an endpoint or a broadcast opens its own route rather than a modal,
and each of those routes is reachable by its own address. A new row in the log appears at once
with a brief highlight and is corrected with a message if the write turns out to have failed.
Renaming a credential or toggling a domain setting shows its new value at once and reverts it
with a toast when the write comes back a failure.
At most one banner is shown at a time, the most serious one, because showing four teaches people
to dismiss all four without reading.

## Technical requirements

The backend is `Flask` on Python 3.12, serving JSON under the `/api` prefix on the same origin.
The frontend is `Svelte` built with `Vite` and served as a production build; the browser
receives an application shell on first paint and every screen's data arrives afterwards as JSON
from that same origin. The datastore is `postgres`, reached at `DATABASE_URL`. Mail is sent over
real SMTP to `mailpit` at `SMTP_HOST` and `SMTP_PORT`, with `SMTP_USER` and `SMTP_PASS` read
from the environment alongside them. The app reads `APP_PUBLIC_URL` and `APP_PUBLIC_PORT` from
the environment and hardcodes no host and no port. Authentication is email and password with
bearer tokens, implemented by the app.

Use only the libraries named here plus their direct dependencies. Do not introduce a second
database, cache, queue, object store, identity provider or mail vendor: the only backing
services available in this environment are `postgres` and `mailpit`, and reaching for anything
else is a contract violation. Both are already running and reachable at those environment
variables, and must not be downloaded, installed, compiled or started.

`GET /api/health` returns `200` once the app is ready and requires no token.

Every response carries the standard security headers. Every response carries an `X-Request-Id`
header whose value is echoed in the app's own log line for that request, a
`X-Content-Type-Options: nosniff` content-type policy and a `Strict-Transport-Security`
transport policy, and every response to an authenticated route also carries
`Cache-Control: private, no-store`. Nothing the browser downloads carries a credential, an API
key or an administrative token.

Transport is HTTPS only at a minimum of TLS 1.2, with strict transport security carrying a long
lifetime, and an unsafe request arriving over plain HTTP is refused rather than redirected,
because a redirect means the credential has already crossed the wire in the clear and telling
the caller to try again elsewhere does not un-leak it. The referrer policy is
`strict-origin-when-cross-origin`. Camera, microphone and geolocation permissions are all denied
by the permissions policy, since this product needs none of them. The session cookie carries
`HttpOnly`, `Secure` and `SameSite=Lax` and is scoped to the site root. The post-sign-in return
path must be a relative path on this origin: an absolute address there is refused rather than
followed, because following it turns the sign-in route into an open redirect. Backups are kept for 35 days, are encrypted, and their restoration is exercised
quarterly rather than assumed.

A password is at least 12 characters and is checked against a mix of letters, numbers and
symbols, and it is stored with a memory-hard transformation and a per-password salt rather than
a plain digest.

Every externally visible identifier is prefixed with a short type token, sortable so that a
paginated list can use it as its own cursor, and unguessable so that holding one identifier
reveals nothing about the existence of another. Sequential integers are refused as external
identifiers: they leak volume, they make enumeration trivial, and they turn one missing
authorisation check into a complete export rather than a single leaked row.

When the platform is shedding load, maintenance work is paused first and customer-facing
acceptance is the last thing to be given up.

Every list response under `/api/v1` is a cursor page: it accepts a `limit` between 1 and 100
defaulting to 20 and an opaque `after` cursor, and it returns `data`, `has_more` and
`next_cursor`. Offset paging is refused for these collections because they are append-heavy: a
customer paging through the log while messages arrive would see duplicates and gaps and would
never be told.

Error bodies have one shape everywhere, including for authentication and for refusals:
`{"error": {"type": "...", "message": "...", "request_id": "..."}}`, with an optional `field`.
An error message never contains a value the caller did not send, and a validation failure
reports every failing field rather than the first, because a client correcting one field at a
time across five round trips multiplies load for no gain.

Two writes racing for the same outcome must leave the workspace consistent. Two simultaneous
sends carrying one `Idempotency-Key` and one body admit **exactly one** message: the loser
receives the stored acceptance and creates no second row, and the workspace never ends with two
`messages` rows for one key. Two simultaneous contact creates for one address in one audience
admit exactly one contact row. A broadcast sent twice in quick succession produces one set of
messages, not two.

An idempotency key is chosen by the client, is between 1 and 255 bytes, and is expected to be
either a random value or a stable natural key such as an order identifier. A key is scoped to
the workspace, the credential, the method and the path together, and it is retained for
24 hours. The acceptance record and the queued message become durable together, so there is no
window in which a retry duplicates a message and no window in which a failure suppresses a
message that was never sent.

**Rate limits, quotas and abuse.** Every response carries the state of the caller's budget as
`RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset`, and a refusal for being over
budget additionally carries `Retry-After` in seconds. The send budget is 100 requests per minute
per workspace and the console budget is 600 requests per minute per session. A caller over
budget is refused rather than queued, and refusing costs less than the work it prevents. At the
monthly allowance boundary the behaviour is the same shape: the send is refused before anything
is written, and the reason names the allowance rather than a generic failure. A signup from an
address that has already been used is refused, and six failed sign-ins for one address within
15 minutes lock further attempts on that address for 15 minutes.

**Versioning and deprecation.** The sending interface carries its version in the path as `/v1`.
A new optional request field or a new response field ships without a version change, and clients
ignore fields they do not recognise; a change that breaks an existing caller gets a new path
version, and a retired version keeps answering for twelve months after its replacement ships. A
call to a deprecated version answers with a `Deprecation` date header and a `Sunset` date
header, and the credential list records, per credential, which interface version it last called,
so a customer can find the one service of theirs that has not been upgraded.

**Validation.** Every request is validated at the boundary, before any business logic and before
anything is written, so no handler ever sees an unvalidated field. An unknown field on a write
is refused rather than ignored, because a mistyped field name that is ignored is a silent
data-loss fault and a refused one is an obvious error. The same rules drive the inline form
checks in the console, so a rule cannot say one thing in the browser and another on the server.
Addresses are normalised and compared case-insensitively on their domain part; a display name in
a `from` value is encoded rather than passed through raw; and a subject is between 1 and 998
bytes after encoding. Tags are optional, up to 10 name and value pairs, each restricted to
letters, digits, underscore and hyphen, and each at most 256 bytes.

**Delivery, retry and dead letters.** A message the receiving server defers is retried on a
widening schedule, and its timeline shows the attempt number and the next attempt instant. A
message that exhausts its attempts becomes a terminal failure carrying the last diagnostic, and
it is never silently dropped. A notification delivery behaves the same way: attempts widen, and
an endpoint whose attempts are exhausted has those events held as dead letters that the replay
control can send again. Under load the platform sheds new work by refusing it with a clear
reason rather than by accepting work it cannot finish, because an accepted message that never
moves is worse than a refused one. Exactly-once delivery to a third party does not exist and is
not claimed: what is guaranteed is that a duplicate is detectable, which is why every event
carries a stable event identifier that survives a replay.

**Observability.** Every log line is structured, one JSON object per line, and carries at least
`request_id`, `workspace_id`, `route`, `status` and `duration_ms`. The `request_id` is the value
returned in `X-Request-Id`, so a line in the log and an answer given to a caller can be joined.
A request that crosses into background work carries the same identifier onto it, so one trace
covers the whole path from acceptance to delivery. The app exposes its own counts of accepted,
delivered, bounced and complained messages alongside the request counts, which is what makes a
service level objective measurable rather than aspirational, and a sustained bounce rate above
5 per cent or complaint rate above 0.1 per cent raises an alert on the workspace rather than
waiting for a customer to notice.

**Caching and retention.** Public routes are cacheable and carry no per-visitor variation; every
authenticated response is `private, no-store` and is never held in a shared cache. Read models
that are expensive to compute, such as the hourly delivery rollup, are recomputed on a schedule
and every figure drawn from one states the instant it was computed, so a stale figure is visible
as stale rather than presented as current. A domain verification result is cached briefly and a
forced verification pass bypasses that cache. Message bodies are retained for 30 days and are
then erased, leaving the message row and its events in place; after erasure the body panel
states that the content has been erased and when, which is not an error.

**Performance.** A console route becomes interactive within 2 seconds on a warm cache and the
message log stays smooth at fifty thousand rows in one workspace, which means the list asks the
server for a page at a time rather than for everything. Admission latency, the time the sending
interface takes to answer with an acceptance, sits under 300 milliseconds at the
ninety-fifth percentile, measured over a rolling 30 days.

**Module boundaries.** The server is organised so that one module owns one subject: accounts and
membership, domains and verification, credentials, sending and the message state, the log and
its reads, audiences and broadcasts, notifications, metering. A module reaches another module
through its stated operations rather than through its tables, so a change to one table touches
one module. Every mutation is a named operation with one place that validates it, one place that
writes it and one place that records what happened, and a mutation never half-completes: either
every part of it lands or none of it does. One schema definition serves two consumers, the
server boundary and the browser form, so the two cannot disagree about what a valid value is.

**Pagination.** Cursor pagination is the rule for every collection that grows, and the cursor is
opaque so that its contents never become a contract. Offset paging is not offered anywhere. The
same ordering that produces a cursor also produces the list, so a page boundary is stable.

**Ordering and duplicate guarantees, stated honestly.** Event ordering across a network is not
guaranteed and the product does not pretend otherwise. Each event carries an event identifier
and the instant it occurred, the receiver is told to order by that instant rather than by
arrival, and a duplicate is expected and is made detectable rather than made impossible. Within
one endpoint the platform caps how many deliveries it has in flight at once, so one slow
customer endpoint cannot consume the whole delivery capacity. A delivery is retried only when
the receiver answered with a rate-limit refusal or a server error, on an exponential schedule
with jitter, honouring a `Retry-After` header when one is given.

**Backpressure and shedding.** When work arrives faster than it can be finished, new work is
refused at the boundary with a clear reason and the reason names the budget. Shedding at the
edge is the only honest response: accepting work that will never be finished converts a visible
refusal into an invisible loss.

**Behavioural thresholds.** Two rates decide whether a workspace is allowed to keep sending. A
bounce rate above 5 per cent or a complaint rate above 0.1 per cent over a rolling window raises
a warning to the owner naming the numbers and the affected domain; an unknown-recipient rate
above 10 per cent does the same. Crossing the higher band of either suspends sending for the
workspace, and the console says so plainly rather than silently dropping messages.

**Tracing.** Alongside the request identifier, a request carries a trace identifier and a span
identifier into every log line it produces and onto every unit of background work it starts, so
one delivery can be followed from the acceptance that created it to the event that closed it.

**Tenancy and authorisation.** Every query that touches a workspace-owned table is scoped by a
workspace identifier derived from the authenticated principal. Background work is scoped the
same way, from the workspace named in its own payload, and never runs unscoped: background work
is the classic place a cross-tenant leak escapes. The proof that this holds is a test in the
build that walks every route the application declares, calls each one with one workspace's
credential and another workspace's identifier, and requires a refusal every time, for a
credential and for each of the three roles. It finds the routes by asking the application what
it can do rather than by reading a list somebody typed, so a route added next year is already
covered. A route with no isolation coverage fails the build.

**Principles of validation, and edge cases.** Validate at the edge; refuse the unknown; report
every failure at once; never echo back a value the caller did not send. Addresses are normalised
before comparison: the domain part is lowercased and punycode-encoded, and an internationalised
address is accepted, stored punycode-encoded and displayed in its own script. A display name
containing a comma, a semicolon or a quotation mark is quoted and escaped rather than passed
through. The message-level edge cases are stated rather than discovered: a recipient list
carrying the same address twice sends one message to that address; a subject that is only
whitespace is refused; a message whose body is empty on both alternatives is refused; a message
accepted and then found to name a domain deleted a moment later is delivered, because acceptance
was already promised; and a message that is permanently undeliverable at handoff becomes a
terminal failure carrying the handoff diagnostic.

**Growth.** The message and event rows are the ones that grow without bound, and they are aged
out a whole month at a time rather than row by row, so enforcing retention is a routine
operation rather than an outage. Delivery attempts grow in bursts during an outage and are kept
for 30 days.

## Data model

Fifteen tables. All timestamps are UTC. The entity map is a person joined to a workspace by a
membership; the workspace owning domains, credentials, notification endpoints, audiences,
broadcasts, messages, suppressions and usage counters; a domain owning its records; an audience
owning its contacts; a notification endpoint owning its deliveries; and a message owning its
events.

**Every seeded account uses the password `deku-demo-pw-2026`.** It is benchmark fixture data,
not a secret. Hash it as normal; the exact literal must work at login, and it must be written
into `/app/USER_README.md` alongside each account so a grader can sign in.

`users` - `id`, `email` unique after normalisation, `password_hash`, `display_name`,
`created_at`.

`workspaces` - `id`, `name`, `plan`, `monthly_allowance`, `created_at`.

`memberships` - `id`, `user_id`, `workspace_id`, `role` in `owner`, `admin`, `member`. One
membership per person per workspace. The acting workspace is resolved from the authenticated
principal and never from a value in the request path or body.

`domains` - `id`, `workspace_id`, `name`, `state` in `pending`, `verified`, `failed`,
`selector`, `verified_at`, `last_checked_at`. A name is unique within a workspace and
deliberately not unique across the platform, because two customers may each legitimately control
a subdomain of one parent.

`domain_records` - `id`, `domain_id`, `record_type` in `TXT`, `MX`, `CNAME`, `host`, `value`,
`status` in `pending`, `correct`, `mismatch`, `missing`, `observed_value`. A domain reads
`verified` only while every one of its records reads `correct`; the domain state is derived from
the record statuses rather than set on its own.

`credentials` - `id`, `workspace_id`, `name`, `scope` in `sending`, `full`, `token_prefix`,
`token_hash`, `domain_id` nullable, `created_by`, `last_used_at`, `revoked_at`. The secret
itself is never stored.

`sessions` - `id`, `user_id`, `active_workspace_id`, `token_hash`, `last_seen_at`, `ip`,
`user_agent`, `revoked_at`. A session cookie is set with the http-only, secure and same-site
flags at the site root.

`messages` - `id`, `workspace_id`, `domain_id`, `credential_id`, `from_address`, `to_address`,
`cc`, `bcc`, `reply_to`, `provider_message_id`, `size_bytes`,
`subject`, `state`, `idempotency_key`, `broadcast_id` nullable, `created_at`, `last_event_at`.
The combination of workspace, credential and `idempotency_key` identifies at most one row while
the key is present, and that has to hold when two identical requests arrive at the same instant.

`message_events` - `id`, `message_id`, `event_type` in `queued`, `sending`, `sent`, `delivered`,
`bounced`, `complained`, `canceled`, `rejected`, `occurred_at`, `recorded_at`, `detail`. Rows
are appended and never updated. `messages.state` is derived from these rows rather than written
on its own, and an event whose rank sits below the current state is appended without moving the
state back.

`suppressions` - `id`, `workspace_id`, `address` normalised, `reason` in `hard_bounce`,
`complaint`, `source_message_id`. An address appears at most once per workspace.

`audiences` - `id`, `workspace_id`, `name`, `contact_count` derived from the contacts rather
than stored as an independent truth.

`contacts` - `id`, `audience_id`, `email` normalised, `first_name`, `subscribed`,
`unsubscribed_at`. One address appears at most once in one audience, and that holds under
simultaneous creates.

`broadcasts` - `id`, `workspace_id`, `audience_id`, `subject`, `body`, `state` in `draft`,
`requested`, `sent`, `scheduled_at`, `sent_at`.

`notification_endpoints` - `id`, `workspace_id`, `url`, `events`, `state` in `active`,
`degraded`, `disabled`, `signing_prefix`, `consecutive_failures`.

`notification_deliveries` - `id`, `endpoint_id`, `message_id`, `event_type`, `attempt`,
`status_code`, `duration_ms`, `state`. One row per attempt.

`usage_counters` - `id`, `workspace_id`, `period`, `metric`, `count`.

Operational objects can be deleted; historical facts cannot. Deleting a domain keeps the
messages sent from it, with the domain name kept on them. Deleting a credential keeps the
messages it sent. Deleting an audience removes its contacts and is refused while a broadcast
still points at it. Removing a membership keeps everything that person created, and a screen
showing a creator renders the stored display name with a former-member qualifier rather than
failing to resolve.

**Seed data.** Workspace `Northwind Relay` on plan `starter` with a monthly allowance of `500`,
carrying `owner@example.com` as `owner`, `admin@example.com` as `admin` and `member@example.com`
as `member`. Domain `mail.northwind.example.com` in `verified`. Domain `docs.northwind.example.com` in
`pending`, with its `TXT` record at `correct` and its `MX` record at `missing`. Audience
`Launch List` with three subscribed contacts. Three messages sent from `mail.northwind.example.com`:
one in `delivered`, one in `bounced` carrying a diagnostic on its bounce event, and one in
`complained`. A second workspace `Acme Relay` owned by `owner2@example.com`, carrying the
verified domain `mail.acme.example.com` and one message of its own.

Seeding must be idempotent: restarting the app must not duplicate rows.

## Front-end specification

This section carries the visual detail that the character notes above state as intent. Nothing
here introduces a new requirement; it fixes the type identities and the arrangement so that two
builders reading this brief produce the same product.

**Typography.** Four families carry four jobs: the body and interface family, a display sans for
the largest headings, a display serif for the hero heading, and a monospace for identifiers and
code. Each is declared with a fallback stack so that a face that has not arrived yet does not
leave a blank page, and each declares metric overrides so the fallback occupies the same space
as the real face.

**Type identities.** `Inter` is the body and interface family and is loaded as a variable face.
A display family carries the one largest heading per route; where a licensed display face is
unavailable, a freely licensed transitional serif with matched metrics stands in for it, and the
fallback stack declares metric overrides so that the largest heading does not reflow when the
face swaps. The monospace family carries identifiers, record hosts, record values and code
samples; a freely licensed monospace with matched metrics is an acceptable substitute, and the
code panel's line count per height shifts by roughly one line in twenty when it is used. No
binary asset ships with the build: every mark, portrait and illustration is generated from a
described procedure rather than fetched as a file.

**Sizes actually used.** `16px` at a regular weight with comfortable leading carries body text
and table cells. `14px` at a regular weight carries the log rows, the rail and the secondary
labels, and `14px` at a medium weight carries a table header. `12px` carries the smallest
labels and the chart axis. `20px` and `24px` carry a panel heading. One display size per route
sits far above all of them. Tracking tightens as size grows, and the largest heading is the
tightest.

**Arrangement.** The left rail is fixed at a comfortable reading width and collapses to an icon
strip whose collapsed state is remembered for that person. The top bar is short and sticky and
carries the breadcrumb, the search control, the notification bell and the account menu. The main
region scrolls independently of the rail. Transient confirmations appear at the bottom right in
a polite live region. The overview is one band of counters above one full-width chart above two
half-width panels. The emails list is a full-width table. A detail route is a header band, then
a two-column arrangement of envelope and timeline, then the body panel beneath.

**Surfaces and edges.** Section boundaries are drawn with a hairline that fades to nothing at
both ends rather than with a solid rule, which is why this product has almost no visible
borders between bands. The large display heading is filled with a gradient running from bright
at its top left to half strength at its bottom right, so the words read like polished metal
catching a light. Product imagery fades into the ground at its lower edge rather than ending on
a hard line. A faint grain sits over the large panels at low strength.

**Label palette.** A tag a person assigns draws from a fixed set of hues at three steps each,
covering bronze, crimson, cyan, grass, iris, lime, mauve, orange, plum, teal and yellow, so that
every choice stays legible. A free colour picker produces unreadable tags within a day and is
not offered.

**Empty and loading.** A route whose data is in flight shows a skeleton after a short pause, and
after ten seconds it replaces the skeleton with an explanation and a retry rather than spinning
for ever. An offline browser shows a persistent marker, serves its last read with the age of
that read stated, and refuses writes with an explanation rather than queueing them, because a
silently queued send that fires an hour later is worse than a refusal now.

**The colour architecture.** Colour is organised as a ladder rather than as a paint chart. Each
family runs twelve steps from the app background, through a subtle raised background, the
component background at rest, hovered and pressed, a subtle border used for separators, the
border at rest, the border hovered which is also the focus ring, the solid fill carrying the
strongest chroma, that fill hovered, the low-contrast secondary text, and finally the
high-contrast primary text. Each step has one fixed job, so nobody picks a grey: they pick a
step. A parallel ladder of the same steps at partial opacity exists for surfaces that have to
composite over whatever sits behind them, and those steps are a cool blue-white rather than a
neutral, which is what makes a panel read as lit. A modal scrim is the ground at near-full
opacity. Placeholder text inside a field sits at the mid step of the neutral ladder, which is
dimmer than secondary text and still legible.

**The state colour contract.** Delivered and operational take the solid green fill with green
secondary text. Queued and scheduled take a translucent neutral with the light neutral text.
Deferred and delayed take the solid yellow fill with yellow text. Bounced and failed take the
solid red fill with red text. Complained takes the solid amber fill with amber text. Canceled
takes the faintest translucent neutral with the mid neutral text. A light scale of the same
neutral ladder exists for print and for any surface that has to be read on white.

**Iconography.** Every icon is drawn as geometry in the page rather than fetched as a file:
outlined strokes on a square drawing box, one stroke weight throughout, rounded caps and joins,
and the stroke taking the current text colour so an icon inherits whatever it sits inside. The
log carries one glyph per state, and each one is distinguishable by shape alone: a tick inside a
circle for delivered, a circle with an exclamation for deferred, an arrow turning back for
bounced, a flag for complained, a clock for queued, and a struck-through circle for canceled.
The product wordmark is a single path drawn at the rail head, and the only decorative marks in
the product are generated from a described procedure, never shipped as an image.

**Elevation.** There is one raised treatment and it is not a drop shadow. A control that is
pointed at gains a stack of soft white glows spreading outward, so on the black ground it reads
as the control emitting light rather than lifting off the page. Large panels carry a very wide,
very soft shadow that reads as depth rather than as an edge. Reproducing this with a
conventional dark drop shadow produces a page that looks flat and cheap in a way that is hard to
diagnose afterwards, and that is the failure to design against.

**Recurring surface treatments.** Four treatments recur often enough to be decisions rather than
one-off styling: a glass panel whose fill is a faint diagonal wash of near-white over the ground
and whose backdrop is blurred; a chip fill that fades from a pale cool tint at its leading edge
to nothing at its trailing edge; the display-text fill described above; and the hairline that
fades to nothing at both ends. Masks carry real work here rather than decoration: imagery fades
into the ground at its lower edge, a screenshot fades at its diagonal corner, a long panel
dissolves downward, and a horizontally scrolling strip fades at both of its ends.

**Spacing, radius and containers.** Every gap is a multiple of one small base unit, so spacing
is chosen by counting units rather than by picking a number. Radii rise in a fixed order:
hairline for the smallest chips, small for inputs and buttons, medium for cards inside panels,
large for the big product panels, and fully round for pills and status dots. Container widths
rise in the same conventional way, with a reading column at the middle of the range and the
widest bands at the top of it.

**The type scale, declared and used.** The declared scale runs from the smallest label through
body, large body, and the heading steps up to the display sizes, each with its own line height,
and tracking tokens run from tighter through normal to widest with the display sizes taking the
tightest. What the interface actually uses is much shorter than what is declared, and that gap
is deliberate: the two body sizes and the one display size carry almost all of the volume.

**Global chrome.** The signed-out header is a short bar carrying the wordmark at the left,
linking to the site root, then the navigation, then a pair of controls at the right. Its items
sit at the secondary neutral at rest and rise to the primary neutral when pointed at or focused,
and the horizontal padding grows one step at the wide breakpoint. A navigation item that opens a
panel waits a moment of sustained hover before opening, so that crossing the bar on the way
somewhere else does not open three panels; the panel itself is a glass surface with the large
radius and comfortable padding. The footer carries the product links in columns, grouped as
resources and company, with a status indicator whose healthy state is the teal signal green
drawn as a dot with a second circle pulsing outward behind it. On a narrow viewport the header
collapses to the wordmark and one control, and the navigation becomes a full-height panel that
slides down over the page and can be dismissed with the escape key or by the control that opened
it.

**Motion, in detail.** The vocabulary is small and every entrance is short. A surface appears by
fading in while sliding a few pixels from the direction it belongs to, or by fading in while
growing from just under its final size, and it leaves the same way in reverse. The easing is a
symmetric ease for most things, a soft settle on the pulsing indicator and on panel opacity, a
hard decelerate where almost all of the movement should happen immediately, and an acceleration
into an exit. There is exactly one overshoot in the whole system, on one small transform, and
everywhere else the product refuses to bounce. Two motions are spring-driven rather than curve
driven, a container resizing as its contents change and a value stepping between states, and
both settle without visibly oscillating, one over about a second and the other over about two
thirds of that. The loops are a spinning busy indicator, a slowly rotating border angle, a
status dot pinging outward, a pulsing skeleton, three dots rising in sequence, a slowly rotating
wash behind one pill, a strip scrolling horizontally which pauses rather than stops when it is
pointed at so it resumes from where it was, a highlight sweeping a surface once, a gradient
travelling through text, and a blinking caret. Under a reduced-motion preference the entrances
land in their final state with no fade and no travel, the loops stop except the busy indicator
which falls back to an opacity pulse because it carries meaning, the scrolling strip stops at
its start and becomes scrollable by hand, and the spring motions become immediate.

**Responsive, in detail.** The breakpoints are declared in `rem` rather than in pixels so that
they move with the reader's own text size, and they run small, medium, large, extra large and
double extra large, with one further wide-screen adjustment above the last of them. Layout
decisions are made by capability queries rather than by guessing from width alone: a hover
affordance appears only where a pointer can hover, a coarse pointer gets larger targets, and a
preference for reduced motion or for a particular colour scheme is asked for rather than
assumed. At the two handset widths the rail becomes a slide-over, the log becomes a stack of
cards, and the chart keeps its columns but sheds its axis labels. Orientation is not assumed
either: turning the device on its side rearranges rather than breaks, and zoom to twice the
normal size loses no control and overflows nothing sideways.

**Accessibility, in detail.** The document structure is landmarks with one main region per
route, headings descend in order without skipping a level, and every form control has a label
bound to it rather than a placeholder standing in for one. A live region announces a transient
confirmation politely and an error assertively; a send in progress is announced politely at its
start and at its completion and not at every step in between. Text that is present for a screen
reader and hidden from the eye uses the visually hidden pattern rather than being removed from
the page or moved off it. Every image declares its dimensions so that nothing below it jumps
when it arrives, and imagery in a band further down the page is loaded as that band nears the
viewport rather than all at once on load. The chart is reachable by keyboard column by
column and its figures are available as a table. Focus moves to the first heading of a route
after a navigation, and focus is trapped inside a dialog and returned to whatever opened it.
Accessibility testing runs as part of the build rather than after it, covering keyboard reach,
announced names and contrast, and a failure there is a defect like any other. The same is true
of testing in general: the isolation proof, the idempotency proof and the reconciliation between
the counters and the rows are all checked on every change rather than by hand.

**Honesty about what this specification is.** Everything above states the product and its
requirements. Where the source material carried a non-goal, an evidence gap, a commercial figure
or a measurement that could not be reproduced, it has been left out on purpose rather than
guessed at, and the non-goals in `## Constraints` are the record of that.

## Constraints

These are the non-goals, named so that their absence is a decision rather than an oversight.

One workspace per view, resolved from the session and never from the request. No second tenant
model above the workspace, no organisation tree, no custom role builder and no per-resource
grant. No marketing site, no documentation application, no blog, no changelog, no careers
listing and no status page. No visual broadcast editor, no template library, no automation
builder, no inbound mail routing and no reading interface for received mail. No dedicated
sending addresses and no sending pool selection. No open tracking and no click tracking. No
payment processor, no invoices, no plan change and no card on file: the plan is a stored name
and an allowance. No single sign-on, no directory provisioning, no policy engine, no delegated
grant and no tamper-evident audit store. No region preference and no data residency pinning. No
command line tool, no client library and no editor integration. No block-list checking and no
reputation scoring beyond the counts the overview already carries. No file upload and no
attachments. No external network calls at runtime beyond the two named backing services. No
native application. The app must stay responsive with fifty thousand `messages` rows and five
thousand `contacts` rows in one workspace.

## Deployment contract

- The app must be reachable at `APP_PUBLIC_URL`. The port mapping is `${APP_PUBLIC_PORT}:4173`.
  `4173` is the container-internal port and `APP_PUBLIC_PORT` is what the outside world uses.
  Read both from the environment; never hardcode either.
- The HTTP API is served on that same origin under the `/api` prefix.
- `GET /api/health` returns `200` once the app is ready.
- The app starts from the environment image with no manual steps.
- Login credentials, or an explicit statement that there are none, are written to
  `/app/USER_README.md`.
- Reserved `.browser_screenshots/` and `.downloads/` directories exist at the app root, empty.
- Serve a production build behind a static or preview server, never a dev server.
- The server must keep running after this session ends and must not be a child of the shell. An
  ordinary background job dies with its shell, and the app will not be running when it is next
  opened.
- Bind `0.0.0.0`, never `127.0.0.1` or `localhost`. A loopback-only listener is unreachable from
  outside the container.
- The backing services named in this brief are already running and reachable at their
  environment variables. Do not download, install, compile or start a copy of any of them.
- Use only the providers named in this brief. No edge functions.
- No persistent volumes, no fixed container names, no custom networks.

**API shapes.**

|---|---|---|
| `POST /api/auth/signup` | `{"email", "password", "display_name"}` | the created person and their workspace |

| `GET /api/auth/me` | none | the signed-in person, their workspace and their role |
| `GET /api/domains` | none | a top-level JSON array of domains |
| `POST /api/domains` | `{"name"}` | the created domain with its generated records |
| `GET /api/domains/{id}` | none | one domain with its `records` |
| `POST /api/domains/{id}/verify` | none | the domain with each record status refreshed |
| `DELETE /api/domains/{id}` | none | an empty success |
| `GET /api/credentials` | none | a top-level JSON array of credential metadata |

| `DELETE /api/credentials/{id}` | none | an empty success |
| `POST /api/v1/emails` | the send body above, with an `Idempotency-Key` header | the accepted `id` and `created_at` |
| `GET /api/v1/emails/{id}` | none | one message and its current `state` |
| `POST /api/v1/emails/{id}/cancel` | none | the message in `canceled` |

| `GET /api/broadcasts` | none | a top-level JSON array of broadcasts |
| `POST /api/broadcasts` | `{"audience_id", "subject", "body"}` | the created broadcast in `draft` |
| `POST /api/broadcasts/{id}/send` | none | the broadcast in `sent` |
| `GET /api/notifications` | none | a top-level JSON array of endpoints |
| `POST /api/notifications` | `{"url", "events"}` | the endpoint and its signing secret, once |
| `POST /api/notifications/{id}/test` | `{"event_type"}` | the status code, the duration and the response excerpt |
| `GET /api/notifications/{id}/deliveries` | none | a top-level JSON array of attempts |
| `GET /api/usage` | none | the period, the metered count and the allowance |
| `GET /api/health` | none | `200` |

Bearer authentication is carried on everything except `POST /api/auth/login`,
`POST /api/auth/signup` and `GET /api/health`. A successful call returns the named resource or
shape; an invalid or unauthorized call is rejected as a client error, never as a server error
and never as a silent success.

**No mocks.** An in-memory list of sent messages, a hardcoded delivery state the app hands back
to itself, a message written to a file on the app container instead of handed to the mail
server, or a counter incremented in the app process instead of read from the rows: each of those
is a contract violation. The named providers are the fact. The app's screens and its own tables
can only reflect what lives in `postgres` and what was actually handed to `mailpit`, never
substitute for it.

## Definition of done

A developer can sign up, prove they control a sending domain, mint a credential, hand a message
to the sending interface, and watch that message settle into `delivered` in the log while real
mail reaches an ordinary recipient. The overview's counters and chart agree exactly with the
message rows beneath them for the same window. The same message handed over twice under one
idempotency key produces exactly one message, and a member who composes a broadcast cannot send
it to a live audience.
