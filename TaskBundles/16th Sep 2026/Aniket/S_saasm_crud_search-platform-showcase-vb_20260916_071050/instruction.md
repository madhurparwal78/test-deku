# Kestrel

Build and deploy a working web application from this brief. There is no starting codebase. When you are done, a stranger must be able to open the app in a browser, type into the search box in the header and watch real ranked results with live per-source counts appear as they type, narrow the customer stories index by two industries at once and see the counts on every other filter group stay truthful, read the four pricing plans against a comparison grid whose plan names stay visible while it scrolls, and submit the demo request form and land on its success page, without hitting an error page. The hard part is that the search is the product: the ordering is a ladder of eight tie-breaks with no score anywhere in it, and the counts beside an unticked filter value must answer "how many would I get if I ticked this as well", which is a different question from the one that produced the results on screen. A search box that filters an array the page already holds is a picture of this product, not this product.

## Overview

Kestrel sells search and retrieval to other businesses, and the site that sells it demonstrates it on itself. The box at the top of every page is not decoration: it runs the company's own documentation, support articles, blog posts, website pages, developer content, resources, academy courses and customer stories through the same engine the company sells, with counts beside each group, matched words picked out, and a conversational mode that answers in prose and always offers a way back to the plain results.

Four audiences arrive and each is served in a different stretch. Engineers asking whether they can integrate this and what it costs per request are served by the header search over the documentation and by the pricing route. Commerce and merchandising leads asking whether it lifts conversion and whether their team can steer results without a developer are served by the home route's capability panel, the customer stories and the operator console. Executives and analysts asking whether this is a credible vendor are served by the analyst recognition band and the customer logo walls. Existing customers are served by the utility bar, the search and the console.

Behind the site sits the thing the site is selling: an index, a query engine, a merchandising layer and an operator console. Records are written in batches, folded and tokenized into a per-generation index, and answered against a ladder of eight ranking criteria. A merchandising lead pins and hides results, writes synonyms and reads why one hit outranks another. A key system keeps one customer's rows away from another's even inside one catalogue.

What it deliberately is not: no payment of any kind, so the four plans are displayed copy and every paid action leads to the demo request route; no email, no SMS and no push; no third-party script anywhere, which means no consent vendor, no support chat, no tag manager, no analytics vendor, no advertising panel and no embedded video player; no multi-region cluster and no physical replication; no external language model and no external embedding provider; no native application; and no binary asset at all, so no image file, no video file and no font file ships with the build.

The genuinely hard part is that the ordering contract and the counting contract are both lexicographic rather than arithmetic, and the easy version of each looks correct on a small corpus. A single relevance score sorted descending cannot express "a misspelled match never outranks a correct one". A single grouped pass over the result set cannot answer what the counts beside an unticked filter value are asked to answer.

## Core features

### Auth, workspaces and applications

This app owns its own accounts: an email, a password, no external identity provider. Signing in hands back a bearer token, the console sends that token on every later request, and the token is good for twelve hours; past that it is refused and the operator signs in again. A stored password is a hash and never the characters that were typed. Signup asks for an email, a password and a workspace name, lowercases the email before storing it, and refuses a second account on an address already taken, naming the email field when it does. Nothing resets a password and nothing is ever sent to anybody.

1. Signing up with an unused email succeeds, returns a usable token, and creates exactly one workspace, one application inside it and one `owner` membership. Signing up again with the same email is rejected as invalid with a message naming the email field, and no second account, workspace or application row exists.
2. Every request resolves to exactly one workspace and no request may reach two. `owner2@example.com` requesting any index, key, rule, record, task or analytics figure belonging to `Kestrel Demo` is denied and reads nothing, and the same holds in the other direction. A denial for an index the caller may not see is worded identically to a denial for an index that does not exist, so the wording never reveals which indices exist.
3. Every form on the site and in the console rejects invalid input inline, names the field that is wrong, and writes nothing: a signup with an empty password, a demo request with a blank business email, a newsletter submission with a malformed address and a key creation with no access list all leave the database exactly as it was.

### The site search overlay

The overlay is the product demonstration. It opens from the header field on every route with chrome and from the body of the not-found route, and it searches the seeded `site_content` index. It has two modes, a results mode and a conversational mode, and the toggle sits in the field itself.

The overlay is wired to the engine at every point, and two of those wires are what make it a demonstration rather than a decoration: every keystroke is a search request; the source list with its counts is a disjunctive facet count; the marked words come from the highlight contract; `Show more results` is pagination; a click on a hit is an interaction event carrying the query identity; the conversational mode is the answer pipeline; and the typed suggestions are query suggestions built from the analytics rollups. Counts that stay honest when two sources are selected, and suggestions derived from what people actually searched for, are both things a visitor can check in ten seconds.

4. The overlay issues a query against the real index on every keystroke and renders the returned hits, never a filtered copy of anything the page already holds. Each hit row carries a title, a meta line of the form `Website • products`, and an action reading `Learn more →`, under a heading reading `Products & Resources`.
5. Under a heading reading `Filter by source` the overlay renders a refinement list of the eight sources with a live count beside each: `Documentation`, `Support`, `Blog`, `Website`, `Developers`, `Resources`, `Academy`, `Customer Stories`. With no query and no filter those counts are `40`, `24`, `18`, `12`, `9`, `8`, `5` and `4`. Selecting `Blog` must not send the other seven to zero: these counts are disjunctive and answer how many results each source would add, which is rule 27 applied to this component.
6. Matched words are wrapped in the highlight tags inside the hit's own text and rendered as a marked span. The number of results is announced to assistive technology once the list has settled, and never once per keystroke.
7. A control reading `Show more results` loads the next page in place, without a navigation and without losing the visitor's place. A click on a hit records an interaction event carrying the query identity that produced that hit, per rule 83.
8. Before anything is typed the overlay shows four whole questions, each a full sentence rather than a keyword: `How will Kestrel improve our search experience and conversions?`, `How do I integrate Kestrel search into my app?`, `Can Kestrel help shoppers find products faster and increase sales?` and `Will Kestrel scale with our traffic and data size?`. Under a heading reading `Suggestions` it shows four keyword buttons: `Kestrel API integration`, `Kestrel search benefits`, `Kestrel scalability` and `AI search for ecommerce`. Those buttons are built from the query rollups of rule 85, not from a fixed list written once, so a query nobody has ever run is never offered.
9. The mode toggle is labelled `AI mode`. In the conversational mode the panel carries the assistant title `Kestrel Assist`, a `New chat` action, a `Back to results` action and the attribution `AI powered by Kestrel`. `Back to results` is not optional: the conversational answer is a layer over the results and never a replacement for them, so the results are still there when the answer is not useful. The filter controls in the overlay read `Show All` and `Clear All Filters`.
10. The overlay is a combobox over a live list. Down and Up move the active option while the input keeps focus. Enter opens the active option, or submits the raw query when none is active. The first Escape clears the list and the second clears the input. Tab completes to the active option's text without opening it. Home and End move within the text and never within the list. The overlay closes on a route change and is never restored by one.

### The ranking cascade

The core contract of this build. Hits are ordered by eight criteria applied in sequence: each criterion is a comparison, and only when two hits are equal on it is the next one consulted. There is no weighted sum anywhere in the ordering and no relevance score is computed for it.

11. The eight criteria, in the order the `ranking` setting holds by default, are `typo` ascending, the total typos across matched words; `geo` ascending, the distance bucket; `words` descending, the number of matched optional words; `filters` descending, the sum of matched optional-filter scores; `proximity` ascending; `attribute` ascending; `exact` descending; then `custom`, the `customRanking` list in its own order. A record with one typo ranks below every record with none, however good it looks on every later criterion and however popular it is.
12. The seeded `fixtures` index holds `r1` titled `Blue Running Shoes` with popularity `1`, `r2` titled `Blue Runing Shoes` with popularity `100`, `r3` titled `Shoes Running Blue` with popularity `50`, and `r4` titled `Blue Shoes` with popularity `90` and the word `running` in a second attribute, under a `customRanking` of `desc(popularity)`. The query `blue running shoes` returns them in the order `r1`, `r3`, `r4`, `r2`. `r2` is the most popular record by a wide margin and carries one typo, so it is last. Removing `customRanking` entirely leaves that order unchanged. With `typoTolerance` set to `false`, `r2` is absent and the other three keep their order.
13. Ordering is total and stable. After `custom`, the final tie-break is `objectID` ascending. The same query run fifty times returns a byte-identical ordering, and collecting every page of a result set yields each `objectID` exactly once, none repeated and none omitted.
14. `proximity` is, for each adjacent pair of query words in query order, the number of tokens between their closest matching positions in the same attribute plus one, capped at `8`, summed over the pairs. Adjacent and in order costs `1`; adjacent and reversed costs `2`, not the cap. Words matched in different attributes cost the cap. Optional words that were not matched are skipped when forming pairs rather than contributing the cap. A phrase requires proximity `1` for its pairs and is a filter rather than a preference. The query `blue shoes` therefore returns `r4` before `r1`.
15. `attribute` compares the position of the winning attribute in `searchableAttributes` first, zero based, lowest wins, then the position of the match inside that attribute, zero based and capped at `63`, earliest wins. Attributes wrapped as `unordered(attr)` at one list position share an index and set the word-position component to zero, so a match anywhere in them is as good as a match at the start, which is what a description wants and a title does not. Ordered attributes at different positions never tie.
16. `exact` counts the query words matched with zero typos, not through a prefix expansion and not through an alternative unless `alternativesAsExact` says so. For a single-word query, `exactOnSingleWordQuery` chooses the definition: `attribute`, the default, means the word equals the whole value of a searchable attribute; `word` means it matches a whole word in any searchable attribute; `none` disables the criterion for single-word queries. `alternativesAsExact` may carry `ignorePlurals`, `singleWordSynonym` and `multiWordsSynonym`, and by default a one-word synonym counts as exact while a multi-word one does not. Decompounded parts never count as exact.
17. `custom` is the `customRanking` list, each entry its own tie-break level, each written `asc(attr)` or `desc(attr)`. Numeric values are compared at a precision of four significant decimal digits, so `4.7192` and `4.7195` are equal and fall through to the next criterion while `4.71` and `4.83` do not. A record missing the attribute sorts last for both `asc` and `desc`: a record that does not have the attribute never wins on it. Booleans compare as one and zero, strings compare by code point after folding, and a list compares by its first element.
18. `geo` applies when `aroundLatLng` is set. Distance is haversine metres on a sphere of radius `6371000` metres, then bucketed by `aroundPrecision`, default `10` metres, and the bucket rather than the distance is what the criterion compares. A record may carry `_geoloc` as one point or a list of points and the closest is used. The seeded `catalog` index holds three records at `5`, `8` and `60` metres from the pinned point `48.8566,2.3522`, with popularity `1`, `100` and `50`. Searching around that point returns the eight-metre record first, then the five-metre record, then the sixty-metre one: the two nearest tie on the geo bucket and popularity breaks the tie. Returning them in raw distance order has made geo a total order and starved every criterion below it. `aroundRadius` filters before ranking, `aroundRadius` set to `all` disables that filter and keeps the ranking, and `insidePolygon` and `insideBoundingBox` are filters only and do not enable the criterion.
19. `relevancyStrictness`, from `0` to `100` with a default of `100`, controls how far down the cascade a record may be admitted once optional-word matching has been used. At `100` only the best `words` bucket is returned; at `0` every partial match is returned; in between, hits below the cut are returned marked as not promoted and the response reports the count of hits above the cut.

### Text pipeline, typo tolerance and prefixes

20. Every string value of every attribute named in `searchableAttributes` passes through one pipeline, in this order, and the order changes results on accented and cased text. Apply Unicode normalization to `NFKC`. Fold case fully, so both `SS` and the eszett fold to `ss`, with the Turkish tailoring applied only when `queryLanguages` carries `tr`. Fold diacritics by removing combining marks after decomposition and recomposing, so `crème` and `creme` become the same token, exempting per language the letters that are letters rather than accents in Danish, Swedish, Norwegian and Finnish. Tokenize by script: Latin, Cyrillic and Greek split on anything that is neither letter nor digit, keeping an apostrophe inside a word as one token so `o'brien` is one token while `l'hotel` yields `l` and `hotel`, and yielding three tokens for a hyphenated word, the two parts and the joined form; Han, Hiragana and Katakana take overlapping bigrams, so `東京都` yields `東京` and `京都`, never unigrams and never a dictionary segmentation; Thai, Khmer and Lao take dictionary segmentation, falling back to whole-run tokens with the fallback reported in the index build log rather than passed over. Treat a run of digits as one token, with a decimal point inside digits not splitting it, and a digit run adjacent to letters yielding the joined token and both parts, so `a4` yields `a4`, `a` and `4`. Remove stop words only at query time and only when `removeStopWords` is on for the matching language, never at index time, because removing them at index time makes the setting irreversible without a full rebuild. Map a token to a canonical form only when `ignorePlurals` is on, from a language-specific suffix table and not a stemmer, so `houses` maps to `house` while `housing` does not. Decompound a token into its parts, marked as decompounded, for German, Dutch, Finnish, Swedish, Danish, Norwegian and Korean when `decompoundedAttributes` names the attribute.
21. **Every token keeps a byte offset range into the original, un-normalized string.** Folding changes string lengths, and the highlight tags of rule 39 are inserted into the original text at those offsets, so a build that records offsets after folding places the tags in the wrong place on exactly the accented and cased text that made the folding necessary.
22. Typo tolerance is decided per query word by the word's length in code points **after** folding, never in bytes and never before folding: below `minWordSizefor1Typo`, default `4`, no typos are allowed; from there to below `minWordSizefor2Typos`, default `8`, one typo; at `minWordSizefor2Typos` and longer, two. The distance is Damerau-Levenshtein, so a transposition of two adjacent characters costs `1` and not `2`: the seeded `fixtures` record `t1`, titled `Hello World`, is one typo from the query `hlelo` and is returned with a reported typo count of `1`. Plain Levenshtein scores that as two and pushes a very common human error out of a one-typo budget.
23. The first character may never be substituted or deleted, so the query `xello` returns `t1` not at all. Digit tokens get no tolerance unless `allowTyposOnNumericTokens` is on, so the query `2024` returns `t4`, titled `2024 Edition`, and never `t5`, titled `2025 Edition`. Tolerance is off inside a phrase and off for attributes named in `disableTypoToleranceOnAttributes`. `typoTolerance` set to `min` returns typo matches only when the zero-typo set is empty, and `strict` drops the two-typo matches whenever a one-typo match also exists.
24. Only the last word of a query is matched as a prefix, and only under the default `queryType` of `prefixLast`; `prefixAll` applies the rule to every word and `prefixNone` to none. The query `hel` returns both `t1` and `t2`, titled `Helo Word`; the query `hel world` returns `t1` and not `t2`, because only `world` is the prefix candidate. Prefix expansion is bounded at `1000` term-dictionary entries, and on reaching the bound it stops at the most frequent matching terms by document frequency and the response reports `exhaustiveTypo` as `false` rather than truncating in silence.
25. A record matches when **every** query word matches, after word removal has decided which words are still required. Matching is per word across the whole record and not per attribute, so the query `wor hello` still returns `t1`. The seeded `fixtures` index proves the folding in four more ways: the query `creme` and the query `crème` both return `t3`, titled `Crème Brûlée`; the query `strasse` returns `t7`, titled `Straße`; and the query `東京` returns `t6`, titled `東京都庁`.
26. Words in `optionalWords`, and every query word past the tenth, are optional, and the `words` criterion orders by how many of them were matched. When the required words yield nothing, `removeWordsIfNoResults` decides what happens next: `none` returns zero hits; `lastWords` drops the last word and retries, one word at a time, until non-empty or one word remains; `firstWords` does the same from the front; `allOptional` retries once with every word optional and returns records matching at least one. **Each removal round is a fresh, complete ranking pass.** Results from a round that removed two words never interleave with results from a round that removed one; the earlier round's results come first, in their entirety.

### Filters, facets and deduplication

27. **Disjunctive facet counts, the behaviour this product is sold on.** For an attribute the visitor is currently filtering on, where the interface allows several of its values to be selected at once, the counts are computed with that attribute's own filter removed and every other filter kept. Every other facet, and the hits themselves, use the full filter tree. The seeded `catalog` index holds `10` red Acme records, `5` blue Acme, `20` red Zeta and `1` blue Zeta. With `brand:acme` and `colour:red` both ticked and both `brand` and `colour` declared disjunctive, the counts are `brand.acme` `10`, `brand.zeta` `20`, `colour.red` `10` and `colour.blue` `5`. A single grouped pass over the result set returns `0` for `brand.zeta` and `0` for `colour.blue`, which is the wrong answer and is recognizable on screen because every unticked box shows zero and the filter list can then only ever be narrowed.
28. A value of a disjunctive attribute that is currently selected but matches zero records under the pruned tree is still returned, with a count of `0`, so the visitor can untick it. Dropping it strands the interface in a state the visitor cannot leave. `exhaustiveFacetsCount` is reported as `false` whenever any grouping reached `maxValuesPerFacet`.
29. `facets_stats` follows the same rule: the numeric minimum, maximum, average and sum for an attribute the visitor is filtering a range on are computed with that range removed. Computing them with the range applied collapses a range control to the width of the current selection and the visitor can never widen it again.
30. For an attribute that is **not** currently filtered on, the count of each value is the number of records matching the query and every filter, grouped by that attribute's values: one grouped pass, and that is the whole of it.
31. The `filters` string is one string parsed into a boolean tree. The atoms are a facet as `attr:value` with the value quoted when it contains a space, a numeric comparison with `<`, `<=`, `=`, `!=`, `>=` or `>`, a range written `attr:number TO number` and inclusive at both ends, and a tag as `_tags:value`. Parentheses group. Precedence is `NOT`, then `AND`, then `OR`, which is the arithmetic convention and the opposite of what a left-to-right reader expects, so `a:1 OR b:2 AND c:3` parses as `a:1 OR (b:2 AND c:3)` and the interface renders the parenthesization back rather than echoing the string. An attribute not present in `attributesForFaceting` is rejected as invalid, as is a numeric comparison against a quoted value: `price > "10"` is rejected because the quotes make it a string, and is never a silent lexical compare. Anything outside the grammar is rejected with the offending span named.
32. `facetFilters`, `numericFilters` and `tagFilters` take a nested array whose nesting **is** the boolean structure. `["a:1", "b:2"]` means `a:1 AND b:2`. `[["a:1", "a:2"]]` means `a:1 OR a:2`. `[["a:1","a:2"], "b:3"]` means `(a:1 OR a:2) AND b:3`. `["-a:1"]` means `NOT a:1`. The outer level is AND, one level of nesting is OR, and there is no second level: a doubly nested array is rejected as invalid. A multi-select interface produces `[["brand:acme","brand:zeta"]]` when two values of one group are ticked and `["brand:acme","colour:red"]` when one from each of two groups is, and flattening both into one array turns a search for two brands into a search for records made by both brands at once, which returns nothing and reads as missing data.
33. `optionalFilters` does not filter. It feeds the `filters` criterion of rule 11: `["brand:acme<score=3>"]` adds `3` to that criterion for matching records and nothing for others, and a negative form such as `["-brand:zeta<score=2>"]` scores the records that do not match.
34. Filtering happens before ranking and before facet counting. A filtered-out record contributes to no count anywhere except a disjunctive count on its own facet.
35. `attributeForDistinct` names an attribute and `distinct` set to `N` keeps at most `N` records per distinct value of it, keeping the best ranked. Deduplication runs **after** ranking and **before** pagination, so records it removes do not occupy slots on a page. `nbHits` then counts **groups**, not records. The seeded `shirts` index holds `1200` records, `300` distinct `shirt_id` values in groups of four colours. With `attributeForDistinct` set to `shirt_id`, `distinct` set to `1` and `hitsPerPage` at `20`, page zero reports `nbHits` `300` and `nbPages` `15` and returns twenty distinct `shirt_id` values. Reporting `1200` and `60` tells the visitor there are twelve hundred results and runs out after fifteen pages.
36. Facet counts under deduplication count **records**, not groups, unless `facetingAfterDistinct` is true, in which case they count groups: on the `shirts` index the red colour count is `300` by default and `75` with `facetingAfterDistinct` on. The two settings must agree across a session or the numbers on one page contradict each other. A record promoted by a rule is exempt from deduplication and does not consume its group's quota.
37. Facet value search answers over the **values** of one facet rather than over the records, with prefix matching, the index's own typo settings, and the same disjunctive rule. Only attributes declared `searchable(attr)` in `attributesForFaceting` are eligible and the rest are rejected as invalid.
38. The read path runs in one order and reordering any two stages changes results: parse the query and parameters; apply the rules whose conditions match and merge their params; expand synonyms and plurals into the query tree; retrieve candidates per word with typo and prefix expansion; intersect the words and apply word removal if empty; apply filters, tombstones and exclusions; compute personalization scores if enabled; rank by the cascade; apply rule promotions and hides; deduplicate; compute facet counts, conjunctive and disjunctive; paginate; highlight and snippet **the returned page only**; then attach the query identity, the ranking info, the applied rules and the variant. Highlighting the whole result set rather than the page is the most common reason a correct engine is too slow to ship.

### Highlighting, snippeting, pagination and the response

39. Every hit carries a highlight result mirroring the shape of the record, and a snippet result for the attributes named in `attributesToSnippet`. Tags are inserted into the **original** attribute value at the offsets rule 21 recorded, and the value returned is the original text and not the folded text: the query `creme` against `Crème Brulee` returns the accented word wrapped in tags, never an unaccented one, and the query `strasse` against `Straße 12` wraps the eszett word without shifting the tags by a character. The default tags are `<em>` and `</em>` and are configurable through `highlightPreTag` and `highlightPostTag`.
40. A match level of `none`, `partial` or `full` accompanies each highlighted attribute, and `full` means every query word matched inside that attribute. Overlapping matches merge into one tag pair: two adjacent matches with nothing between them merge, and with one space between them they do not, so `red red red` under the query `red` returns three separate tag pairs. A prefix match highlights only the matched prefix, so `hel` against `Hello World` wraps only the first three letters. Snippets are `N` words wide, centred on the first match, with `snippetEllipsisText`, default `...`, on any side that was cut and on neither side when the whole value fits. The service returns raw text with tags and never escapes it itself, because escaping is the caller's decision and a service that escapes as well produces double-escaped output.
41. `nbHits` is the number of matching records, exact when `exhaustiveNbHits` is true and an estimate otherwise. `nbPages` is the lesser of the pages implied by `nbHits` over `hitsPerPage` and the pages implied by `paginationLimitedTo`, default `1000`, over `hitsPerPage`. `page` is zero based and `hitsPerPage` runs from `1` to `1000`. `offset` and `length` may be used instead of `page` and `hitsPerPage`, and mixing the two in one request is rejected as invalid rather than resolved by a silent precedence rule. A page past `nbPages` returns an empty hit list and a success, never a not-found; an offset past `paginationLimitedTo` is rejected as invalid.
42. A search response carries the hits, each with its `objectID`, its highlight result and, when `getRankingInfo` is on, its ranking info; `nbHits`, `page`, `nbPages`, `hitsPerPage`; the three honesty flags `exhaustiveNbHits`, `exhaustiveFacetsCount` and `exhaustiveTypo`; a processing time; the `query` and the `parsedQuery`; a `queryID` of thirty-two hexadecimal characters; the `facets` map and the `facets_stats` map; the list of applied rule identifiers; the A/B variant identifier when one applied; and any `userData` a rule attached. Every one of the three honesty flags is computed. A build that returns them as constants is correct and unmaintainable, because nobody can then tell a wrong answer from a truncated one.
43. The ranking info, returned only when `getRankingInfo` is on, carries a value per criterion for that hit: the typo count, the first matched word, the proximity distance, the user score, the geo distance and precision, the exact-word count, the words count, the filters score, whether the hit was promoted, and the matched geo location. It is recorded by the ranker while it compares, not reconstructed afterwards, because it is the only way an operator can answer why one hit is above another.

### The customers index

44. `/customers` is a faceted index of `24` seeded customer stories in the `customer_stories` index, and it is the route where a visitor can check the counting contract in ten seconds. It carries one large search field with the placeholder `Search for a customer story`, then five facet controls in a row, then a card grid.
45. All five facet groups are multi-select: `Features`, `Use Case`, `Industry`, `Region` and `Integration`. Ticking two industries and one region must leave the counts on the other three groups truthful and must leave the industry group still offering the industries not yet picked, which is rule 27 on this route. ### Ingestion, tasks and reindex

55. A write batch carries a list of operations and is **not** a transaction. Operations are applied in array order, each individually accepted or rejected, and the response carries a per-operation result with a null at the position of a rejected operation. A batch of `1000` records with one record over the size limit applies `999` and reports one null. Rolling the whole batch back on one bad record silently loses the other `999`; reporting success with no per-operation detail leaves the caller unable to tell which one failed.
56. The legal actions differ from each other in exactly defined ways. `addObject` creates, and creates a second object with a new server-assigned `objectID` when one already exists. `updateObject` replaces every attribute, and the operation reports not found when the object is absent while the batch continues. `partialUpdateObject` merges and reports not found when absent. `partialUpdateObjectNoCreate` merges and is a no-op rather than an error when absent. `deleteObject` deletes and is a no-op when absent. `clear` empties the index and keeps its settings, synonyms and rules.
57. `partialUpdateObject` merges at the **top level only**: an object value in the body replaces the whole nested object rather than deep merging. The conditional operators are `Increment`, `Decrement`, `IncrementFrom`, `IncrementSet`, `Add`, `Remove` and `AddUnique`. `Increment` and `Decrement` treat a missing attribute as zero and reject a non-numeric one. `IncrementFrom` applies only when the attribute already equals the supplied value and then results in that value plus one; applied twice from `4`, the second attempt is rejected as a condition that was not met and the value stays `5`. `IncrementSet` applies only when the supplied value is greater than the stored one, so `IncrementSet` of `7` followed by `IncrementSet` of `6` leaves `7`. `Add` appends, `AddUnique` appends unless already present, `Remove` removes every equal element, and all three create a one-element list on a missing attribute and reject a non-list one. `IncrementFrom` and `IncrementSet` exist so that a retry is safe: a counter moved with `Increment` and retried after a timeout moves twice.
58. Every mutating request returns a `taskID` that is monotonically increasing **per index** and is not comparable across indices, so a cross-index task list sorted by `taskID` is sorted by noise. Tasks on one index are applied in `taskID` order. Asking for a task reports it published once it is visible to every reader, and not published otherwise; a failed task reports published for the queue and carries its error on the task itself. Waiting means polling with backoff from `100` milliseconds, doubling, capped at `5` seconds and giving up at `300` seconds; there is no long wait and no callback.
59. A full rebuild is done beside the live index and swapped in one motion. The temporary index inherits **nothing**, so settings, synonyms and rules are copied onto it explicitly before the records are written; a build that assumes inheritance ships a reindex that quietly resets relevance configuration and the symptom appears as search getting worse overnight with no change to blame. The move is atomic with respect to readers: a query in flight finishes against the old generation, a query arriving after the swap binds to the new one, and no query ever sees a mixture. The move destroys the destination index including its settings, synonyms and rules, and the source name does not exist afterwards. Replicas survive the move and are rebuilt from the new generation, keeping their own settings.
60. **Deletion and reclamation.** Deleting an object marks it dead in the current generation and queries filter the dead after retrieval and before ranking. Compaction runs when the dead exceed a fifth of the generation or on an explicit request. The record count excludes a deleted record from the moment its delete task publishes, so the count the console shows and the count a cursor walk returns agree. A delete by filter is a query followed by a delete, is not atomic, and says so: records matching the filter that are written while it runs may survive it, so it is never presented as a way to guarantee an empty index. Clearing the index is that guarantee.
61. Every mutating request accepts an idempotency key of `16` to `128` characters, stored with the workspace, the path, a digest of the body and the response, for `24` hours. The same key with the same path and the same body digest inside the window returns the stored response verbatim, including the original `taskID`, marks the response as a replay, and enqueues nothing. The same key with a different body digest, or with a different path, is rejected as invalid and the second body is never applied. A key whose first request is still in flight holds the second for up to `5` seconds and then reports a conflict. A mutating request with no key is allowed and is then at-least-once.
62. A record over `100` kilobytes serialized is rejected and its batch operation with it. A batch over `1000` operations or `10` megabytes is rejected. A query longer than `512` characters is truncated at `512` and the response says the query was truncated. Words past the tenth are optional. Facet values returned are capped at `maxValuesPerFacet`, itself capped at `1000`, and truncation sets `exhaustiveFacetsCount` to false. Attribute nesting deeper than `6` and more than `100` distinct facet attributes per index are both rejected as invalid. Every one of these is enforced at the front door and never discovered downstream.

### Merchandising: synonyms, rules, personalization and tests

63. Synonyms come in five types. `multiWay` expands any one of a list to all of them. `oneWay` makes an input also match its replacements and never the reverse. `altCorrection1` and `altCorrection2` match with one or two typos already spent. `placeholder` lets a token in a record stand for any value of a named placeholder. A multi-word synonym expands into a phrase and not into loose words, so `bike` expanding to `mountain bike` matches only records carrying the two words adjacent. Expansion happens after tokenization and before retrieval, so a synonym is itself typo-tolerant unless it came from an alternative correction, which has already spent its budget. Synonyms are per index and are not carried by a move unless copied explicitly.
64. A query rule is a condition and a consequence, and the evaluation is exact. Collect every enabled rule whose validity window contains the request time and whose context matches. Evaluate conditions against the **parsed** query, after tokenization, and against synonym expansions of it when the rule allows alternatives. Anchoring is `is` for the whole query, `startsWith` and `endsWith` at the ends and `contains` anywhere, and a facet-capture pattern captures a token that is a value of that facet and hands it to the consequence. Sort the matching rules by priority ascending then identifier ascending. Merge consequences in that order, with a later rule overwriting an earlier one on the same parameter, promote lists concatenating, and a repeated object keeping its first and therefore highest-priority position. Apply hides last.
65. **A hide beats a promote.** A rule promoting an object to position zero for the query `sofa` puts it first; adding a rule that hides the same object removes it entirely, because a merchandiser removing something must not be overridden by a merchandiser boosting something. Two promotions to the same position resolve by rule order and the loser takes the next free position. Promotion positions are zero based against the final list **after** deduplication and are honoured on the first page only; a promotion to a position beyond the page size is dropped and reported in the applied rules as not applied, rather than silently ignored. **A filter always beats a promotion:** a rule cannot promote a record the filter removed.
66. A personalization profile maps a facet value to an affinity between zero and one, built from interaction events with a view weighted `1`, a click `3` and a conversion `10`, decayed by half every `30` days by default. At query time the boost enters the cascade as a term of the `filters` criterion, never as a multiplier on a final score and never above the `typo`, `words` or `proximity` criteria. That placement is the whole design: personalization may reorder equally relevant results and may not promote a worse match. A visitor who prefers one brand and searches for another must still see the exact match of what they typed above a typo-match of what they like. `personalizationImpact` runs from `0` to `100` with a default of `100`, and at `0` the feature is inert but still logs.
67. An A/B test carries a control index, a challenger, a traffic split from `1` to `99`, and a window. Assignment is deterministic: a stable hash of the test identifier and the user token modulo one hundred, compared against the split. The same user token gets the same variant for the whole test, across devices and processes; a random assignment per request destroys the test while producing plausible numbers. A request with no user token is **not** assigned: it runs the control and is excluded from the analysis. The variant identifier is returned in the response and stamped on the query event, and every interaction event carrying that query identity inherits it rather than re-deriving it at analysis time, because the split may have been edited since. Stopping a test freezes assignment and deletes no events.
68. Precedence, when several controls speak at once, is strict: rules change the query and its parameters before retrieval; synonyms expand the query before retrieval; filters and exclusions remove records and are never overridden; the eight-criterion cascade orders what is left; personalization contributes inside the `filters` criterion; rule promotions move records to fixed positions; rule hides remove records; deduplication collapses groups with promotions exempt.

### Hybrid retrieval and the grounded answer

69. Every record in an index with vector search enabled carries a vector the app computes itself from a template over the record's attributes. The dimension is fixed at index creation, between `256` and `1536`, and is immutable afterwards. Vectors are stored normalized so that similarity is a dot product. Each vector is stamped with the identity of the model that produced it, and a query may not mix models: if any candidate carries a different identity from the index's current one, the response reports the vector index as stale and falls back to keyword-only results. Changing the model creates a new generation and re-embeds rather than rewriting in place. Vectors from two models are not comparable and produce an ordering that looks plausible and is arbitrary.
70. Nearest-neighbour retrieval walks a graph whose parameters are exposed rather than buried: neighbours per node default `16`, build-time breadth default `200`, query breadth default `64` and raisable per query to `512`, and a fixed seed per index so a build is reproducible. **Filters are applied during the walk, not after it.** Retrieving a hundred neighbours and then discarding those that fail a selective filter returns three results for a query that has thousands, and the interface then reports three. The walk consults the filter at each candidate and continues until enough surviving candidates are found or the graph is exhausted.
71. The two ranked lists are combined by reciprocal rank fusion over **ranks**, never over scores: each document scores the keyword weight over a constant plus its keyword rank, plus the vector weight over the same constant plus its vector rank, with the constant at `60`, both weights defaulting to `1.0`, ranks one based, and a document absent from a list contributing nothing for that list. Normalizing the two onto a common range is the obvious move and is wrong, because the keyword side has no score to normalize and any score invented for it will not respect the cascade of rule 11.
72. Two guarantees sit on top of fusion. A record that matched every query word exactly, in the sense of rule 16, may not be ranked below position ten by fusion; if fusion places it lower it is lifted to position ten and the response records that a lift was applied. This is what stops the meaning-based side burying a literal match for a product code. And `semanticRatio` at `0` must be exactly keyword search, identical to the same query with vector search disabled, while `1` must be exactly vector search: if the endpoints are not exact, nobody can debug the middle.
73. The conversational mode runs an answer pipeline whose every stage is observable in the response. Retrieve by hybrid search, eight hits by default, honouring every filter and every key restriction. Ground the answer on the retrieved records only, using the attributes named for that purpose: nothing outside the retrieved records enters it, no index-wide summary and no memory of earlier questions beyond the supplied history. Compose the answer from the grounding text with inline citation markers of the form `[n]` referring to the nth retrieved record. **Verify, and this stage is not optional:** reject the answer and fall back to the plain result list when a citation marker refers to a record that was not retrieved, when the answer contains a number that appears in no retrieved record, or when every sentence is uncited. Return the answer, the citations mapped to their `objectID`, the retrieved hits and a confidence between zero and one.
74. The results are sent before the answer begins, so the interface renders the hit list while the answer is still being written, and the citation for a marker may arrive before the marker's own text. A visitor navigating away mid-answer stops the answer within `200` milliseconds and the query event is still written. Record text enters the grounding inside a delimited block and instructions found inside record text are never followed. Attributes named as redacted are stripped before grounding and may not appear in an answer. An answer caches on the index generation, the normalized query, the filters, a digest of the key's restriction and the model identity, for `15` minutes, and a cache hit says so. **The key restriction digest is part of that cache key**: two visitors of one workspace holding different row restrictions must not share a cached answer.

### Keys, secured keys and quotas

75. There are three stored key kinds and one derived one. An `admin` key does everything including creating keys, and never leaves the server, never appears in a browser and is never logged. An `ingest` key writes records and settings and can neither search nor read analytics. A `search` key searches, and browses when granted, and writes nothing. A secured key is derived from a `search` key at run time, on the caller's own server, and can only search within the restrictions embedded in it. Secrets are stored hashed. **A key value is shown once at creation and never again**, in a panel that must be dismissed deliberately; there is no reveal control, and its absence is the specification.
76. The seeded application `kestrel-web` carries a `search` key with the identifier `key_site_search` and the value `sk_site_1f6b2d8e4a`, whose access list is `search` and whose index patterns are `site_content` and `customer_stories`; a `search` key with the identifier `key_story_search` and the value `sk_story_3c9a7e51b2`, scoped to `customer_stories` alone; and an `ingest` key with the identifier `key_ingest_demo` and the value `ik_demo_74d2c0a9f1`, whose access list carries `addObject`, `deleteObject` and `settings` and whose pattern is `*`. `key_story_search` requesting `site_content` is refused, and the refusal is worded identically to a refusal for an index that does not exist.
77. A secured key embeds restrictions its holder cannot alter. It is built in exactly this order: the restrictions are the query string, url-encoded, with parameters sorted by name ascending and joined with `&`, for example `filters=industry%3AEcommerce&userToken=u_1029&validUntil=1767225600`; the signature is the hexadecimal HMAC-SHA256 of that encoded string under the parent search key; and the secured key is the base64 of the signature followed by the restriction string, **signature first**. Signing the parameters before encoding them, or concatenating in the other order, both fail identically at the server and send the debugging in the wrong direction.
78. Validating a secured key: decode the base64, read the first `64` characters as the signature and the rest as the restriction string, recompute the HMAC over the restriction string with **every** active parent search key of the application and accept if any matches, which is what lets a parent key be rotated without invalidating live sessions; refuse when `validUntil` has passed. **Then merge, and this step is the whole security property: the `filters` carried by the key is combined with the request's own filters by conjunction, never replaced and never combined by disjunction**, the key's index restriction is intersected with the requested index, and a `userToken` in the key overrides any in the request so a visitor may not choose their own personalization identity. A build that lets the request's filters replace the key's has built a system where every restriction is advisory, every row of every customer is readable by any of them, and no test fails. A secured key restricted to `industry:Ecommerce` and a request asking for `industry:Media` therefore returns zero hits and never Media's hits.
79. The authorization decision runs in one order, and the first failure decides: the key must be present and parseable; a secured key's signature must be valid; the key must not be expired; the referer must match when the key restricts referers; the action must be in the access list; the index must match the key's patterns; the rate limit and the quota must allow it; then the request-level limits of rule 62 apply. A refusal for an index outside the key's patterns must not be distinguishable from a refusal for an index that does not exist, because the difference is an enumeration oracle. Not-found is only correct once the key is known to be allowed to see the index.
80. Two independent limits exist and conflating them produces a system that either refuses a paying customer's burst or lets one customer consume a month of capacity in an afternoon. The rate limit is a per-key bucket with a capacity of `100` requests refilled continuously at `10` requests per second, costing `1` for a search, `5` for a batch write and `20` for starting an answer. Refill is continuous and computed from elapsed time on each request: a fixed window that resets on the second boundary allows twice the burst across that boundary. The quota is per workspace per calendar month in UTC, counting one search unit per search request or facet-value search, one record unit per stored record sampled hourly and billed on the maximum, and one answer unit per thousand generated tokens rounded up per request. At `80` percent of quota responses carry a quota warning header. **At `100` percent search continues and writes are refused**, because cutting search off takes the customer's storefront down while pausing writes degrades gracefully. Any refusal for rate or quota carries a retry hint in whole seconds; a refusal without one turns a graceful queue into a stampede.
81. Every write, every key creation, every settings change and every rule change writes an audit record carrying the acting key identifier, the action, the index, a digest of the before and after, the request identifier and the timestamp. Audit records are append-only, are readable only with an admin key, and are retained for the workspace's retention window with a floor of `90` days on every plan.

### Events, analytics and the metrics contract

82. Event intake accepts `click`, `conversion` and `view` events and is fire and forget from the client's point of view: it answers success even when individual events are dropped, and reports the count accepted, because this call is made from a page during navigation and a client that retries on failure will double count far more often than it will recover a lost event. An event is dropped when its timestamp is more than `4` days old, counted as stale; when a click carries a query identity but no positions, counted as malformed; when it names more than `20` objects; when it carries no user token; or when its index is unknown. A timestamp more than one hour in the future is clamped to the receipt time rather than dropped.
83. A click or a conversion carrying a query identity is **attributed** to that search; without one it is counted and unattributed, and the two are never mixed in one figure. The attribution window is `24` hours from the query event, extended to `30` days for a conversion carrying an authenticated user token, because a purchase a week later on another device is still that search's doing.
84. Two events sharing a user token, an event type, an object, a query identity and the same whole minute are one event. Exact-timestamp deduplication catches nothing, because the two fires of a double-firing client differ by a millisecond. An event arriving after its hour has been rolled up triggers a **recomputation** of that hour, up to `4` days back. Rollups are idempotent recomputations from the raw events and never incremented counters: an incremental counter cannot absorb a late event and cannot be repaired after a bad deploy without replaying anyway.
85. Rollups are computed per index per hour in UTC into five tables: searches by hour with the count, the users, the no-result count and the processing-time average and ninety-fifth percentile; queries by hour and normalized query with the count, users, clicks, conversions and no-result rate; hits by hour and object with impressions, clicks, conversions and summed position; filters by hour, facet and value with the count; and variants by hour, test and variant with searches, users, clicks, conversions and revenue. Hour boundaries are UTC and the console converts for display, because rolling up in the viewer's timezone means two viewers of one account see different totals.
86. The metric definitions are exact, because every one of them has a plausible wrong version. Click-through rate is attributed clicks divided by **searches that returned at least one hit**, not by all searches. Conversion rate uses the same denominator. No-results rate is searches with zero hits divided by all searches, including those a rule rewrote. Average click position is the mean of the reported positions over attributed clicks only, one based. Users is the distinct count of user tokens in the period and is **not** the sum of the sub-periods: distinct counts do not add, so a daily figure is computed by merging the sketches rather than by summing the hourly figures, and every distinct count is marked approximate in the figure itself rather than in a footnote.

### The console

87. `/console` is the signed-in operator surface, behind the same visual system as the marketing routes at a higher information density. It opens on an application picker and redirects straight through when the account has exactly one application. A left rail carries the application switcher and eleven destinations: the index list, a record browser and its `configure`, `rules`, `synonyms` and `preview` tabs, analytics, A/B tests, keys, tasks and members. The top bar carries an index switcher that is itself a search over index names using the product's own engine, because a customer with four hundred indices has the same problem the product solves.
88. **Every console screen that reads data shows, in one fixed position, the generation it read and the age of that read.** With the read path asynchronous, a stale screen is a normal state, and a console that hides it produces bug reports about writes that did not happen and actually did.
89. The record browser walks the index with a forward-only cursor rather than searching it, so the operator can reach the record past the pagination cap that a search cannot return. It offers a visible way to start over, operator-chosen attribute columns persisted per index per member, an inline edit that writes a partial update and shows and polls the returned `taskID`, a delete that requires typing the `objectID` because there is no undo, and a read-only raw view with a copy control. **A value edited inline and saved is the persisted value**: the row the table shows after the task publishes, the row a fresh page load shows, and the row the search returns all carry the new value, and reloading the browser does not bring the old one back. The table renders `200` rows without stalling and does not re-request a page it has already fetched when the operator scrolls back.
90. The search preview is where relevance is judged. Three panes. Left, the query: a search box, a filter builder that emits the nested array form of rule 32 and renders it back as prose such as `brand is Acme or Zeta, and colour is red`, and the parameter overrides. Centre, the results as the customer's own interface would receive them, each with its position number, its highlight tags rendered, and a disclosure carrying its ranking info. Right, every attribute in `attributesForFaceting`, each with a toggle between conjunctive and disjunctive counting so the operator can see the difference rather than read about it.
91. **The per-hit disclosure is the point of the preview.** It shows the eight criteria of rule 11 as one row per criterion, with the value for this hit and the value for the hit above it, and marks the criterion where the two first differed. Opening the disclosure on `r3` in the fixture query of rule 12 names the criterion that separated it from `r1`. That single row answers why one hit is above another, which is otherwise unanswerable and is the most common question a customer asks in its first week.
92. The preview also turns `getRankingInfo` on by default here and off everywhere else, renders the degradation flags of rule 99 as a visible banner rather than as a field in a payload, lists the rules applied to this query each linking to its editor, and offers a comparison mode that runs one query against two sets of settings side by side with the ordering differences highlighted. Without that comparison, every relevance change is a deploy and a hope.
93. The merchandising editor is a visual editor over the query rules of rule 64. The operator types a query, sees live results from the preview engine, and drags a result to a position. **Dragging writes a rule and not a separate pinning object**, so one mechanism, one precedence order and one audit trail: dragging a hit to position `n` writes a promote for that object at that position, hiding a hit writes a hide, adding a banner writes user data on the consequence, and boosting a category for a query writes an optional filter. Above the results the editor shows the precedence list of rule 68 with the steps active for this query highlighted, so an operator whose promotion is being overridden by a filter can see why. Rules carry a validity window and the editor defaults to starting now with no end while keeping the seasonal case one control away.
94. The analytics screens read **only** the rollup tables and never the raw events: a screen that queries raw events is fast on a demonstration account and unusable on a real one, and the difference does not appear until after launch. There are four: an overview of searches, users, click-through rate and no-results rate over a date range, with the denominators of rule 86 stated on the screen beside each figure; top searches by normalized query with count, click-through rate, average click position and no-results rate, and the raw variants behind a disclosure; a no-results screen listing queries that returned nothing, each with a control that opens the rule editor pre-filled; and a results insight screen of impressions, clicks, conversions and mean position per object, joining to the record browser. Date ranges are inclusive of both ends and are labelled with the timezone.
95. The keys screen writes the access list, the index patterns, the optional expiry and the optional query restrictions, and shows the value once per rule 75. It also carries the secured-key derivation of rule 77 as a worked example generated live from the parent key selected, showing the resulting string and the exact steps that produced it, because every customer implements this and most implement it wrong the first time. The members screen renders the role matrix of `## User roles` and enforces it on the server. The tasks screen lists the write queue per index with the task identifier, the kind, the status, the accept time and the publish time, and shows a failed task's error and the operation that caused it, so that "my update has not appeared" has an answer that is not a support request.
96. Five things the console must never do, each stated as a prohibition because each has a tempting shortcut. It never waits synchronously for a task inside a form submission; it shows the task and polls it, because a synchronous wait turns a forty-millisecond write into a two-second one. It never queries raw events for a screen. It never searches where a cursor walk is specified. It never stores an admin key in the browser: the console's own session is not an application key and must not be one. And it never shows a figure derived from a sketch without marking it approximate.

### The site's remaining obligations

97. A privacy page at `/privacy`, reachable from the footer of every route that has one and from the not-found route, states plainly what Kestrel records about a visitor: the demo request fields, the newsletter address, the cookie answer, and the search queries and clicks that feed the analytics rollups, together with how long each is kept. It is an ordinary route with its own title and its own description.
98. A band above the footer puts the non-essential-cookie question to a first-time visitor once. Whichever way the visitor answers, the answer is remembered: a reload shows no band, and neither does any later route in the same session. Refusing is as easy as accepting: the refuse control sits beside the accept control at the same size and takes one press, so neither answer is cheaper to give than the other. This app stores the answer itself and loads no consent vendor to ask the question for it.
99. Every public route carries its own title and its own description, and no two routes share either. The service degrades under load in a fixed order, and **every degradation is flagged in the response**: answer generation is shed first because it has a result-list fallback, then personalization because it is a reordering rather than a result set, then disjunctive facet counting which degrades to conjunctive and says so, then vector retrieval which falls back to keyword and says so; keyword search is never shed. A silent degradation is worse than an error, because a customer then tunes relevance against results that were never the real ones.
100. An unmatched path renders the product's own not-found route and answers not found, never a success: a soft not-found is invisible to everyone except a crawler. The route carries the numeral `404` with the brand mark standing in for the zero, the heading `Page not found`, a field labelled `Search Kestrel` that opens the overlay, and three ways out, each with the circle-arrow glyph: `API Status`, `Home page` and `Support`.

## UI/UX notes

**North star.** Somebody arriving should understand within one screen that the box at the top of the page is the product running, not a picture of it.

**Register.** One product with two registers, and the surface decides which is in force. A marketing route is consumer-facing, may carry atmosphere, and shows the subject before the frame. The console is an instrument: an operator arrives to scan a table, judge an ordering and repeat an action, so it stays plain, packs more into a screen than a marketing band would, and reaches for no hero and no editorial layout. Where a marketing surface meets an operating one, being understood wins over being admired.

**Two grounds, hard edges.** The page alternates between dark and light bands rather than gradating between them, so the boundary between two bands is a hard horizontal edge across the full width. The dark ground is a near-black, muted blue carrying display type in a near-white neutral; the light ground is a near-white neutral, with a second, fractionally greyer near-white neutral for the alternating band and body copy in a deep cool neutral. A band is one or the other and never half-committed, and the change always happens at a band boundary. Hard edges over gradients: this product is a sequence of arguments, and a fade between two of them reads as one long argument.

**Colour by role, and by exclusivity.** One accent does nearly all the work. A mid, vivid blue is the primary button fill, the link colour, the eyebrow label and every hover target on both grounds: the resting colour of a navigation item changes with the route and the hover colour never does, which is the small thing that makes the site feel like one site. A light, vivid blue is the secondary fill and the start of every gradient. A second mid, vivid blue one step deeper is the pressed state. A near-white, muted blue is the selected-row tint on light surfaces and appears nowhere else. A mid, muted blue is the secondary text colour on light and the divider on dark; a near-white cool neutral is the border and divider on dark; a near-white neutral hairline rules the light surfaces, and that hairline exists twice in the reference, once in the plain grey ramp and once in the cooler grey ramp, which is two authors rather than a distinction: pick one and hold it. One mid, vivid green appears in exactly one gradient and nowhere else. The yellow behind matched words in the search overlay is the only yellow in the product and has no substitute, because nothing else in the palette does that job. Two contrast substitutions are contract rather than taste, because the reference carries text on both and should not: the light, vivid blue clears the bar for large text and for non-text use only and never carries body copy, and the light cool neutral placeholder grey is replaced by the mid, muted blue wherever it would carry text, while the light neutral hairline grey rules lines only and never sets text. Failure, success and work-in-progress each own one colour, each of those three colours is reserved to its meaning, and a state outside the three borrows from none of them: a rate refusal, an out-of-scope key and a stale generation marker all read in the neutral ramp. Which shade sits behind each of those roles is yours to pick, so long as the exclusivity holds.

**What this must not turn into.** A build that reaches for the nearest default produces four things this product cannot ship. A wall of one blue with nothing else carrying signal, so a failed field and a promoted hit read alike. An ornament sitting where a count, a hit or a row belongs. A landing-page composition wrapped around the record browser, which is a table, or around the preview, which is three panes. And an entrance choreography, which the motion paragraph forbids on measured grounds rather than on taste.

**Typography.** Two families with a strict division of labour, both named rather than shipped, each behind a fallback stack chosen so the swap does not shift the layout. `Sora` carries display headings and the large statistics: `"Sora", "Trebuchet MS", "Segoe UI", system-ui, sans-serif`. `Inter` carries everything else: `"Inter", "Helvetica Neue", Arial, system-ui, sans-serif`. A third family declared in the reference stylesheets was never rendered and is not loaded.

The scale is one overwhelming body size and a very short ladder above it, and that gap is the whole typographic argument: ordinary, ordinary, ordinary, then enormous. Body and nearly everything is `16px` over a `24px` line at weight 400. Small bold labels, navigation and table headers are `14px` over `16px` at weight 700. Body in tighter components is `16px` over `19.2px`; fine print is `13px` over `24px`; secondary body is `14px` over `20px`; body in dense lists is `16px` over `18px`; bold body is `16px` over `24px` at weight 700; captions are `12px` over `16px`; the smallest all-caps label is `10px` over `13px` at weight 700; button text is `14px` over `20px` at weight 600. Lead paragraphs are `20px` over `28px` and section subheadings `24px` over `32px`. The display heading is `76px` over a `76px` line at weight 700, a line height of exactly one. The not-found heading is `45px` rising to `56px` on a wide screen at a line-height factor of `1.2`. Three fractional steps, `14.4px`, `12.992px` and `13.6px`, belong to one component that scales its own root by a factor: reproduce the factor, not the fraction. No tracking is declared anywhere; the apparent tracking on the smallest all-caps label is a consequence of its weight. Figures line up in a column wherever amounts or counts stack, so a facet list and a comparison grid both scan straight down.

**Shape.** Corners are barely softened nearly everywhere and a step more on cards and large buttons, with navigation panels between the two. Four shapes are fully rounded and nothing else is: the header search field, the plan chooser, the filter pills and the small status markers. Circular icon buttons are true circles and are square by construction, so the two ways of writing a circle are not interchangeable on anything else.

**Density and space.** Comfortable on the marketing routes, compact in the console, where rows sit tight enough that a full page of records fits one screen without the operator scrolling to learn how many there are. Space over dividers on the marketing routes: two bands read as separate at a glance because of the hard ground change and the space around them, not because a rule was drawn. Dividers over space in the console, where a table needs its columns separated and a merchandiser is scanning rather than reading.

**Elevation and layering.** There is no elevation ladder and there must not be one. Each shadow belongs to one component and is quoted by that component: a wide, soft band under the header once it is stuck to the top of the page; a two-step lift under a navigation panel; a brand-tinted glow and a one-pixel blue text shadow on the demo request submit. Anything else sits flat on its ground. Flat over floating: this is a document with a working instrument in it, and a page of floating cards reads as neither. The layering ladder is small and fixed, in this order from the bottom: the page in normal flow, in-flow overlaps inside a card, hover and focus lifts, the sticky table header row, a section overlay, the promotion bar, the header, a navigation panel, the search overlay, and the consent band. Nothing invents a new layer to win a fight, and no layer this build owns reaches for the top of the integer range the way an embedded third-party surface does.

**Gradients.** Gradients are a signature and appear only where they are named, never as a general fill. The primary button carries a two-stop diagonal from the light, vivid blue to the mid, vivid blue, at one angle on light grounds and another on dark; a third blue sits between those two as the midpoint wherever a three-stop wash is called for. The large statistics on the demo request route are filled with a left-to-right wash from the light, vivid blue to a near-white, muted blue, clipped to the type, and that is the only place in the product where type is filled with a gradient rather than a colour. A divider on a dark ground runs dark at both ends and lighter in the middle, so it fades out at both edges rather than ending abruptly. The pricing hero sweeps violet-leaning at one edge to teal-leaning at the other over the dark ground; the demo request ground sweeps violet to blue with a soft magenta bloom about a third of the way across. The not-found heading is filled with a radial wash from a mid blue to a deeper blue and carries two stacked drop shadows, one very large and soft and one tight beneath it, so the type sits above the ground rather than on it; it is the only type in the product given depth, which is a good thing to do on the one page nobody meant to visit.

**Motion, and the far more important absence of it.** Motion here is incidental rather than continuous, and the single most important statement in this section is a negative: **there is no scroll-scrubbed motion and there are no scroll-triggered reveals anywhere in this product.** Content is present and static, and a visitor moves down it. Nothing fades up as it is reached, nothing slides in, no ground changes colour as the page passes it. Building it with entrance reveals produces a different and slower product. Presence over arrival.

What does move, moves for one of three reasons and there is no fourth: a declared transition on a state change, a keyframe loop, or a timer. Everything that changes on hover changes colour only, with two named exceptions. The named moments are these, and only these. The promotion bar cycles: a message rises into place from just below while fading in, sits, then rises out of the top while fading away, each half a little under a second, both halves easing in and out, opacity and position moving together, and the fill carried backwards so a waiting slide holds its starting values rather than flashing its end state; it is the only motion a visitor sees without acting. The statistics column loops upward forever, holding two copies of its content in one track and translating by exactly half its own height, linear and infinite, so that at the moment it restarts the second copy sits precisely where the first began and the seam never shows; two columns of different lengths run at the same pixel speed and therefore for different durations, so the speed is what is reproduced and never the duration, and the column's top edge is faded out by a mask. The customer marquee rows do the same thing on the horizontal axis, two rows offset from each other by about half a card, drifting in opposite directions, pausing on hover and on focus within, moving by position only and never trapping a scroll gesture. The hero carousel advances on a timer and says so: a bar fills left to right inside the active dot, as a transform on a child rather than as a width, so it stays smooth. The circle-arrow affordance grows slightly and changes fill when it is pointed at. The demo request submit grows by a whisper and swaps its flat fill for a translucent four-stop wash, and both halves are needed: the growth alone reads as a bug and the wash alone reads as an ordinary hover. A caret blinks beside the rotating placeholder in the search field, which makes the field read as a prompt rather than as a box. A spinner turns while a query is in flight. A progress bar fills toward, and deliberately stops short of, its end while work continues, and one control widens in a short width pulse where attention is wanted. The focus ring animates by expanding its own box-shadow, and that emphasis is reserved for focus and is used nowhere else.

Everything that animates shares one character and one speed; nothing uses a different one to feel special, and the exact durations and curves are yours so long as that holds. Every declared transition names the properties it means, and no property that changes layout is animated: declaring that everything transitions is a habit rather than a decision and is the usual reason a control quietly grows when it is pointed at.

Under a reduced-motion preference the promotion bar stops cycling and shows one message, the statistics column and the marquee rows stop and show their first screenful, the hero stops advancing while its dots stay operable, hover transforms are removed while hover colour changes remain, and the spinner becomes a static glyph with a text alternative. Nothing that conveys information is removed, only its motion, and nothing auto-advances at all.

**Accessibility floors, which are contract rather than taste.** Each route has one banner, one navigation inside the header, one main and one contentinfo, exactly one first-level heading, and heading levels that descend without skipping. A skip control is the first focusable element on every route, is visible on focus, and moves focus to main, or to the working pane in the console rather than to the left rail, which is the same on every screen. Body text meets a contrast ratio of 4.5 to 1 against its own background, large text 3 to 1, and the boundary of every interface component 3 to 1, and that holds on the dark ground and the light ground alike. Every interactive element is reachable and operable by keyboard navigation in the order it appears visually, with a visible focus ring that is restyled and never removed, drawn so that one ring works on both grounds, and containers scroll a focused element into view. Route changes move focus to the new route's first-level heading. Every icon-only control carries its purpose as a text label, naming the job rather than the shape. Touch targets are comfortably sized, no smaller than 44 by 44 pixels including padding. No information is carried by colour alone: the comparison grid pairs its colour with a distinct present marker and a distinct absent marker, a console status pill carries its word as well as its fill, and a failing field carries its message as well as its border. Every content image carries alternative text describing what it shows and a decorative one declares itself decorative; a customer card's alternative text is the customer's name, and the hero product panels carry a description of what the panel demonstrates, because the panel is the argument.

**Responsive.** The arrangement holds at every width between the named tiers, not only at them, and every component is checked at the awkward width between the two thresholds where one family of components is written from the wide end and another from the narrow end and a component can be styled by neither. On a wide screen the header carries the mark and the wordmark, five primary items, the search field, a secondary button and a primary button. Below the desktop threshold the centre and right groups collapse to the mark, a menu control and a circular search control, and the panel that opens is a full-height drawer with the primary items as an accordion, the utility items stacked and the two buttons at full width. The hero's two columns stack with the heading centred and the panel below the button; the capability accordion moves below its media pane; the five solution cards become two rows and then one column; the four plan cards become two rows and then one column with the emphasized plan first; the story cards go three, two, one; the five facet controls go five, then three and two, then a single control opening a full-height sheet dismissible by a downward drag as well as by a button. **At a narrow viewport nothing overflows sideways and every navigation target stays reachable.** The comparison grid is the hardest of these and is specified rather than left open: at and above the desktop threshold it is the full four-column grid with its header row staying visible; below it, it becomes one plan at a time behind a segmented control, with the feature column and one value column shown, the category rail becoming a horizontally scrolling strip, and the selected plan held in the address bar. A horizontally scrolling four-column table is acceptable at tablet width, where the columns still fit, and is not acceptable on a phone, where a cell is narrower than its own marker plus its padding. Where the breakpoints sit is yours; the behaviour at each is not.

**Mode.** One committed mode, light-first, carrying two grounds inside it: the dark bands are a designed surface of that mode rather than a second theme. A separate dark theme is not owed here, and a build that half-delivers one leaves both looking unfinished, which is worse than shipping the committed mode alone.

**Control states.** Resting, pointed-at, pressed, focused and unavailable: a control carries all five, and the unavailable one is legible without reading its colour, because a merchandiser scanning a rule editor should not have to. Escape closes the search overlay, the navigation panels, the mobile drawer and the console slide-over, returning focus to the trigger each time. A destructive action confirms first, and deleting a record asks for its identifier rather than for a confirmation click, because there is no undo.

## Technical requirements

Frontend: Astro, rendering every public route on the server and hydrating islands for the search overlay, the facet controls, the hero rotation, the capability accordion, the comparison grid and every console pane. The browser receives rendered HTML on first paint and the islands take over the parts that are interactive. Backend: Fastify, serving the HTTP API on that same origin under the `/api` prefix. Datastore: PostgreSQL, read from `DATABASE_URL`. Auth: this app's own email and password with bearer tokens for a console session, and this app's own API key system for every search and ingest call. Health: a readiness probe answers success at `/api/health` once the app can serve. Logging: standard output, one line per request.

Every host, every port and every credential arrives from the environment and none of them is written into the source. The backing service named in this brief, PostgreSQL, is already running and reachable at that environment variable; do not download, install, compile or start a copy of it.

Use only the libraries named here plus their direct dependencies. Do not introduce a second database, cache, queue, object store, identity provider or mail vendor - the only backing service available in this environment is PostgreSQL, and reaching for anything else is a contract violation.

**The engine is this application, not a service it calls.** There is no managed search product available in this environment and no network at run time. PostgreSQL holds the durable records, the settings, the synonyms, the rules, the keys, the tasks and the events. The index structures the query path reads are built by this application per generation and rebuilt from PostgreSQL on start.

**Capability requirement for the index structures.** A generation needs four things: a posting list per token carrying the documents, attributes and positions the token appears at; a term dictionary; a forward view of each document's attribute values for highlighting and faceting; and a per-value document set per facet attribute. The term dictionary must support exact lookup, a prefix range walk **and** traversal against an edit-distance automaton. A plain hash map satisfies the first and neither of the others, and a build that uses one will pass a small test corpus and then be unable to answer the prefix query that every keystroke in the interface depends on, or to expand a typo budget without scanning every term. The per-generation document identifier is a dense integer that is reassigned on every rebuild, so nothing outside a generation may store one.

**Generation binding.** Writes build immutable generations and a read binds to one generation for the whole life of a query. A query that begins against one generation finishes against it even when the next is published mid-flight, because facet counts, hit counts and pagination taken from two generations do not add up and the disagreement is invisible inside a single response. Every console screen shows the generation it read.

**Read-your-writes, without pretending.** A read may carry a minimum task identifier, and the query path either answers from a generation at or beyond that task or refuses with a retry hint of one second. It never serves older data silently in that case. The console uses the header on the screen immediately after a write and waits for a task nowhere in an interactive path.

**Vectors without a provider.** A record's vector is computed by this application from a template over the record's own attributes. No external model is called and none is available. What matters is unchanged by that: the dimension is fixed at index creation and immutable, the vector is stored normalized, the identity of the producing routine is stamped on each vector so a mixed index is detectable, and fusion combines the two ranked lists by their ranks.

**Answers without a provider.** The conversational mode composes its answer out of sentences drawn from the records it just retrieved, with the citation markers of the answer rule above. No external language model is called and none is available. The grounding limit, the citation markers, the verification that suppresses an answer whose claim traces to no retrieved record, and the fall back to the plain result list are all unchanged by that, and they are what the mode is judged on.

**Budgets, as observable requirements.** The search overlay shows its first result within a third of a second of opening and keeps up with typing, updating within a sixth of a second of a keystroke at the ninety-fifth percentile over the seeded corpus. A site that sells instant search and takes half a second to answer a keystroke has disproved its own headline in the header of every page. A search over the seeded corpora answers in under twenty milliseconds at the median measured at the service, with ranking info off. Largest contentful paint stays under two seconds, interaction to next paint under two hundred milliseconds, cumulative layout shift under 0.05 and total blocking time under two hundred milliseconds, on every route. First-party script stays under 120 kilobytes compressed per route and first-party style under 40 kilobytes.

**No third-party surface on the critical path, or anywhere.** The reference this product is modelled on spends nearly fourteen megabytes of images, six hundred tracking pixels and four hundred script files across six routes, and almost none of it is its own work: it is consent banners, chat widgets, analytics, tag managers and testing tools layered up over years. None of them exists here. The build ships no image at all, which removes the largest cost outright, and every remaining surface is first-party.

**Loading order, and it may not be reordered.** Markup, style and the two preloaded faces arrive first: `Sora` at weight 700 and `Inter` at weight 400 and nothing else. Then the route's own script for the chrome, the accordion and the carousel timer. The search overlay's code loads on the first focus of the search field and not on page load, because the field itself is markup and needs no script to render. Then, when the browser is idle, the marquee, the statistics loop and the remaining font weights. The consent band loads last of all, after everything above, because a consent surface loaded before the page is interactive is how a build with a small script budget ends up with a slow first paint.

**Observability.** Per request, record the request identifier, the workspace, the index, the key identifier, the generation, the timing of each stage of the read path, the candidate counts before and after each stage, and the honesty flags. The stage timings are not for a dashboard: they are the only way to answer why one query was slow, and the answer is nearly always a prefix expansion that reached its bound, a disjunctive facet pass over a large result set, or highlighting applied before pagination. All three are visible in the stage timings and invisible in a total.

**Client behaviour is part of the contract.** A caller retries on a connection failure, a timeout or a server error, and never on a client error other than a rate refusal, and never retries a mutating request without an idempotency key. It honours a retry hint exactly when one is given and otherwise backs off exponentially from two hundred milliseconds with full jitter, capped at ten seconds. Connect timeout two seconds, read timeout five seconds for a search and thirty for a write, and no read timeout while an answer is arriving.

**No secret reaches the browser.** No admin key, no ingest key, no database address and no session secret appears in anything the browser downloads: not in the served HTML, not in a script bundle, not in a JSON response. The only key the site's own overlay may carry is the seeded search-only key scoped to the two public indices, and that is what a search-only key is for.

## Data model

Nineteen tables. All timestamps are UTC.

**Every seeded account uses the password `deku-demo-pw-2026`.** It is benchmark fixture data, not a secret. Hash it as normal; the exact literal must work at login, and it must be written into `/app/USER_README.md` alongside each account so a grader can sign in.

`accounts` - `id` integer, `email` text unique and stored lowercase, `password_hash` text, `display_name` text, `created_at` timestamp.

`workspaces` - `id` integer, `slug` text unique, `name` text, `plan` text and one of `free`, `growth`, `premium` or `elite`, `quota_search_units` integer, `quota_records` integer, `retention_days` integer and one of `7`, `30`, `90` or `365`, `created_at` timestamp.

`memberships` - `id` integer, `account_id` referencing `accounts`, `workspace_id` referencing `workspaces`, `role` text and one of `owner`, `admin`, `operator` or `analyst`. At most one membership per account per workspace.

`applications` - `id` integer, `slug` text unique within its workspace, `workspace_id` referencing `workspaces`, `name` text, `regions` a non-empty ordered list of text.

`indices` - `id` integer, `application_id` referencing `applications`, `name` text unique within its application and case sensitive, `primary_index_id` nullable and set when this index is a replica, `replica_kind` nullable and one of `standard` or `virtual`, `generation` integer and monotonic, incremented on every publish, `record_count` integer, `created_at` timestamp.

`index_settings` - one row per index, holding `searchable_attributes`, `attributes_for_faceting`, `custom_ranking`, `ranking`, `attribute_for_distinct`, `distinct`, `typo_tolerance`, `min_word_size_for_1_typo`, `min_word_size_for_2_typos`, `allow_typos_on_numeric_tokens`, `disable_typo_tolerance_on_attributes`, `ignore_plurals`, `remove_stop_words`, `query_languages`, `advanced_syntax`, `optional_words`, `remove_words_if_no_results`, `exact_on_single_word_query`, `alternatives_as_exact`, `pagination_limited_to`, `hits_per_page`, `max_values_per_facet`, `sort_facet_values_by`, `attributes_to_highlight`, `attributes_to_snippet`, `highlight_pre_tag`, `highlight_post_tag`, `snippet_ellipsis_text`, `relevancy_strictness`, `numeric_attributes_for_filtering`, `decompounded_attributes` and `replicas`. The defaults are those stated in `## Core features`.

`records` - `id` integer, `index_id` referencing `indices`, `object_id` text and unique within its index, supplied by the caller or generated by the server, `attributes` a JSON map of arbitrary nesting up to six deep, `vector` a list of numbers, `vector_model_id` text, `version` integer incremented on every accepted write, `updated_at` timestamp.

`synonyms` - `id` text, `index_id` referencing `indices`, `type` text and one of `multiWay`, `oneWay`, `altCorrection1`, `altCorrection2` or `placeholder`, `synonyms` a list, `input` text, `replacements` a list, `corrections` a list, `placeholder` text.

`rules` - `id` text, `index_id` referencing `indices`, `enabled` boolean, `conditions` a list of anchoring, pattern, context, filters and an alternatives flag, `consequence` holding `params`, `promote`, `hide`, `user_data` and a filter-promotes flag, `validity` a list of from and until timestamps, `description` text, `priority` integer where lower runs first and ties break by `id` ascending.

`api_keys` - `id` text, `application_id` referencing `applications`, `kind` text and one of `admin`, `ingest` or `search`, `acl` a list, `indices` a list of glob patterns where `*` is legal, `valid_until` nullable timestamp, `max_hits_per_query` nullable integer, `max_queries_per_ip_per_hour` nullable integer, `referers` a list, `description` text, `hashed_secret` text.

`tasks` - `id` integer and monotonic **per index** and never per application, `index_id` referencing `indices`, `kind` text and one of `batch`, `settings`, `clear`, `move`, `copy` or `delete`, `status` text and one of `queued`, `processing`, `published` or `failed`, `accepted_at` timestamp, `published_at` nullable timestamp, `error` nullable text.

`query_events` - `query_id` text of thirty-two hexadecimal characters, `index_id`, `workspace_id`, `user_token` nullable text, `query` text, `filters` nullable text, `nb_hits` integer, `processing_time_ms` integer, `variant_id` nullable text, `rule_ids` a list, `personalized` boolean, `at` timestamp.

`interaction_events` - `id` integer, `type` text and one of `click`, `conversion` or `view`, `subtype` nullable and one of `addToCart` or `purchase`, `index_id`, `user_token` text, `authenticated_user_token` nullable text, `object_ids` a list of one to twenty, `positions` a list and required for a click carrying a query identity, `query_id` nullable text, `value` nullable number for a conversion, `currency` nullable text for a conversion, `at` timestamp, `received_at` timestamp.

`ab_tests` - `id` text, `index_id` the control, `variant_index_id` the challenger, `variant_params` a map, `traffic_split` integer from `1` to `99`, `start_at` timestamp, `end_at` timestamp, `status` text and one of `scheduled`, `running`, `stopped` or `expired`.

`personalization_profiles` - `user_token` text, `workspace_id`, `facet_scores` a map from a facet and value to a score between zero and one, `event_count` integer, `last_seen_at` timestamp.

`demo_requests` - `id` integer, `first_name` text, `last_name` text, `email` text, `phone` text, `company` text, `country` text, `status` text and one of `received`, `delivered` or `rejected`, `at` timestamp. Every one of the six value fields is required and none may be stored empty.

`newsletter_signups` - `id` integer, `email` text unique, `status` text, `at` timestamp.

`cookie_choices` - `id` integer, `visitor_token` text unique, `accepted` boolean, `decided_at` timestamp.

`idempotency_records` - `key` text, `workspace_id`, `path` text, `body_digest` text, `response` JSON, `at` timestamp. A row lives for twenty-four hours from its own acceptance.

**Invariants, stated as properties of the running system.**

A search result's ordering is total: two hits equal on all eight criteria are ordered by `object_id` ascending, so collecting every page returns each `object_id` exactly once and the same query repeated returns the same order.

A facet the caller is filtering on is counted with its own clause pruned from the filter tree and every other clause kept, and a currently selected value that matches nothing under the pruned tree is still returned with a count of zero.

Deduplication precedes pagination and `nbHits` counts groups whenever `distinct` is above zero.

A key's `filters` restriction and the request's own filters are both in force: neither replaces the other, and their conjunction is what the query runs.

Two requests carrying the same idempotency key, the same path and the same body leave exactly one task: the second returns the stored response and enqueues nothing. The same key with a different body is refused and that body is never applied.

`task_id` is monotonic within one index and carries no meaning across two.

A demo request that was accepted is readable afterwards with the six values that were submitted, unchanged by a restart. A demo request that was refused left no row at all.

A record edited in the console carries its new value everywhere it is read afterwards: in the browser, in a fresh page load and in a search result.

An index's `record_count` excludes a deleted record from the moment its delete task publishes.

Seeding must be idempotent - restarting the app must not duplicate rows.

## Front-end specification

This section carries the full visual and structural specification, route by route and surface by surface. Nothing here changes a rule stated above. Values that are somebody's taste are left to you; values that are contract are written out.

### The page type, and what reads it

Every route carries a page type on its root element, and the chrome reads it to decide its own presence and its own resting colour scheme. `marketing` on the home and products routes, where the chrome is present and the header rests dark over a dark hero. `commercial` on the pricing route, chrome present and header dark. `index` on the customers route, chrome present and header **light**, because that route's own body begins light. `capture` on the demo request route, no chrome at all. `error` on the not-found route, no chrome at all. `console` on the signed-in surface. The header's resting colour is therefore a property of the route and never of a scroll position.

The demo request route and the not-found route carry no promotion bar, no utility bar, no header and no footer, and that is a deliberate choice on both for opposite reasons: the form route removes every exit, and the error route is nothing but an exit.

### Iconography

Every symbol in this product is inline geometry drawn from coordinates. No icon is a file, including the mark, which is what lets the whole build ship without a single binary and also what keeps every glyph crisp at any size and recolourable from the surrounding text colour with one instruction.

The **mark** is square, in a 501 by 501 box, rendered at 24 by 24. The **wordmark** is the mark plus the name in a 2197 by 501 box, rendered at 110 by 25, which makes it 4.386 times as wide as it is tall. Any replacement must hold those two ratios or the header's left group re-wraps. The placeholder mark is a quarter-filled ring: a circle at the centre of the box with a generous stroke in the current colour and no fill, plus a filled quarter-arc path, which reads at small sizes and is unambiguously a stand-in. The placeholder wordmark is the word `Kestrel` set in `Sora` at weight 700 with slightly tightened tracking, in the same box, scaled to width.

The **magnifier** is the most-used glyph on the site: a ring and one diagonal handle line running from the ring's lower right toward the box corner, stroked in the current colour with round caps, at 20 by 20 in the header field and 16 by 16 in dense contexts. The **circle arrow** is a ring with an arrowhead and a shaft inside it, at 32 by 32 in the promotion bar and 24 by 24 in the footer and on the not-found route, and it is one of only two glyphs that moves on hover, scaling slightly and changing fill. The **globe** for the language selector is a ring, one horizontal equator line and one meridian ellipse drawn as two arcs, at 16 by 16, and the arcs are what give it its slight barrel.

**There are three distinct chevrons and they are not interchangeable.** A navigation caret, drawn as one polyline, marks a header item that opens a panel. A small right chevron in a narrow tall box marks an inline link. A wide chevron in a short wide box, stroked and unfilled, belongs to the accordion and the select controls. A fourth, the accordion caret, is a path drawn in a square box, sits at zero opacity at rest so it appears when its row is pointed at, and rotates when its panel opens. Using one where another belongs is the kind of thing nobody can name when they look at the finished page and everybody feels.

The **menu** glyph is three evenly spaced horizontal lines and the **close** glyph is two crossing lines, both in a square box at 20 by 20; they are the same control in two states. A small close, two rounded bars drawn as filled shapes in a narrow box, lives inside filter chips. The **check** is one filled path and marks a present feature in the comparison grid; the **tooltip** is a ring with a dot and a stem and marks a feature with a footnote; a **download arrow** is one filled path. The search overlay carries three more from its own family: a filled magnifier for submit, a crossing pair for clear, and a ring in a large box that is rotated by a spin loop while a query is in flight. A second submit and reset pair exists at two other scales in the reference; use the square pair everywhere and scale it.

Thirty-three inline vector elements exist in total across the routes: the twelve above, the mark and wordmark at two sizes, six social glyphs in the footer, and the gradient stop definitions attached to the not-found heading, which are declarations rather than shapes. The consent-surface and chat glyphs the reference carried are not among them, because those embeds are removed rather than replaced.

### Forms and input controls

Specified once and used by the demo request route, the newsletter, the customers route's facets and every field in the console.

A text field sits at the standard field height, the search pill a touch taller. Corners are softened a step, which is the most common corner in the product. The fill is white. There is no border on dark grounds and a hairline border on light ones. The label sits above the field, always visible, in the small size. A required marker is a separate element carrying an asterisk, in the failure colour, before the label text. A placeholder is never a substitute for a label and is used only for a format hint.

A select must open on Enter, Space or Down; filter as the user types when it holds more than twenty options; move its selection with the arrow keys; close on Escape returning focus to its trigger; and expose its state to assistive technology. The country list on the demo request route is the case that matters, at roughly two hundred and fifty options. A native select satisfies every one of those and is the correct default.

The six states of a form are exact. Idle: no error styling and no announcement. Invalid on blur: error text below the field, the field's border in the failure colour, the error associated with the field. Invalid on submit: as above, plus an error summary above the form linking to each failing field, with focus moved to the summary. Submitting: the submit control disabled and announcing that submission is in progress. Success: the form replaced by a success message with focus moved to it. Failure: an error message above the form with the form retained and its values intact.

Input types are not cosmetic, because on a phone they choose the keyboard: `First Name` is text with the given-name autofill token, `Last Name` text with family-name, `Business Email` email with email, `Phone` **tel** with tel, `Company` text with organization, `Country` a select with country-name, and the newsletter field email with email. A text type on the phone field costs a measurable share of completions.

### Module and component architecture

Eleven modules, and a module may depend on modules above it in this list and never below: `tokens`, owning every value, depending on nothing; `primitives`, the button, field, select, pill, card and rule; `icons`, one component per glyph; `chrome`, the promotion bar, utility bar, header, panels, drawer and footer; `motion`, the loop, the carousel timer, the marquee and the reduced-motion handling; `search-ui`, the overlay, its modes, facets, hits and assistant; `forms`, the fields, validation, states and submission; `routes`, the route compositions; `console`; `client`, the transport, retry, host rotation and key handling; and `service`, the engine itself. `client` sits deliberately at the bottom with no interface dependency, because it is imported by both the site and the console and it is the piece a customer would also use.

Seven components recur and each is built once: the button in four variants; the accordion in three bindings; the card as a benefit, a logo, a plan and a story; the marquee row on both axes; the facet control as a list with counts and as a dropdown multi-select; the statistic as a gradient numeral and as an animated bar; and the field in its five types. **The facet control is the load-bearing repetition**: it appears in the search overlay, on the customers route and in the console preview, all three render counts, all three are multi-select, and all three therefore depend on the disjunctive counting rule being right. One component, one contract, three places a defect shows up.

The accordion is specified once and parameterised: a mode of `single`, only one item open, used by the capability accordion and the pricing questions, or `multiple`, used by the mobile drawer; an optional binding to a media pane whose content follows the open item; which chevron it wears; and which item is open on load, or none. Its body's height, top gap and opacity transition together. Animating a height toward a known maximum needs that maximum measured and re-measured on a resize, or the transition truncates a tall panel at the narrowest width where it was measured.

The marquee is specified once and parameterised: an axis, a constant pixel speed shared by every instance, a direction, and a mask fade distance or none. Two copies of the content sit in one track and the track translates by exactly half its own length on the chosen axis, linearly and forever. **Duration is derived from the content length and the constant speed.** Setting a duration per instance gives two rows that visibly move at different speeds.

Five pieces of state live outside any component: the cookie decision, held first-party by the consent band; the chosen language, held by the chrome in a cookie and reflected in the route; whether the search overlay is open, held by `search-ui`, not persisted, and closed on every route change; the facet selection on the customers route, held **in the address bar** so a filtered view is linkable; and the console's table columns, held per member per index on the server.

### Zero-asset substitution

No binary ships with this build: no image file, no video file, no font file and no vector-animation file.

Both type families are named rather than shipped, are open-licensed, and are subset to the Latin range plus the punctuation this product actually uses; naming a font family is not an asset dependency. Only two faces are preloaded, `Sora` at 700 and `Inter` at 400, and the remaining weights arrive later. If neither family arrives the fallback stacks carry the design: the display heading loses its geometric character and nothing else breaks, because the layout is driven by the sizes above and not by the glyph shapes.

The particle field on the two dark bands is a generated layer, not a video: a few hundred soft dots drawn once from a fixed seed, with the parameters above. The reference serves a video weighing more than a megabyte and a half for that effect.

The composed interface panels are handled in two parts, and the split is the most important line in this section. **The interface elements are built, not drawn**: the query bubble, the answer bubble, the product cards, the price and swatch rows, the microphone glyph and the search field inside a panel are real elements using the product's own primitives and its own values, because they are the product being demonstrated. Only the photograph behind them is replaced, by a generated ground: a three-stop diagonal gradient drawn from the panel's own accent, an abstract rounded silhouette occupying the right third filled with the same gradient rotated and lightened, a fine grain layer at very low alpha from a turbulence filter, and a radial darkening toward the corners, each with a seed fixed per panel so the three hero panels are visibly distinct and individually stable. **The result is not a photograph and must not pretend to be one.** The customer story cards and the marquee logo cards use the same generator with a different seed per card.

Customer wordmarks are the customer's name set in `Inter` at weight 800 with slightly loosened tracking, in white, knocked out over the generated card ground at roughly 60 percent of the card width. Partner and integration marks are the partner's name in `Inter` at weight 600 in the deep cool neutral, inside a hairline-bordered box with corners softened a step further than a field. Compliance badges are already text in the reference and stay text.

Four classes are removed rather than replaced, and removing them is the difference between this build's script budget and the reference's actual weight: the tracking pixels, one image per analytics event, because this build sends events to its own collector; the consent surface embed and its artwork, because consent is first-party here; the support chat embed and its artwork, which is out of scope; and the promotion embed with its offsite logo images, which is the surface that claims the top of the stacking order in the reference and is out of scope here. The build's own layers stay in the small fixed ladder named above and never reach for the top of the range.

## Constraints

Multi-workspace by design, and the boundary is the workspace: an account reaches data only through a membership, and no request may span two workspaces.

Absent by design: no payment of any kind, so the four plans are displayed copy, nothing charges a card, no invoice exists and every paid action leads to signup or to `/demorequest`; no email, no SMS and no push, so nothing is ever sent to anybody; no password reset; no third-party script anywhere, which removes the consent vendor, the support chat, the tag manager, the analytics vendor, the advertising panel and the embedded video player; no third-party search product and no managed search service; no external language model and no external embedding provider; no multi-region cluster, no physical replication and no second machine, so the replication guarantees are expressed as generation binding, the task queue and the minimum-task read header rather than as machines; no automatically generated synonyms and no query categorization, which is why those two rows of the comparison grid are shown as absent in every column; no crawler; no native mobile or desktop application; and no external network call at run time of any kind.

The navigation panels behind `Products`, `Solutions`, `Developers` and `Resources` are specified as containers, an arrangement and a behaviour; their link inventories are yours to supply from the routes this brief names.

No binary file ships with the build, and nothing on a marketing route hard-codes a value that should be live: the source counts in the search overlay, the story counts on the customers route and every figure on an analytics screen are read from the data.

The app must stay responsive with `1500` records in the seeded indices, `2000` query events, `5000` interaction events and `200` demo request rows in the database.

## Deployment contract

- The app must be reachable at `APP_PUBLIC_URL`. The port mapping is `${APP_PUBLIC_PORT}:4173` - `4173` is the container-internal port and `APP_PUBLIC_PORT` is what the outside world uses. Read both from the environment; never hardcode either.
- The HTTP API is served on that same origin under the `/api` prefix.
- `GET /api/health` returns `200` once the app is ready.
- The app starts from the environment image with no manual steps.
- Login credentials - or an explicit statement that there are none - are written to `/app/USER_README.md`.
- Reserved `.browser_screenshots/` and `.downloads/` directories exist at the app root, empty.
- Serve a production build behind a static or preview server - never a dev server.
- The server must keep running after this session ends and must not be a child of the shell. An ordinary background job dies with its shell, and the app will not be running when it is next opened.
- Bind `0.0.0.0`, never `127.0.0.1` or `localhost`. A loopback-only listener is unreachable from outside the container.
- The backing services named in this brief are already running and reachable at their environment variables. Do not download, install, compile or start a copy of any of them.
- Use only the providers named in this brief. No edge functions.
- No persistent volumes, no fixed container names, no custom networks.

A list endpoint returns a top-level JSON array. A successful call returns the named resource or shape. An invalid or unauthorized call is rejected as a client error, never a `5xx` and never a silent success, and every error body carries a human-readable `message` that never contains a key, a machine-readable `code`, a `details` object naming the offending path and value where one applies, and a `requestId`. A conflict on an object version is retryable after a re-read; a rate or quota refusal is retryable and carries its retry hint; everything else that is a client error is not. Every search and ingest call authenticates with an application key, not with a console session token; every console endpoint authenticates with a bearer token, except login, signup and health.

**No mocks.** The engine is the fact. Any of the following is a contract violation however convincing the page looks: a search box that filters a list the page already holds; facet counts computed from the hits already on screen rather than from the pruned filter tree; a hardcoded count beside a source name; a ranking that computes one number per hit and sorts by it; highlight tags pasted around a folded copy of the text instead of inserted into the original at its recorded offsets; a hits-per-page figure derived from the record count when deduplication is on; a demo request kept only in the page's own memory or written to a file on the app container rather than stored in PostgreSQL; an analytics figure read from the raw events at display time rather than from a rollup; an honesty flag returned as a constant. PostgreSQL is the fact - the app's UI and its own derived structures can only reflect what lives there, never substitute for it.

## Definition of done

A stranger can open Kestrel, type into the header search and get real ranked results with live counts beside all eight sources, narrow the customer stories to two industries at once and find the counts on every other group still truthful, and submit the demo request form and land on the confirmation page that names their company. A misspelled match never appears above a correct one, whatever its popularity, and the same search twice returns the same order. An operator can sign in, edit a record and find the new value after a reload, drag a result to the top for one query and see the rule that put it there, while an analyst attempting the same edit is refused and the rule list is unchanged.
