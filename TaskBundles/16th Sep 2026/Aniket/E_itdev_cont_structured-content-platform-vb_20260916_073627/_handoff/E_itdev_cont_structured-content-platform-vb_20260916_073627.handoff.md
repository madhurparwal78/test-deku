## What the downstream builder must know before writing the app

**The browser pass runs before the pytest pass, and this bundle is authored around that.**
The strategy used is DISJOINT SEED ENTITIES (reference/J J.12, reference/E E.6). The
browser journeys edit, save, publish and crop exactly one seeded document,
`article-editorial-standards`, and create their own documents for the array, the release
and the modal journeys. Every other seeded document is read-only to the browser:
`article-aurora-pipeline` is read but never emboldened again, `article-migrating-schemas`
is never saved or unpublished, and `article-keys-and-arrays` is only pressed toward a
publish that is refused, which writes nothing. That is what keeps
`test_four_publication_states_are_distinguishable`,
`test_split_span_keeps_the_first_key` and `test_document_carries_reserved_service_fields`
true after the browser pass has run.

**Two durations are env-injected.** `PREVIEW_GRANT_TTL_SEC` is `3600` in
`[environment].env` and `8` in `[verifier].env`; `TRANSACTION_REPLAY_WINDOW_SEC` is `300`
in both. The app must READ both. A duration compiled into the app makes the preview-expiry
path unobservable inside a grading run, and the seam exists so the verifier can shrink an
hour without the agent knowing.

**Scheduling and releases execute lazily.** The kit's baseline forbids cron, workers and
queues, so a schedule whose instant has passed executes the next time that schedule, its
document or the release list is read or acted upon. That is externally indistinguishable
from a sweeper and is what the graders observe.

**Webhook deliveries are recorded, never sent.** The environment makes no outbound network
call at runtime, so a delivery is a row carrying the webhook, the transaction identifier,
the affected ids and a truncation flag. The coalescing rule of the companion's Section 32.4
is observable on that record rather than on a request.

**The stack is a drawn value, not a preference.** `render_model = mpa-progressive`,
`backend = NestJS + Handlebars`, `frontend = Alpine.js + server templates`, drawn by
SHA-256 over the archetype per generate_instruction 2.9. Every route is rendered on the
server; Alpine upgrades the rendered markup in place. The live-update surface is a
long-lived HTTP stream on the app's own origin, because no realtime provider is declared
and none is reachable.
