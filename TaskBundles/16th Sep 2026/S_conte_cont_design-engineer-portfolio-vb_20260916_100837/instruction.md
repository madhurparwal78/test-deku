# atlas.design

Build and deploy a working web application from this brief. There is no starting codebase. When you are done, a stranger must be able to open the app in a browser, land on the fixed-frame home page, browse the ten-card project index, open the nDrive case study and jump straight to one of its headings, and unlock the Field Notes article with its passcode, without hitting an error page. A visitor who has not been given a passcode must NOT be able to read a draft case study, the gated Field Notes article, or any figure attached to either, by any means: not from the index, not by typing the address, not through the API, not from the object store. Figure bytes must live in the object store at their scheme's key; a copy on the app's own disk does not count, and neither does a database row that merely says an upload happened.

## Overview

atlas.design is the portfolio and writing archive of Rin Alvez, a design engineer. It is one person's site with three public jobs, in this order: establish craft in the first few seconds before anything is read, present ten pieces of work as a browsable index sized by importance rather than by a uniform card, and carry long case studies that read like careful documentation, with anchored headings, a side table of contents, code blocks, a reading-progress rail and a metadata footer.

It has two private jobs. One article, Field Notes, sits behind a four-digit passcode that the owner hands to people who ask. And behind a second passcode sits the studio, where the owner writes a case study, uploads its figures, sets its metadata and its place on the index grid, and then either publishes it into the index, marks it as an unfinished stub, or holds it as a draft that nobody else can reach.

The site is written for four audiences: hiring managers who want proof of craft quickly, peer designers and engineers who read the case-study bodies and code, collaborators who want a way to make contact, and the owner. It deliberately is not: a product with visitor accounts, a comment system, a newsletter, a contact form, a search engine, an analytics dashboard, or a store of anybody's data beyond what the owner writes. Contact is a mail address and nothing more.

The genuinely hard part is that the index layout is content rather than code, and publication is a boundary that must hold everywhere at once. Each card's grid placement and position are fields the owner sets, two cards may never be listed at the same position, and a draft must stay invisible on its page, in the API, in the index and in the object store alike, while the gated article stays closed to everyone who has not entered its code on the server.

## User roles

| Role | Can do | Cannot do |
|---|---|---|
| `visitor` | Open every public route with no account. Browse the index, open any published or stub case study, follow any anchored heading, read any figure attached to a published or stub case study, switch the theme and the sound, and submit a passcode for a gated path. Once the correct code for `/field-notes` is accepted, read that article and its figures for the rest of the browser session. | **Cannot see, list, open or fetch a draft case study or any of its figures, by any address.** **Cannot read the gated article or its figures without that article's own accepted code.** **Cannot reach the studio, the studio API or the page-view record.** **Cannot create, edit, publish, stub, hold or upload anything.** **Cannot sign up: there is no visitor account to create.** |
| `owner` | Everything a visitor can do, plus: unlock the studio with the studio passcode, create and edit case studies, upload figures, set every case study's metadata and card placement, publish, stub or hold any case study, preview drafts and the gated article, read the page-view record, and lock the studio again. | **Cannot list two cards at the same index position.** **Cannot save a card placement that falls outside the twelve grid columns.** **Cannot upload a figure without alternative text.** **Cannot give a case study a slug another case study already holds or a reserved one.** |

Authorization is enforced **server-side on every mutating endpoint**. Hiding a button in the UI is not authorization: a direct API call from a `visitor` session to any `owner`-only endpoint must be rejected by the server (an unauthorized request is denied, not served), leaving the protected state unchanged.

Signup is closed. There are no email and password accounts anywhere in this product, and no sign-in form. A browser becomes the `owner` for the rest of its session only by submitting the studio passcode for the path `/studio`; it can read the gated article by submitting that article's passcode for the path `/field-notes`. Every other browser is a `visitor`.

The two seeded passcodes:

| Gated path | Passcode | What it opens |
|---|---|---|
| `/studio` | `5093` | the studio and every owner-only endpoint, plus previews of drafts and of the gated article |
| `/field-notes` | `2718` | the Field Notes article and its figures, and nothing else |

## Core features

### Auth: passcodes and grants

The only way to change what a browser may see is `POST /api/passcode` with the body `{ "path": "<gated path>", "code": "<four digits>" }`. The comparison happens on the server, and the answer carries a boolean and nothing else: never the code, never a hint about how close the attempt was.

1. A correct code answers `200` with a JSON object keyed by the submitted path, for example `{"/field-notes": true}`, and the same response sets a grant for that one path. A wrong code answers `200` with `{"/field-notes": false}` and sets nothing.
2. A path that is not gated at all answers exactly like a wrong code for a gated one: `200` with that path mapped to `false`. The response never tells a missing gate from a wrong code, in its wording or its shape, and a refusal takes the same time as a success to within ordinary network variation, so timing reveals nothing either.
3. A `code` that is not exactly four digits, or a body missing `path` or `code`, is rejected as invalid input before any comparison happens, and such a request is not counted as an attempt.
4. Refused attempts are rate limited per client address and per gated path together. After five refused attempts for one path from one address within one minute, every further attempt for that path from that address, right or wrong, answers `429` with `{"error": "rate_limited"}` until one minute has passed since the first of those five refusals. Attempts for a path that is not gated count exactly as refusals for a gated one. A success is never counted.
5. The grant is carried by a cookie the server sets on the success response. It is readable by the server alone and never by page script, it works over a plain unencrypted connection, the browser sends it back on every later request to this site including requests under `/api`, and it lasts for the browser session and no longer: it carries no expiry date and no maximum age.
6. A grant is scoped to the path it was issued for. A grant for `/field-notes` opens that article and its figures and nothing else: with only that grant, every studio endpoint is still denied and every draft is still invisible. A grant for `/studio` is the owner's grant: it opens every studio endpoint and additionally lets that browser preview drafts and read the gated article and its figures.
7. `POST /api/passcode/release` with `{ "path": "/studio" }` or `{ "path": "/field-notes" }` ends that grant for this browser, on the server as well as in the browser: the old cookie no longer opens anything even if it is sent again. Afterwards the paths it opened are closed again exactly as before the code was entered.
8. Typing a gated path directly never serves its content. Without a grant, `/field-notes` and `/studio` answer with the passcode screen in place of the content, and the response carries none of the article's or the studio's own text. `GET /api/case-studies/field-notes` without a grant is denied and its body carries no title, lead or body text.
9. Every studio endpoint under `/api/studio` is denied to a request that carries no studio grant, and a denied write changes nothing.

### The project index and its placement records

The home page's index is built from card records, never from markup typed into a page. Each card has a title, an optional eyebrow label, a year range, an optional kind label, an aspect ratio for its media, a description of its media, a position, and two grid placements: one for the widest layout and one fallback for mid-width windows. A card either opens a case study on this site or points at an outside address.

10. `GET /api/projects` returns a top-level JSON array of the listed cards, ordered by `sort_order` ascending. Each item carries `id`, `title`, `slug` (the case-study slug, or null for an outside card), `external_url` (null for a case-study card), `kind`, `eyebrow`, `year_from`, `year_to`, `year_label`, `aspect_ratio`, `column_start`, `column_span`, `column_start_lg`, `column_span_lg`, `sort_order` and `media_alt`.
11. A card linked to a case study is listed exactly when that case study's status is `published` or `stub`. An outside card is listed exactly when its own `published` flag is true. A card linked to a draft never appears in this array, on the home page, or anywhere else a visitor can reach.
12. **Two listed cards never share a position.** Publishing or stubbing a case study whose card `sort_order` equals the `sort_order` of any other listed card is rejected as a conflict with the error code `position_taken`, and the case study keeps the status it had. Two publish requests arriving at the same moment for two drafts whose cards claim the same free position must not both succeed: exactly one is accepted, the other is rejected as a conflict with `position_taken` and stays a draft, and afterwards exactly one listed card holds that position.
13. A placement is valid when `column_start` and `column_span` are each whole numbers from `1` to `12` and `column_start` plus `column_span` minus one is at most `12`, and the same holds for `column_start_lg` and `column_span_lg`. `sort_order` is a whole number of at least `1`. `aspect_ratio` is one of `16:9`, `1.54:1`, `0.71:1` or `1:1`. A create or edit carrying anything else is rejected as invalid with the error code `invalid_placement`, and nothing is written.
14. `year_label` is `year_from` alone when `year_to` is null, and `year_from`, a hyphen and `year_to` otherwise: `2025`, or `2024-2026`. It is derived when read and never stored.
15. `media_alt` describes what the card's media shows. A card whose `media_alt` is empty or merely repeats its title is rejected as invalid with `invalid_media_alt`, and nothing is written.
16. The index lays the listed cards on a grid of twelve columns with no gutter between cells. At the widest layout each card starts on its record's `column_start` and spans `column_span` columns; at mid widths it uses `column_start_lg` and `column_span_lg`. The seeded ten therefore start on columns `5, 1, 7, 6, 10, 1, 5, 9, 6, 10` in order at the widest layout. That unevenness is the design: no tidy row of equal boxes, and the positions come from the records, so the owner can rearrange the index without anyone changing code.

### Case studies

A case study has a `title`, a `slug`, a `last_updated` date, a year range, a `lead`, a `body`, the width and height of the window the owner composed it for, an optional outbound link, an optional gated path, a `status` of `draft`, `stub` or `published`, and at most one card.

17. `GET /api/case-studies/{slug}` returns one published or stub case study, and additionally returns a draft to a browser holding the studio grant, with `id`, `slug`, `title`, `status`, `last_updated`, `last_updated_label`, `year_from`, `year_to`, `year_label`, `lead`, `body`, `outbound_url`, `composed_width`, `composed_height`, `dimensions`, `character_count`, `character_label`, `headings` and `figures`. For a stub, the public read carries `body` as an empty string, `headings` as an empty array and `character_count` as `0`; the stored body itself is kept, shown in the studio, and served again if the case study is published later.
18. A draft case study is invisible to everyone without the studio grant, whatever its gated path: draft status takes precedence over gating, so a held gated article also shows the not-found page and denies its figures to everyone but the studio grant. Its page and `GET /api/case-studies/{slug}` answer exactly as a slug that does not exist answers: the same status and no title, lead or body. Its card is unlisted. Its figures are denied. All of this holds for a request that guesses the slug exactly.
19. The page of a case study lives at `/{slug}`, directly under the site root. The seeded case studies are `/kindling`, `/almanac-mono`, `/wasm-design-utils`, `/ndrive`, `/coast-icon`, `/teamharbor` and the gated `/field-notes`.
20. A slug is lowercase letters and digits in groups joined by single hyphens, at most sixty characters, for example `wasm-design-utils`. A slug of any other shape is rejected as invalid with `invalid_slug`. The slugs `api`, `studio` and `static` are reserved and rejected as invalid with `slug_reserved`. A slug another case study already holds is rejected as a conflict with `slug_taken`. Nothing is written on any of these refusals.
21. Changing the slug of a published or stub case study leaves a permanent redirect: the old address `/{old slug}` answers with a permanent redirect whose location is `/{new slug}`, and no other case study may take the old slug while that redirect stands (`slug_taken`).
22. The body is plain text with a small markup. A line starting `## `, `### ` or `#### ` is a heading of level two, three or four. A block opened and closed by a line of three backticks, the opening line carrying a language word such as `python`, is a code block. A line of exactly the form `[[figure:ID]]` places the uploaded figure with that id. A pair of single backticks marks inline code, a bracketed text followed by a parenthesised address is a link, and a blank line separates paragraphs. Levels must descend without skipping: a body that jumps from level two straight to level four is rejected as invalid with `invalid_heading_levels`, and nothing is written.
23. Every heading is addressable. Its slug is its text lowercased, with every run of characters that are not a letter or a digit replaced by one hyphen and hyphens trimmed from both ends; a second heading producing a slug already used in the same body gets `-2`, a third `-3`, in reading order. So `Sync, conflicts & recovery` becomes `sync-conflicts-recovery`, `Offline, then online` becomes `offline-then-online`, `What I would change` becomes `what-i-would-change`, and two headings both reading `Notes` become `notes` and `notes-2`. The same heading text always yields the same slug, on every render and after every restart, because these are shared links. `headings` lists every heading in reading order as `{ "level", "text", "slug" }`, and on the page each heading element carries its slug as its `id`.
24. `character_count` is the number of characters in the stored `body` with every line break left out, computed when read and never stored. `character_label` is that count written with a comma between thousands, so `1602` reads `1,602` and `863` reads `863`.
25. `dimensions` is `composed_width`, a lowercase `x` and `composed_height`, for example `1440x900` or `390x844`. `last_updated` is an ISO date such as `2026-01-15`, and `last_updated_label` writes it as a short month, the day without padding, a comma and the year: `Jan 15, 2026`.
26. The nDrive case study carries exactly nine headings in this order: `Why another drive` at level two, `Files as a timeline` at level three, `Sharing without accounts` at level three, `Sync, conflicts & recovery` at level two, `Offline, then online` at level three, `The merge sheet` at level four, `Designing the empty states` at level two, `What we measured` at level three and `What I would change` at level two. The Wasm design utils case study carries seven headings and at least one code block. The Coast Icon case study carries fifteen headings and at least one code block. Kindling and Almanac Mono are short.
27. The Almanac Mono case study offers a download link reading `Download Almanac Mono`, pointing at `https://www.example.com/almanac-mono/download`.
28. A stub renders its title, its date, its year range, the notice `Work in progress - this page is not finished yet.`, its lead as a one-paragraph summary, its outbound link, the full metadata footer and the reading rail. It renders no body, and no table-of-contents drawer at all rather than an empty one. The seeded Teamharbor case study is a stub whose outbound link is `https://www.example.com/teamharbor`.
29. The Field Notes case study is published, gated on `/field-notes`, has no card, and has the lead `Notes I keep for myself, shared with the people who ask.` It is never listed in the index.

### Figures live in the object store

30. Every figure is stored in the MinIO bucket named by `STORAGE_BUCKET`, reached at `STORAGE_ENDPOINT` with `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY`, and nowhere else. The object key is `case-studies/{case_study_id}/figures/{sha256_of_bytes}.{ext}`, where the digest is the lowercase hexadecimal SHA-256 of the uploaded bytes and the extension follows the content type (`png`, `jpg` or `webp`). For example `case-studies/7/figures/3b1f0c9a8d2e4f6a7b8c9d0e1f2a3b4c5d6e7f8091a2b3c4d5e6f708192a3b4c.png`. Bytes on the app container's filesystem are a contract violation, as is a database column holding the figure itself, however correct the page looks.
31. `POST /api/studio/case-studies/{id}/figures` takes a multipart form with the fields `file`, `alt_text`, `width` and `height`, writes the bytes to that key, and records the key, the content type, the byte size, the intrinsic width and height and the alternative text. It returns the figure with `id`, `case_study_id`, `object_key`, `content_type`, `byte_size`, `width`, `height`, `alt_text` and `url`, where `url` is `/api/figures/{id}`.
32. An upload is refused as invalid, writing nothing to the bucket or the database, when `alt_text` is missing or blank (`alt_text_required`), when `width` or `height` is not a whole number of at least one (`invalid_dimensions`), when the content type is anything other than PNG, JPEG or WebP (`unsupported_type`), or when the file is larger than 5,242,880 bytes, five mebibytes (`file_too_large`). The server reads the real size of the image it received, and a `width` or `height` that disagrees with it is also refused with `invalid_dimensions`.
33. Uploading the same bytes to the same case study twice creates no second object and no second figure record. The second upload is a no-op that returns the figure already stored.
34. Figure bytes are served only through `GET /api/figures/{id}`, which streams them from the bucket with their stored content type after checking who is asking. Draft status takes precedence over gating, and gating takes precedence over publication. A figure of a published or stub case study with no gated path is served to anyone. A figure of a gated case study that is not a draft is served only to a browser holding that path's grant or the studio grant. A figure of a draft is served only to a browser holding the studio grant. Everyone else is denied, and the bucket itself is never made publicly readable and never hands out a time-limited link.
35. On the page, a figure placed in a body is shown at the full width of the text column with its alternative text, and it reserves its box from its recorded width and height before the bytes arrive, so a long article never shifts under a reader.

### The studio

The studio is the owner's authoring surface at `/studio`, and it is the only part of the product that writes.

36. `GET /api/studio/case-studies` returns a top-level JSON array of every case study in every status, each with its card placement. `GET /api/studio/case-studies/{id}` returns one, including a draft.
37. `POST /api/studio/case-studies` creates a case study in the status `draft` from `title`, `slug`, `last_updated`, `year_from`, `year_to`, `lead`, `body`, `composed_width`, `composed_height`, `outbound_url`, `gated_path` and an optional `card` object carrying `eyebrow`, `kind`, `aspect_ratio`, `media_alt`, `column_start`, `column_span`, `column_start_lg`, `column_span_lg` and `sort_order`. `title`, `slug`, `last_updated`, `year_from` and `lead` are required, and a create missing any of them is rejected as invalid with `incomplete` and writes nothing. A present field of the wrong shape (a `last_updated` that is not an ISO date, an `outbound_url` that is not an absolute `https` address, a `gated_path` other than `/field-notes` or null, a year that is not a whole number) is rejected as invalid with `invalid_field` and writes nothing. The `card` object carries exactly `eyebrow`, `kind`, `aspect_ratio`, `media_alt`, `column_start`, `column_span`, `column_start_lg`, `column_span_lg` and `sort_order`.
38. `PATCH /api/studio/case-studies/{id}` changes any of those fields, applying the same validation. Changing the `sort_order` of a listed card to a position another listed card holds is rejected with `position_taken`.
39. `POST /api/studio/case-studies/{id}/publish` sets the status to `published` and lists the card. `POST /api/studio/case-studies/{id}/stub` sets the status to `stub` and lists the card. `POST /api/studio/case-studies/{id}/hold` sets the status back to `draft` and unlists the card at once, after which the page, the API read and the figures of that case study are closed to visitors again. Each returns the case study, including its new `status` and its `published_at`, which is set when a case study is first published. A case study with no card may be published or stubbed; it is readable at its address and simply never listed. Holding a case study that is already a draft is a no-op that returns it unchanged.
40. A browser holding the studio grant may open a draft's own address `/{slug}` and sees it rendered with a banner across the top of the page naming it a draft preview, a banner that appears on no other page, and it may read the gated article without that article's own code.
41. The studio's index preview shows every card as it would sit on the twelve columns at the widest layout, listed cards and the draft being edited together, with the draft visibly marked, so the owner can see the arrangement change as placement fields change.

### The chrome, the theme and the sound

42. A fixed frame sits over every route and never scrolls. It holds the wordmark, reading `atlas` followed by `.design`, which returns home; two controls reading `Work` and `Contact`; a theme control reading `THEME[A]`; a sound control reading `SOUND[` then one spinner character then `]`; a clock; a live pointer readout; and a small wire globe. `Work` and `Contact` are buttons, not links: on the home page they scroll to the `#selected-work` and `#contact` anchors, and on any other route they return home first and then scroll.
43. On a first visit the light theme is on. The theme control is a real button whose `aria-pressed` state is `true` while the dark theme is on and `false` otherwise. Pressing it, or pressing the `A` key anywhere outside a text field, switches between the light and the dark theme. The root element of the document carries the class `light` or `dark` accordingly. The choice survives a reload and a return visit, and it is applied before the first paint, so no page ever flashes the wrong ground: the choice is kept in browser storage and a small blocking script in the document head applies the class before the body renders. The shortcut never fires while a text field, including the passcode field, has focus.
44. The sound control is a real button whose `aria-pressed` state is `true` while sound is on and `false` otherwise. Sound is off on a first visit and nothing audible is created before the visitor presses the control. Turning it on fades an ambient bed in; turning it off fades it out a little faster than it arrived. The character inside the brackets cycles through `|`, `/`, `-` and a backslash while sound is on and holds still while it is off. The choice survives a reload, and a reload with sound previously on still waits for a press before anything plays.
45. `sound_enabled` in the site profile governs whether the sound control is offered at all; it is true, so the control is shown. The clock at wide windows reads the zone label `GMT+8`, the region label `CN` and the local time in that zone as hours and minutes on a twenty-four hour clock, for example `GMT+8 CN 13:48`; at narrow windows it shows the time alone. The pointer readout shows the pointer's position in the window as two four-digit zero-padded numbers, for example `0720 X 0450 Y`. Neither string ever changes width as it updates. No temperature is shown, because no weather source is configured.

### The rest of the product

46. An unknown address renders the site's own not-found page and answers with a not-found status. It keeps the chrome, shows the line `Nothing is filed at this address.` and one action reading `Back to the index` that returns home. A draft's address, for a visitor, is indistinguishable from this page.
47. Every internal link on every public route resolves: the wordmark, every case-study card, every heading anchor, every drawer row, the footer links on case studies, the not-found page's action and the three inline links in the home statement all lead to an address that answers rather than to a not-found page.
48. Each page view is recorded. Every request for a public page (the home page, a case study, a gate screen or the not-found page) stores the route requested and the time in UTC. `GET /api/studio/page-views` returns a top-level JSON array of `{ "route", "viewed_at" }`, newest first, to the studio grant alone. API requests and static files are not recorded, and the record holds no address, cookie or other identifier of the visitor.
49. The home page's secondary statement carries three inline links, to the Kindling, nDrive and Teamharbor case studies.
50. `GET /api/site` returns the site profile the frame and the home page are rendered from, including the three social links in order.

### Entry and redirects

A visitor opening `/`, any case study or the not-found page lands directly with no interstitial. A visitor opening `/field-notes` or `/studio` without a grant stays on that address and sees the passcode screen instead of the content; entering the right code reveals the content in place at the same address, with no redirect and no reload the visitor has to trigger. A wrong code leaves the passcode screen in place. Pressing `Lock studio` in the studio ends the grant and returns that address to the passcode screen. A grant that has ended mid-action, because the session closed, leaves the studio page in place, shows a message that the studio is locked, and keeps whatever the owner was typing so nothing is lost when the code is entered again. A published case study whose slug changed redirects permanently from its old address. A draft's address shows the not-found page to everyone without the studio grant.

### Journeys

**A recruiter scans the work.** Open `/`. Watch the three headline lines rise into place while the loader fills and leaves. Press `Work` in the frame and the page glides down to the index. See Kindling wide across the right two thirds of the first row, Almanac Mono and Wasm design utils beneath it, and the smaller cards scattered so that no two consecutive rows start on the same column. Open `nDrive`.

**A peer reads a case study.** On `/ndrive`, read the title, the date, the rule and the lead. Scroll, and watch the reading rail on the right edge fade in and fill from the top. ### States

Every page has a loading state: on the home page it is the small centred loader, and the type is readable before anything else arrives. The index with no listed cards shows one quiet line in the index band saying there is no work to show yet and keeps the band's height stable. The studio table with no case studies shows a single row inviting the owner to press `New case study`. The page-view list with no views says so in one line. A case study with no headings renders no drawer. A figure that fails to load keeps its reserved box and shows its alternative text. Errors never crash the app: a failed studio request raises a toast naming what failed, keeps the owner's typing, and leaves the page usable.

## UI/UX notes

Somebody arriving should understand within the first moment that this is one careful maker's workbench: that the person behind it cares about type, timing and small instruments, and that the work is what matters here. The register is a personal portfolio and editorial archive: atmosphere is welcome on the home page and the subject, the words and the work, is always the first thing seen; the case-study pages read like a manual addressed to somebody already working; the studio is a quiet tool. The character described below governs every choice, and exact values are the builder's so long as each relationship holds. The site is designed light first: light is what a first visit shows, and dark is designed just as completely.

It has to convey craft before content, so the first screen is complete, still and exact before any decoration arrives, and nothing ever jumps when decoration does arrive. It has to support exploring, so the index repeats one comparable card shape at deliberately unequal sizes and positions. It has to support long reading, so case-study pages are calm, narrow-measured and free of anything that moves while the reader is reading, apart from the rail that reports progress.

**Paper and ink.** The whole site is warm off-white paper and one ink. The ground is a near-white warm neutral, closer to paper than to screen white. Raised surfaces are one step warmer and darker than the ground, a near-white warm neutral that must read as separate from the ground without any shadow. The ink is a warm near-black with a trace of brown in it. There is no grey anywhere: every quieter tone is that same warm ink made partly transparent, in a short ladder of strengths used by role. The ladder has five steps, each clearly fainter than the one above it. The strongest step is for headings, titles and anything that must be read first. The second is for body prose and de-emphasised copy, and still reads comfortably. The third is for line numbers, resting rings and placeholder text only, never for a message a visitor must read. The fourth is the faintest legible ink and is used for decoration only. The fifth is barely there and is every hairline and rule on the site, and nothing else uses it. Two faint special strengths exist: a very faint wash behind inline code and behind the case-study footer, and a medium-faint strength for code comments. Absolute black is used by exactly one thing, the ring of the passcode slot that is waiting for the next digit. The exact shades are yours, so long as the ladder is one ink at several strengths and never a separate grey.

**The only colour.** The light theme has exactly two saturated colours, and they are the same family: a light, vivid lime for the ground of selected text, and a light, vivid lime for the hand-drawn scribble over the home statement. Nothing else in the chrome, the index or the case-study prose is saturated; code blocks carry their own hues, described below. The one other chromatic presence is the three-dimensional scene on the home page's first screen, whose accent is a mid, vivid blue used by the floating pointer object and nowhere in the page's own interface. No page is dominated by a single hue, no button is coloured, and no colour doing a job that the ink ladder already does.

**Code colours.** Code blocks carry their own small palette of six hues, all mixed to one shared mid lightness so that no token shouts against the warm paper: a deep warm red for tags, a mid, vivid blue-violet for keywords, a deep green for strings, an ochre for numbers, a cool mid blue for function names, and the ink at a medium strength for operators and punctuation, with comments at the fainter strength described above. Changing any one of these must never make it visibly brighter or darker than the others.

**The dark theme.** Dark mode is real and fully designed, not an inversion of colours. It swaps the relationship rather than the hues: a warm near-black ground, a raised surface one step lighter, and the same warm ink ladder carried over as light ink at the same relative strengths, so every role above still reads the same way. The lime keeps its two jobs. Both themes are expected to be complete; neither may leave a surface unstyled.

**Type.** Three families carry the whole site, and choosing them is yours within these characters. A variable grotesque, spanning the full weight range, with tight apertures and a single-storey lowercase g, sets all display type and all prose. A variable monospace with a generous x-height sets code. A single-weight monospace with a slightly squared, technical drawing sets the chrome: every string in the frame except the wordmark, which is set in the grotesque, plus the clock, the readout, the labels and the passcode prompt. Each family needs a fallback chosen to match its metrics so that swapping between the fallback and the real face moves nothing on the page. Display type is sized as a fixed fraction of the window width and scales continuously rather than stepping, headline lines sit touching, with no extra air between one line and the next, and below the site's one real breakpoint the display fraction grows rather than shrinks so the headline stays commanding on a phone. The home headline is set in sentence case in the text and shown in capitals. Two leading ratios do all the work: a relaxed one shared by code and dense prose, and a tight one shared by every heading level. Heading levels two, three and four step down clearly in size and all carry the same semibold weight; the two heavy headings on the site are the home headline and the case-study title. Body prose on case studies is a little smaller than the site's default text and runs in a measure that is wide for prose and suits a document carrying code. At the smallest window the whole text scale steps down slightly, never below the minimum text size in the accessibility floors.

**The grid and space.** The home page is laid on twelve columns with no gutter at all: cells touch, and the only visible gap comes from a small, equal inset inside every cell. That inset is also the distance every chrome string sits inside its control. The contact band is the one place with a real gutter. The page has a small side margin on narrow windows and a much larger one on wide windows. Space over dividers: sections separate by their own air and scale, and the only rules are hairlines that are themselves part of the drawing.

**Shape and depth.** The site is flat. Card media corners are barely softened, embedded frames, figures and the case-study footer are a little softer, inline code is the least softened of all, a touch less than card media, and the loader fill and passcode slots are fully round. There are no drop shadows. Rings are drawn inside the element, hard-edged, with no blur and no offset: resting rings in the third-strength ink, and the active passcode ring in absolute black. Embedded frames carry a hairline ring. A code block's header bar is separated from the code by a single hairline along its bottom edge.

**Density.** Comfortable on the home page, where each band is a screen or more; compact in the chrome, where every control is a small label in a generous hit area; comfortable in case studies; compact in the studio table, where rows sit tight so the whole archive fits one screen.

**Motion.** Motion here is a signature, not an ornament, and the character is precise: things arrive almost at once and then drift the last hair of the way, so they read as objects settling rather than panels sliding. Three speeds carry the whole site: a quick one for anything a pointer causes, a slightly slower one for anything a state change causes, and a long settling one for content arriving. Only the loader, the reading rail's fade and the sound ring keep timings of their own, each between the state-change speed and the settling one; nothing else invents a fourth. The exact durations and curves are yours, so long as every motion shares this character. Paired elements arrive one short beat apart. Fades are deliberately asymmetric: a fade in holds back early and rushes late, a fade out leaves faster than the matching fade in arrives, and substituting a symmetric fade anywhere changes the character of the site. The named moments, each of which must exist: the centred loader bar that covers most of its distance at once and then settles, and animates its length rather than stretching its round ends; the three headline lines each rising into a slot slightly shorter than its letters and being trimmed as they arrive, one just behind the other; the hairlines on the first screen fading in after a deliberate hold; the headline and the chrome strings resolving from random capitals, digits and symbols into their real characters one character at a time from left to right, without the headline's width changing at any moment; the wire globe turning continuously, its six meridian arcs squashing and stretching sideways about the globe's centre and flipping as they pass the far side; the bracketed character in the sound label cycling while sound is on; the reading rail fading in while the reader scrolls, filling from the top, and fading out when they stop; the passcode bar blinking as a hard on-off flicker with no fade; the passcode ring changing between resting and waiting with the settling character; the menu button's two flat bars shrinking away to one side while two crossing bars grow in, each pair's second bar a beat behind its first, so it reads as a gesture rather than a swap; the drawer opening by growing sideways from the left edge; the held statement band changing its own ground colour while it is pinned; and the small drawing beside the home statement drawing itself, holding, and clearing on a slow loop. Nothing on this site is tied to the scroll position except the rail's fill and the pinned band; every other animation runs on its own clock. Hover is applied only where a real pointer exists, and it moves an element one step up the ink ladder at the quick speed; nothing latches in a hovered state after a tap.

**Reduced motion.** When a visitor's system asks sites to reduce motion, honour that preference: motion that moves things stops and motion that only changes brightness or reports progress stays. Scroll smoothing, the character scramble, the headline rise, the pinned band, the globe's rotation and the three-dimensional scene's movement all stop: the strings render final at once, the lines are simply present, the band collapses to a single screen with its three words present, the globe holds one angle and the scene shows one still frame. The blinking passcode bar, the loader, fades and colour transitions all remain.

**Components behave, not just appear.** Every control has resting, pointed-at, pressed, focused and unavailable states, and unavailable is never signalled by colour alone. Every chrome control, contact link and social link has an invisible hit area covering its whole box, so a short label is easy to hit. The passcode slots are one field, not four: typing advances, backspace retreats and clears, pasting four digits fills all four, and only digits are accepted. Every toast in the studio names what happened in plain words and stays until it is dismissed or replaced; nothing important disappears on a timer before it can be read. Destructive studio actions, holding a published case study as a draft, ask once before they run, and the confirming control names what will happen. Escape closes the drawer, the phone menu and the hold confirmation prompt.

**One primary action per page.** Each page leads with one primary action, set in the strongest ink and visually distinct from every secondary control: on the home page it is the `Work` control that takes a visitor to the index, on a case study it is the contents drawer opener, on a passcode screen it is the waiting slot, and in the studio it is `Publish` for the case study being edited. Everything else on the page is quieter.

**Responsive.** The site has one real breakpoint, around the width of a small laptop, and a handful of refinements either side; the layout must hold at every width between them rather than only at the named ones. Below that breakpoint the four chrome controls collapse into a menu button, the clock drops its zone and region, the discipline label and tagline on the first screen disappear, card kind labels hide, the case-study title steps down to its smaller size, page and footer padding tighten, and the reading rail is replaced by a slimmer small-screen variant. Hover treatments are guarded by pointer capability and never appear on touch. At a narrow viewport nothing overflows sideways, the document never scrolls horizontally, and every navigation target stays reachable through the menu button.

**Accessibility floors.** Contrast meets WCAG AA: at least 4.5 to 1 for body text against its ground in both themes, and at least 3 to 1 for a focus ring and for any glyph that carries meaning. The third-strength ink never carries text a visitor must read, and the passcode prompt is set in the body-prose strength for that reason. Full keyboard navigation with a visible focus ring on every card, chrome control, heading anchor, drawer row, mail link and social link, in reading order, with no positive tab order; the focus ring is the same hard inset ring the passcode slots use. The inner scroller responds to page up, page down, home, end and the space bar. Every touch target is at least 44 by 44 CSS pixels (WCAG 2.5.5), and no readable text is ever set smaller than 12 CSS pixels at any width. Each route carries one banner landmark for the frame, one main landmark for the page content, and one contentinfo landmark for the contact band on the home page and for the footer on a case study; each route has exactly one level-one heading, and heading levels never skip. Labels on every icon-only control: the menu button's accessible name is `Menu`, and the drawer opener's is `Contents`. Meaning is never carried by colour alone. Success, failure and waiting are told apart by words, not hues: a studio toast that reports a refusal opens with the word `Refused`, a success toast states what happened, and nothing in the interface uses a red, green or amber to carry that meaning. Every content image carries alternative text, and every decorative drawing, the globe, the sound ring, the reading rail, the scribble, the stickers and the two scene surfaces, is hidden from assistive technology. Under forced colours every ring falls back to a system border, hairlines stay visible, and the scene surfaces are hidden rather than left as blank rectangles.

**What it must not look like.** No grey text or grey surfaces that are not the one ink made transparent. No coloured call-to-action buttons. No card grid of equal boxes in tidy rows. No shadows standing in for separation. No decoration standing in for content: the first screen must look finished and deliberate with the scene switched off. No marketing composition inside a case study or the studio. No icon font and no picture file doing a drawing's job.

## Technical requirements

The rendering model is multi-page with progressive enhancement: every public page is complete HTML produced by the server, a visitor with scripting unavailable can read the whole index and every case study, and scripts only add behaviour on top. The backend is Python 3.12 with Flask, rendering pages with Jinja templates and serving the JSON API under the `/api` prefix on the same origin, run by the gunicorn production server. Client behaviour is vanilla progressive enhancement: plain browser JavaScript modules served as static files, with no client framework and no required build step. The datastore is PostgreSQL, reached through `DATABASE_URL` with the psycopg driver. The object store is MinIO, reached through `STORAGE_ENDPOINT` with `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY` using boto3. Authentication is the passcode grant described above, implemented in this application; passcodes are stored only as salted hashes. `GET /api/health` returns `200` once the app is ready. Every request is logged as one structured record to standard output. The three-dimensional layer may be drawn directly on the browser's own drawing surfaces or with one openly licensed rendering library installed from the npm registry at image build time, and that library is the only client-side dependency permitted.

Use only the libraries named here plus their direct dependencies. Do not introduce a second database, cache, queue, object store, identity provider or mail vendor - the only backing services available in this environment are PostgreSQL and MinIO, and reaching for anything else is a contract violation. Both are already running and reachable at the variables above; do not download, install, compile or start a copy of either.

**What the browser receives.** The chrome's text, the first screen's text, all ten cards, and every case study's title, lead, headings, body and footer are present in the HTML the server sends. The theme class is set on the root element by a blocking script in the document head, from the choice kept in browser storage, before the body renders, so there is no flash of the wrong ground. The window itself never scrolls: every route sets a fixed full-window scroller and scrolls that element, and the document reports itself one window tall. Scroll position is read from that scroller and never from the window, anchor jumps move that scroller, sticky elements pin against it, and it does not chain its scroll to anything behind it. The scroller carries the attribute `data-scroller`. Wheel and touch scrolling glides to a stop rather than halting dead, like a sheet with some weight, and the smoothing switches off under reduced motion; keyboard scrolling keeps working on the scroller. The document root carries `data-page` set to `home`, `case-study`, `gate`, `studio` or `not-found`, and that one attribute drives what differs between page types: the rail and drawer appear only on case studies, and the scene appears only on the home page. The index container carries `data-index-grid`, and each card is an `article` carrying `data-order` set to its `sort_order`. The five home bands carry `data-band` set to `first-screen`, `statement`, `index`, `held` and `contact`.

**No binary asset ships.** The site loads no image, audio or three-dimensional model file of its own, and uses no icon font. The only raster bytes it ever serves are figures the owner uploaded, streamed from MinIO, and the only font files it serves are the three families, self-hosted, in one web font format. Every other asset is generated: the wordmark is type, the five drawings are inline vector geometry, the card media are soft two-colour gradients in pale, low-saturation tints taken from the scene's sky and the paper, seeded from each card's slug or title with the title set faintly across them at the card's aspect ratio, the stickers are inline vector outlines, the ambient sound bed is synthesised in the browser from a few slightly detuned low tones through a slowly drifting filter and a long reverb so it never audibly repeats, and the three-dimensional objects and their lighting are built from primitives in code. Fonts are openly licensed families served from this origin, and exactly one web font format ships, with no desktop format alongside it.

**Loading order.** The document and its styles arrive with the theme applied; the fonts arrive over a fallback that does not shift; the first screen's type and the chrome are readable and the site is usable; then the scene loads and reports its progress to the loader, which waits for nothing else; card media render as the index approaches; the sound bed is created only when the visitor turns sound on. The scene's arrival moves no text. The scene's drawing surfaces are sized to the window at no more than twice the pixel density, resize without reloading, run only while the first screen is visible and stop entirely when it scrolls away, and the globe stops while the document is hidden. First contentful paint stays under one and a half seconds on a mid-range laptop over a normal connection, and layout shift from the scene or the fonts is zero.

**The three-dimensional layer.** Two full-window drawing surfaces sit on the home page only: one behind all content and one in front of it that ignores the pointer, so the floating objects read as behind the words while spilling light across them. The rear surface shows a pale desaturated blue field crossed by soft warm streaks of light drifting slowly on a diagonal, like sunlight through water, with the word `hello` floating near the centre as a glossy inflated tube in a heavy rounded script, near-white where the light catches it and mid blue where it turns away, faintly iridescent between the two; and, lower right, a matte arrow-shaped pointer object in the scene's vivid blue, tilted and lit from the upper left. Nothing casts a shadow and nothing stands on a floor. The glossy look comes from a generated reflection image, a pale sky above a deeper blue below with a soft horizon and one small hot highlight, and the streaks come from a soft, tiling cloud-like pattern stretched into long diagonal bands, all generated in code. At the smallest widths a scatter of flat vinyl-sticker shapes joins them on the front surface: a rounded tab, a pen-nib outline, a five-pointed star with a face, a partial disc, a lightning bolt and a few more, twelve in all, with flat fills and heavy outlines, carrying no text and no meaning; their fills are the one place colours beyond the lime and the scene blue appear, and only at the smallest widths. The objects are named `greeting` and `pointer` in the scene so real models could replace them later. Degradation is graceful: if the renderer is unavailable and the device cannot draw the scene, or it reports a low-power or reduced-data preference at the smallest widths, the first screen renders its type, hairlines and dotted field over the flat ground with no gap and no layout change; the stickers may still render.

**Scale.** The app must stay responsive with an archive of a hundred case studies, a case study of several screens holding dozens of headings and figures, and a page-view record of tens of thousands of rows.

**Security of the gate.** The passcode comparison happens on the server with a constant-time comparison of the stored hash, the response carries only the boolean, and the grant cookie cannot be read by page script. Every gated and draft read is decided on the server for every request, never by hiding content in the page.

## Front-end specification

This section carries the visual and behavioural detail each surface needs, in the same register as `## UI/UX notes`: the arrangement and the character are fixed, and the exact values are the builder's.

### Information architecture and structure

The structure is one long home page, six case-study pages, one gated article, one studio and one not-found page, with no persistent navigation beyond the frame. The global chrome is the same on every route. Every page type scrolls an inner element; one root attribute drives what differs between them: only the case study has the rail and the drawer, and only the home page has the three-dimensional layer. The toggle for the theme and the toggle for the sound both live in the global chrome, and both choices are persisted.

### Typography, scaling, spacing and radii

The typography is the three families described in `## UI/UX notes`, with display scaling tied to window width rather than stepped. Spacing follows one base step and every gap, margin and inset is a multiple of it. The corner radii form a short scale of four: barely softened for card media, a little softer for frames, figures and the footer, the smallest softening for inline code, and fully round for capsules and slots.

### Effects vocabulary and layering

The effects vocabulary is deliberately short: a bottom hairline under a code block header, the resting ring and the waiting ring on passcode slots, a hairline ring around embedded frames, a visually hidden clip for screen-reader-only labels, the dotted field, a directional fade whose direction is set per use so one rule serves all four edges, a short soft fade masking the top and bottom of a scrolling list, and one faint vertical scrim. There is no glow and no grain texture anywhere; the dotted field is the only texture and the site is otherwise flat.

The layering, from back to front, is: the scene surface behind everything; the scroller and all page content; card eyebrow labels and the contact band just above their neighbours; the pinned statement's contents above those; the full-viewport foreground overlay canvas, which ignores the pointer and so lets a sticker pass over a headline; the loader above that; the frame above that, so nothing ever passes over the clock; and the contents drawer above everything. Content is therefore sandwiched between two drawing surfaces.

### Iconography

The iconography is five drawings and no picture files: the globe, the sound ring, the reading rail, the menu button and the scribble. Every one is inline vector geometry that stays sharp at any size. The wordmark is not a drawing at all; it is type.

### Motion inventory

The easing inventory is small and every curve is either the settling signature, a gentle symmetric default, or a pure deceleration used for entrances; a tightened symmetric curve and a strong deceleration each appear once, and the loader has its own arrive-then-settle curve. Beyond the passcode's hard blink, a second, soft interpolated blink exists for any caret that must feel alive rather than mechanical, and a loading spinner turns a full circle on a loop. Nothing else is scroll-driven: the rail's fill and the pinned band are the only things tied to scroll position.

### Performance budget

The performance budget is part of the design. The headline is readable before the scene has loaded, always; the scene causes zero layout shift and the fonts cause zero layout shift; the scene's frame budget is the display's refresh interval while the first screen is visible and zero once the loop has stopped; the globe costs nothing while the document is hidden. The code is tiny and the media would be enormous, which is why the zero-asset substitution below matters: nothing is fetched until somebody needs it, card media below the first screen render lazily, and every case-study figure carries its intrinsic size.

### Zero-asset substitution

Every class of asset is built from a recipe rather than loaded. The greeting object is a swept tube: the word authored as one continuous open path in a rounded script, sampled evenly along its length, with a round cross-section swept along it, round caps at both ends, enough segments along and around that the silhouette never facets, and a smooth near-mirror surface with a thin clear coat and a faint colour shift between facing and glancing angles. The pointer object is a closed seven-point outline, a tip, two barbs and two tail corners in the classic pointer silhouette, given thickness with a slight bevel, matte, in the scene's vivid blue. The reflection image is generated once: a pale sky blue fading to near-white at a soft horizon band across the middle, a mid blue deepening towards the bottom, and one small hot white highlight in the upper left quarter. The caustic streaks come from a soft, tiling cloud-like pattern: stretch it so it runs in long streaks, rotate it to a clear diagonal roughly a third of the way from horizontal towards vertical, falling from upper left to lower right, threshold it high so only its brightest ridges survive, blur those ridges generously, and composite them in a warm near-white over the pale blue, drifting slowly along their length; the drift is slow enough to notice only after watching for a while, and its exact period is yours. The ambient bed is a few pure, low tones tuned very slightly apart so they beat gently, softened so only their warmth comes through with that softening drifting slowly, a quieter, higher layer drifting at its own slower pace so the two never fall into step, and a long, quiet tail of reverberation. Desktop font formats are not shipped at all.

### Evidence gaps

A few things here are reconstructions rather than exact recipes, and are written as such: the scene's geometry is not recoverable from any model file, so the objects above are built from primitives; the dark theme is derived from the light one; most hover states follow the single rule of stepping one strength up the ink ladder, as a circular control does; and what the held statement's three words do during their eight screens is left to the builder, so long as the band holds still and changes its ground. Each substitution is written so the finished site looks deliberate either way, and the renderer's absence is handled by the degradation rule in `## Technical requirements`.

### The frame

The frame is one fixed layer over the whole window, above the page content and above the scene, transparent to the pointer everywhere except its controls. A top bar and a bottom bar are pinned to its edges, each the same height, each holding a row of controls that are all the same height and vertically centred in the bar, with the bar's contents pushed to its two ends. The side padding of both bars matches the page's side margin at every width.

Top left, the wordmark: two spans of the grotesque at the default text size in bold, `atlas` then `.design`, letter-spaced tight, forming one link home. Top right, the control group: `Work`, `Contact`, `THEME[A]` and `SOUND[` plus its spinner character plus `]`, all in the chrome monospace, evenly spaced, each with the full-box invisible hit area. Below the breakpoint the group is replaced by the menu button, a square button holding four bars: two flat ones at rest, and two that cross into an X when open, with the retreat and the growth both starting from the same side and each pair's second bar trailing its first by a beat. The open menu lists the same four controls and closes on Escape and on choosing an item.

Bottom left, the clock, which ticks over without anything around it moving. Bottom centre, the pointer readout, which stays centred however its digits change. Bottom right, the globe: one ellipse outline, one straight horizontal line through its middle, and six copies of a single curved meridian arc, all thin unfilled strokes in the current ink. Each arc copy is squashed and stretched horizontally about the ellipse's centre from one continuously advancing angle, the six spread evenly so the globe appears to turn; arcs that pass the far side flip their curvature. It is a drawing that changes, never a video, a sprite sheet or a rotation of the whole drawing. Beside the sound control sits a small ring drawing, a track and a sweep starting at twelve o'clock, which fills as the ambient bed loads and holds full once it is ready.

### The loader

Present on first load only, centred in the window above the content and below the frame: a short, thin capsule track with a capsule fill that grows its length from the left and does most of its travel almost immediately, then leaves once the scene is ready or has failed.

### Case-study pages

One centred column: the article is a little wider than its text column, which it pads evenly, with generous vertical padding that tightens below the breakpoint. ### The passcode screen

One window, no scrolling, on the flat ground, with the frame unchanged. Centred both ways: the prompt `Please enter passcode` in the chrome monospace in the body strength, and below it a row of four round slots of equal size, evenly spaced and centred on the window's middle. The slots are one input. Two visually hidden labels, `Passcode for` and the gated path itself, give that input its accessible name and must be kept. Each slot carries `data-slot-state` set to `empty`, `next` or `filled`. An empty slot has a resting ring in the third-strength ink; the slot waiting for the next digit has the absolute-black ring and a caret inside it, a thin full-ink bar blinking as a hard on-off flicker that never fades; a filled slot keeps the resting ring and shows its digit in the full ink. On the fourth digit the code is sent with no button. On refusal the slots clear, the waiting ring returns to the first slot, and the prompt is replaced by `That code is not right. Try again.`, or by `Too many attempts. Wait a minute and try again.` when the rate limit answers. Neither message reveals anything about the code.

## Constraints

Single owner, single site: one profile, one index, one archive. Nothing here is multi-tenant.

No visitor accounts, no sign-in form, no password reset, no comments, no likes, no newsletter, no contact form, no search, no analytics identifiers, no third-party analytics, no advertising, no cookie beyond the grant cookie, no mail sent by the product. The contact route is the mail address and the three social links, deliberately. No payments provider, no cache, no queue, no search service, no realtime service and no mail service is available; the only backing services are PostgreSQL and MinIO. No outbound network call at run time. No native application.

Every outside link points at the `www.example.com` addresses given here. No real company, product or person is named anywhere in the build; `Orchard` and `Hirebase` are placeholder former employers and every project title is a placeholder.

The seeded case-study bodies are original placeholder writing. The three-dimensional objects, their lighting and the sticker shapes are reconstructions from still pictures, not recovered geometry, and the dark palette is a derivation rather than a measurement; their exact look is the builder's within the descriptions given.

## Deployment contract

- The app must be reachable at `APP_PUBLIC_URL`. The port mapping is `${APP_PUBLIC_PORT}:4173` - `4173` is the container-internal port and `APP_PUBLIC_PORT` is what the outside world uses. Read both from the environment; never hardcode either.
- The HTTP API is served on that same origin under the `/api` prefix.
- `GET /api/health` returns `200` once the app is ready.
- The app starts from the environment image with no manual steps.
- Login credentials - or an explicit statement that there are none - are written to `/app/USER_README.md`.
- Reserved `.browser_screenshots/` and `.downloads/` directories exist at the app root, empty.
- Serve a production build behind a static or preview server - never a dev server.
- The server must keep running after this session ends and must not be a child of the shell. An ordinary background job dies with its shell, and the app will not be running when it is next opened.
- Bind `0.0.0.0`, never `127.0.0.1` or `localhost`. A loopback-only listener is unreachable from outside the container.
- The backing services named in this brief are already running and reachable at their environment variables. Do not download, install, compile or start a copy of any of them.
- Use only the providers named in this brief. No edge functions.
- No persistent volumes, no fixed container names, no custom networks.

### API shapes

| Endpoint | Request body / query | Returns |
|---|---|---|
| `GET /api/health` | none | `200` |
| `GET /api/site` | none | `brand`, `brand_suffix`, `person`, `discipline_label`, `tagline`, `introduction`, `redaction_length`, `contact_email`, `timezone_label`, `region_code`, `socials` as an array of `label`, `url` |
| `GET /api/projects` | none | a top-level JSON array of listed cards |
| `GET /api/case-studies/{slug}` | none | one published or stub case study, the gated article for a granted browser, or a draft for the studio grant |
| `GET /api/figures/{id}` | none | the figure bytes, streamed from the bucket |
| `POST /api/passcode` | `path`, `code` | `{"<path>": true}` or `{"<path>": false}`, or `429` with `{"error": "rate_limited"}` |
| `POST /api/passcode/release` | `path` | `{"<path>": false}` |
| `GET /api/studio/case-studies` | none | a top-level JSON array of every case study |
| `POST /api/studio/case-studies` | the case-study fields and an optional `card` object | the created case study in status `draft` |
| `GET /api/studio/case-studies/{id}` | none | one case study in any status |
| `PATCH /api/studio/case-studies/{id}` | any writable field | the updated case study |
| `POST /api/studio/case-studies/{id}/publish` | none | the case study in status `published` |
| `POST /api/studio/case-studies/{id}/stub` | none | the case study in status `stub` |
| `POST /api/studio/case-studies/{id}/hold` | none | the case study in status `draft` |
| `POST /api/studio/case-studies/{id}/figures` | multipart `file`, `alt_text`, `width`, `height` | the figure |
| `GET /api/studio/page-views` | none | a top-level JSON array of `route`, `viewed_at` |

Field names are exact. A list endpoint returns a top-level JSON array. A studio case study carries its card as a `card` object with the placement fields, or null. A successful call returns the named resource or shape; an invalid or unauthorized call is rejected as a client error, never as a server error and never as a silent success. A refusal carries a JSON body `{"error": "<code>", "message": "<sentence>"}` using the error codes named in `## Core features`. Every `/api/studio` endpoint requires the studio grant; health, site, projects, case studies, figures and the passcode endpoints are public and decide per request what the caller may see.

### No mocks

The named provider is the fact. Any of the following is a contract violation: an in-memory array standing in for the case-study or card tables, figure bytes written to the app container's filesystem, a database column holding figure bytes instead of an object key, index placements written into the page markup instead of read from the card records, a passcode compared in the browser, a grant kept only in page script, a draft hidden by the page while its API read or its figure stays open, or a figure endpoint that reports success without an object existing in the bucket. The app's UI and its own tables can only reflect what lives in the provider, never substitute for it.

## Definition of done

A visitor can open the home page, watch it settle, browse the ten cards, read the nDrive case study, jump to any of its headings, and unlock Field Notes with its code. The owner can unlock the studio, write a case study with a figure, place its card, and publish it, mark it as a stub, or hold it as a draft. A draft and the locked article stay unreadable to everyone without the right grant, on the page, through the API and in the object store alike.
